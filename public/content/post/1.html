🚀 Starting point

Modal runs Python functions on cloud GPUs. You decorate a function with the hardware it needs, and .remote() runs it in a container and returns the result. The four objects you use constantly: an App (a named group of functions), an Image (the container’s packages), a Volume (a persistent disk for datasets and checkpoints) and a Secret (API tokens as environment variables). Billing is per second of container time.

"""Modal crash course: an app, an image, a volume, a secret and a GPU function.

One-time setup:   pip install modal && modal setup
                  modal secret create huggingface-secret HF_TOKEN=hf_...
Run:              modal run modal_hello.py
"""
import modal

app = modal.App("pt-book-hello")

# The container image: a slim Debian base plus pinned Python packages.
image = modal.Image.debian_slim(python_version="3.12").uv_pip_install(
    "torch==2.14.1", "transformers==5.20.2"
)

# A persistent disk shared by every function in the app (datasets, checkpoints).
volume = modal.Volume.from_name("pt-book-data", create_if_missing=True)


@app.function(
    gpu="L4",                                   # "T4", "L4", "A100-80GB", "H100", "H100:8", ...
    image=image,
    volumes={"/data": volume},
    secrets=[modal.Secret.from_name("huggingface-secret")],   # exposes HF_TOKEN as an env var
    timeout=10 * 60,                            # seconds; the container is killed after this
)
def gpu_info() -> dict:
    import torch

    props = torch.cuda.get_device_properties(0)
    with open("/data/hello.txt", "w") as f:     # anything written under /data persists...
        f.write(props.name)
    volume.commit()                             # ...once committed
    return {
        "gpu": props.name,
        "memory_gb": round(props.total_memory / 2**30, 1),
        "bf16": torch.cuda.is_bf16_supported(),
    }


@app.local_entrypoint()
def main():
    print(gpu_info.remote())                    # .remote() runs it in the cloud and returns the result

What to know before your first real run:

  • GPU strings (from Modal’s GPU guide): T4, L4, A10, L40S, A100-40GB, A100-80GB, RTX-PRO-6000, H100, H200, B200, B300. Append :n for \(n\) GPUs on one machine (up to 8, e.g. "H100:8"). Multi-node training is in private beta.

  • Volumes need volume.commit() before the function exits, or writes may be lost. Another container sees them after volume.reload().

  • Imports of heavy libraries go inside the function body, so your laptop doesn’t need them installed.

  • Local code the remote function imports is shipped with .add_local_python_source("module") on the image.

  • Timeouts are in seconds. Long runs should checkpoint to a volume regularly and be able to resume.

  • Prices change, so check modal.com/pricing. Compare runs in GPU-hours and convert at the current rate.

✏️ Derivation: will it fit? GPU memory for training

Step 1. Mixed-precision training with Adam stores, per parameter: BF16 weights (2 bytes), BF16 gradients (2), FP32 master weights (4), FP32 Adam \(m\) (4) and \(v\) (4): 16 bytes per parameter, before activations.

Step 2. Qwen3-0.6B: \(0.6\times10^9\cdot16=9.6\) GB. Fits one L4 with room for activations. Qwen3-8B: 128 GB. Doesn’t fit one 80 GB GPU.

Step 3. LoRA keeps the base weights frozen in BF16 (2 bytes per parameter) and trains only the adapters: 8B \(\times\) 2 = 16 GB plus a small adapter. Fits one 24 GB card for short sequences.

Step 4. FSDP across \(G\) GPUs divides all 16 bytes by \(G\) (Chapter 6): 128 GB / 8 = 16 GB per H100 for Qwen3-8B.

Step 5. Activations grow with batch \(\times\) sequence length \(\times\) width \(\times\) layers. Gradient checkpointing (on by default in TRL’s SFT) trades about 30% more compute for storing only each layer’s input.
