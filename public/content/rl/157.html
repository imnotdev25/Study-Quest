2. Sequence KL is a sum over generated tokens

For a response \(y=(a_1,\ldots,a_L)\), autoregressive factorization gives:

\[\underbrace{ \log\frac{\pi(y\mid x)} {\pi_{\text{ref}}(y\mid x)} }_{\text{sampled sequence log-ratio}} = \underbrace{ \sum_{t=1}^{L} \left[ \log\pi(a_t\mid s_t) - \log\pi_{\text{ref}}(a_t\mid s_t) \right] }_{\text{sum of sampled token log-ratios}}\]

Here \(s_t=(x,a_{<t})\). Include generated EOS according to your token convention; exclude prompt and padding tokens.

Define:

\[k_{it} = \underbrace{ \log\pi(a_{it}\mid s_{it}) - \log\pi_{\text{ref}}(a_{it}\mid s_{it}) }_{\text{sampled token contribution}}\]

The sequence-KL-shaped reward is:

\[R_i^{\text{sum}} = \underbrace{R_i^{\text{task}}}_{\text{sequence reward}} - \underbrace{ \beta\sum_t m_{it}k_{it} }_{\text{total reference-drift penalty}}\]

If average token drift is \(c\), a length-\(L\) response pays approximately \(\beta cL\). This can favour shorter answers when task reward does not compensate for length.

A length-normalized alternative is:

\[R_i^{\text{mean}} = R_i^{\text{task}} - \beta \underbrace{ \frac{\sum_t m_{it}k_{it}} {\sum_t m_{it}} }_{\text{average drift per generated token}}\]

This is a different objective. It treats a six-token response with constant per-token drift like a two-token response, even though the six-token sequence accumulates three times the total log-ratio.

For token-level credit assignment, place the task reward once:

\[r_{it}^{\text{shaped}} = \underbrace{-\beta k_{it}}_{\text{local KL cost}} + \underbrace{ \mathbf 1[t=L_i-1]R_i^{\text{task}} }_{\text{terminal task reward}}\]

Then returns or GAE propagate the terminal reward backward. Repeating the sequence reward at every token creates a length-dependent reward bug.

Shapes:

  • token log-ratios and masks: [B, T]

  • lengths and sequence rewards: [B]

  • coefficient \(\beta\): scalar []

DPO also uses sums of completion-token log-probabilities:

\[z = \beta_{\text{DPO}} \underbrace{ \left[ \log\frac{\pi_\theta(y_w\mid x)} {\pi_{\text{ref}}(y_w\mid x)} - \log\frac{\pi_\theta(y_l\mid x)} {\pi_{\text{ref}}(y_l\mid x)} \right] }_{\text{preferred-minus-rejected sequence margin}}\]

Length-normalizing those log-probabilities changes the DPO objective; it is not merely a reporting choice. DPO remains offline preference optimization, without online rollouts or a PPO KL controller.

Hints

  • Sum over dim=1 after masking.

  • Divide each sequence sum by its own length for the per-response mean.

  • Rank with torch.argsort(..., descending=True).

  • Initialize token rewards with -beta * log_ratio.

  • Reverse return recursion: reward plus continuation times the running return.

  • A global token mean uses valid_mask.sum(), not the average sequence length.

Debugging checks

  • Accidentally penalize prompt or padding tokens.

  • Exclude EOS from one metric but include it in another.

  • Add the sequence reward at every generated token.

  • Tune \(\beta\) using a summed observation and a per-token target.

  • Assume every sampled log-ratio must be nonnegative.

  • Compare runs without logging response-length distributions.

4. Checks for understanding

  1. Why is the sum the natural sequence-distribution quantity?

  2. Is length normalization merely a variance-reduction technique?

  3. When can summed KL create an unwanted short-answer incentive?

  4. Why must KL-controller observations and targets use matching units?

Solutions

KL aggregation and shaped rewards:

sequence_log_ratio_sums = (
    sampled_log_ratios * valid_mask
).sum(dim=1)

sequence_log_ratio_means = (
    sequence_log_ratio_sums
    / valid_mask.sum(dim=1)
)

sum_shaped_rewards = (
    task_sequence_rewards
    - beta * sequence_log_ratio_sums
)

mean_shaped_rewards = (
    task_sequence_rewards
    - beta * sequence_log_ratio_means
)

sum_ranking = torch.argsort(
    sum_shaped_rewards,
    descending=True,
)

mean_ranking = torch.argsort(
    mean_shaped_rewards,
    descending=True,
)

Token reward placement:

token_rewards = (
    -beta
    * sampled_log_ratios
    * valid_mask
)

token_rewards[
    torch.arange(batch_size),
    lengths - 1,
] += task_sequence_rewards

Returns:

running_return = (
    token_rewards[:, t]
    + continuation_mask[:, t]
    * running_return
)

running_return = (
    running_return
    * valid_mask[:, t]
)

returns[:, t] = running_return

Identity check:

return_identity_error = (
    returns[:, 0]
    - sum_shaped_rewards
).abs().max()

Controller measurements:

observed_sequence_sum = (
    sequence_log_ratio_sums.mean()
)

observed_token_mean = (
    (
        sampled_log_ratios
        * valid_mask
    ).sum()
    / valid_mask.sum()
)

beta_from_sum_units = update_beta(
    beta,
    observed_sequence_sum,
    sum_target,
)

beta_from_mean_units = update_beta(
    beta,
    observed_token_mean,
    token_mean_target,
)

beta_from_mixed_units = update_beta(
    beta,
    observed_sequence_sum,
    token_mean_target,
)

The two reward vectors are:

\[R^{\text{sum}} = \underbrace{[0.65,\ 0.68,\ 0.60,\ 0.83]}_{\text{total sequence penalty}}\]

\[R^{\text{mean}} \approx \underbrace{[0.75,\ 0.92,\ 1.10,\ 0.877]}_{\text{length-normalized penalty}}\]

Thus their rankings differ:

sum:  [3, 1, 0, 2]
mean: [2, 1, 3, 0]

The return identity error should be zero: the initial return equals the task reward minus all token KL costs.

Check answers

  1. Autoregressive sequence probabilities multiply, so their log-probability ratios add across generated tokens.

  2. No. It changes which policies and response lengths the objective prefers.

  3. When task reward is roughly length-independent but positive per-token KL accumulates with length.

  4. Otherwise the controller interprets a unit mismatch as a large constraint violation and changes \(\beta\) unnecessarily.

Retrieval answers

  1. \(\pi_{\text{old}}\) measures movement within the current PPO phase; \(\pi_{\text{ref}}\) anchors cumulative behaviour to the SFT policy.

  2. A sampled token may be more probable under the reference model. Nonnegativity applies to the expected KL, not every sampled contribution.

Takeaway: sequence KL naturally sums token log-ratios. Averaging removes the direct length dependence, but defines a different objective. Choose deliberately, mask consistently, place sequence reward once, and never mix summed and per-token KL units in diagnostics or controllers.
