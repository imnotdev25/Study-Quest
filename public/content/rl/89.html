🧩 Analogy: testing a new dish on one table

A restaurant tries a new dish on one randomly chosen table per evening before putting it on the menu. Offline evaluation decides which dishes deserve a table. A small randomized online test, the canary, decides which deserve the menu.

2. Offline evidence earns a small online test—not full deployment

Offline evaluation depends on old-policy coverage and modeling assumptions. A canary rollout sends a small, randomly selected fraction of complete episodes to the candidate policy:

\[Z_i\sim\operatorname{Bernoulli}(p)\]

where \(Z_i=1\) means candidate and \(Z_i=0\) means control.

Because assignment is randomized, the difference in observed means estimates the candidate’s online effect:

\[\hat\Delta_R = \bar R_{\text{candidate}} - \bar R_{\text{control}}\]

Its Welch standard error is:

\[\operatorname{SE}(\hat\Delta_R) = \sqrt{ \frac{s_c^2}{n_c} + \frac{s_b^2}{n_b} }\]

At a fixed sample size, a one-sided approximate 95% lower bound is:

\[\operatorname{LCB}_R = \hat\Delta_R - 1.645\operatorname{SE}(\hat\Delta_R)\]

Promotion should also have an independent safety gate. For a rare incident rate \(p\), a Wilson upper bound is more stable than the simple normal approximation:

\[U_p= \frac{ \hat p+\frac{z^2}{2n} + z\sqrt{ \frac{\hat p(1-\hat p)}{n} + \frac{z^2}{4n^2} } }{ 1+\frac{z^2}{n} }\]

Promote only if both conditions hold:

\[\operatorname{LCB}_R>\Delta_{\min}\]

\[U_{\text{incident}}<p_{\max}\]

Randomize by an independent unit—usually user, prompt, or complete agent episode. Randomizing individual tokens falsely treats correlated decisions as independent and can let one policy affect another policy’s context.

These are fixed-horizon bounds. Repeatedly checking an ordinary 95% interval and stopping at the first success inflates false-positive rates; that requires planned alpha spending or an anytime-valid confidence sequence.

Tensor shapes:

  • assignment, rewards, incidents: [N]

  • candidate and control masks: [N]

  • arm-specific samples: [N_candidate], [N_control]

  • estimates, bounds and decisions: scalars

A DPO checkpoint can be the candidate, but DPO’s preference objective does not establish better task reward, tool success, latency, or safety. The randomized canary measures those deployment outcomes directly.

🔍 Deeper: randomization and rare events

Random assignment makes the two arms comparable, so a simple difference in means is unbiased. Rare safety events are the hard part. With 0 incidents in \(n\) canary requests, the 95% upper bound on the incident rate is about \(3/n\). To show a rate below \(10^{-4}\) you need about 30,000 clean canary requests, regardless of how good the reward looks.

🔑 Key ideas

  • Offline evaluation earns a canary, and online randomized evidence earns deployment.

  • A reward win never overrides an unresolved safety bound.

🚶 Walkthrough: reward passes, safety doesn’t

Canary: 2000 requests, reward \(+0.03\) (CI clears 0), incidents 0. Safety bound \(\approx3/2000=0.15\%\), but the requirement is \(<0.01\%\). Keep the canary running. Don’t ship.

Common mistakes

  • Hand-picked (non-random) canary traffic.

  • A canary window too short to see weekly patterns.

  • Treating zero observed incidents as zero risk.

Hints

  • Use torch.randperm(num_episodes)[:num_candidate_episodes].

  • Select probabilities with torch.where(candidate_mask, candidate, control).

  • Reward standard error combines the two sample variances.

  • Convert counts to float64 before division.

  • Wilson’s radius includes both Bernoulli variance and \(z^2/(4n^2)\).

  • Promotion requires both Boolean gates.

Debugging experiments

  • Route easy prompts to the candidate instead of randomizing. The observed improvement becomes confounded.

  • Randomize tokens from one response independently. Token outcomes are not independent experimental units.

  • Drop refusals or failures as “missing data.” They are policy outcomes and normally belong in evaluation.

  • Check the ordinary confidence interval after every episode and stop at the first positive result.

  • Optimize one scalar reward while ignoring incident rate, latency, cost, or subgroup regressions.

Solutions

Random assignment:

candidate_rows = torch.randperm(
    num_episodes
)[:num_candidate_episodes]

control_mask = ~candidate_mask

Outcomes:

reward_probabilities = torch.where(
    candidate_mask,
    torch.tensor(
        candidate_reward_probability
    ),
    torch.tensor(
        control_reward_probability
    ),
)

incident_probabilities = torch.where(
    candidate_mask,
    torch.tensor(
        candidate_incident_probability
    ),
    torch.tensor(
        control_incident_probability
    ),
)

rewards = (
    torch.rand(num_episodes)
    < reward_probabilities
).to(torch.float64)

incidents = (
    torch.rand(num_episodes)
    < incident_probabilities
).to(torch.float64)

Reward improvement:

candidate_rewards = rewards[
    candidate_mask
]

control_rewards = rewards[
    control_mask
]

candidate_count = (
    candidate_mask.sum()
    .to(torch.float64)
)

control_count = (
    control_mask.sum()
    .to(torch.float64)
)

candidate_reward_mean = (
    candidate_rewards.mean()
)

control_reward_mean = (
    control_rewards.mean()
)

estimated_reward_improvement = (
    candidate_reward_mean
    - control_reward_mean
)

reward_standard_error = torch.sqrt(
    candidate_rewards.var(
        correction=1
    ) / candidate_count
    +
    control_rewards.var(
        correction=1
    ) / control_count
)

reward_lcb = (
    estimated_reward_improvement
    - confidence_z
    * reward_standard_error
)

Wilson safety bound:

candidate_incidents = incidents[
    candidate_mask
]

candidate_incident_count = (
    candidate_incidents.sum()
)

candidate_incident_rate = (
    candidate_incidents.mean()
)

wilson_denominator = (
    1.0
    + confidence_z ** 2
    / candidate_count
)

wilson_center = (
    candidate_incident_rate
    + confidence_z ** 2
    / (2.0 * candidate_count)
)

wilson_radius = (
    confidence_z
    * torch.sqrt(
        candidate_incident_rate
        * (
            1.0
            - candidate_incident_rate
        )
        / candidate_count
        + confidence_z ** 2
        / (
            4.0
            * candidate_count.square()
        )
    )
)

candidate_incident_ucb = (
    wilson_center + wilson_radius
) / wilson_denominator

Promotion gates:

reward_gate_passes = (
    reward_lcb
    > minimum_reward_improvement
)

safety_gate_passes = (
    candidate_incident_ucb
    < maximum_incident_rate
)

promote_candidate = (
    reward_gate_passes
    & safety_gate_passes
)

The exact expected reward improvement is:

\[0.72-0.60=0.12\]

The approximate reward standard error is:

\[\sqrt{ \frac{0.72(0.28)}{400} + \frac{0.60(0.40)}{3600} } \approx0.0239\]

Therefore, its expected lower bound is:

\[0.12-1.645(0.0239) \approx0.081\]

This comfortably clears the required improvement of 0.02.

For safety, the candidate’s true rate is only 0.035, but the expected Wilson upper bound with 400 candidate episodes is roughly:

\[U_{\text{incident}}\approx0.054\]

Thus reward will likely pass while safety blocks promotion. The candidate may actually be safe, but the canary has not produced enough evidence to establish that. Quadrupling the sample size approximately halves the uncertainty radius.

Check answers

  1. Each arm directly produces on-policy outcomes from randomly comparable traffic, so its sample mean is unbiased for that arm’s current deployment value.

  2. Reward is common and has a large effect size; rare safety events need substantially more observations, especially when the true rate is close to the limit.

  3. Persistent assignment prevents cross-policy contamination, respects temporal correlation, and makes the independent sample size closer to the number of users or episodes.

  4. Log assignment probability, randomization unit, policy version, prompt/context, completion status, reward components, incidents, costs, latency, masks, timestamps, exclusions, and the precommitted stopping rule.

Retrieval answers

  1. Moving away from the behavior policy makes a shrinking subset of logged actions carry increasingly large importance weights.

  2. Bonferroni adjusts for repeated comparisons across a prespecified grid; it does not repair support failure, data leakage, distribution shift, or candidate tuning on evaluation data.

Takeaway: offline evaluation decides what deserves a canary. Randomized online evidence decides what deserves deployment—and reward improvement never overrides an unresolved safety bound.
