2. “Not significant” may simply mean “underpowered”

Before launching a canary, choose the minimum effect worth detecting:

\[\Delta_*\]

This is the smallest improvement that would justify deployment—not an optimistic prediction of the candidate’s gain.

For equal-sized candidate and control arms with \(n\) independent units per arm and outcome variance \(\sigma^2\):

\[\operatorname{SE}(\hat\Delta) = \sqrt{\frac{2\sigma^2}{n}}\]

For a one-sided improvement test with false-positive probability \(\alpha\) and desired power \(1-\beta\):

\[n \approx \frac{ 2\sigma^2 \left( z_{1-\alpha}+z_{1-\beta} \right)^2 }{ \Delta_*^2 }\]

Power is the probability of successfully detecting \(\Delta_*\) when it is real.

For repeated episodes from each user:

\[Y_{u,t} = \tau Z_u+b_u+\epsilon_{u,t}\]

the variance of a user’s mean across \(m\) episodes is:

\[\sigma_{\bar Y}^2 = \sigma_b^2+\frac{\sigma_\epsilon^2}{m}\]

Use this user-level variance and the number of users in the planning equation. Treating all episodes as independent can dramatically underestimate the required traffic.

Notice the inverse square:

\[n\propto\frac1{\Delta_*^2}\]

Detecting half the effect requires approximately four times as many independent units.

This is fixed-horizon planning. If you repeatedly inspect results and stop early, use a prespecified sequential method or anytime-valid evidence instead.

Tensor shapes in the simulation:

  • user effects: [R, 2N]

  • episode outcomes: [R, 2N, M]

  • user means: [R, 2N]

  • estimates and standard errors: [R]

For subgroup gates, calculate power for the rarest important group. If that group is 10% of traffic, obtaining 400 independent group members may require roughly 4,000 total users before accounting for arm allocation.

DPO dataset size and preference-pair accuracy do not determine online power. The relevant sample size is the number of independent deployment units producing the outcome you intend to claim improved.

🔍 Deeper: sample size and MDE

Two-arm comparison, per-arm sample size: \[n=\frac{2(z_{1-\alpha/2}+z_{1-\beta})^2\sigma^2}{\delta^2}\times\mathrm{DEFF},\] with \(z_{0.975}=1.96\) and \(z_{0.80}=0.84\), so \(2(2.80)^2=15.7\). MDE (minimum detectable effect) is the same formula solved for \(\delta\). Choose \(\delta\) as the smallest effect that would change your decision, not as whatever your budget can detect.

🔑 Key ideas

  • Fix the meaningful effect and the variance at the randomization unit first.

  • More logged rows can’t rescue a canary that lacks independent users.

🚶 Walkthrough: size the canary

\(\sigma=0.5\), \(\delta=0.02\): \(n=15.7\times0.25/0.0004\approx9800\) users per arm. With DEFF 6.7 for turn-level outcomes and 20 turns per user, measure at the user level, or plan about \(9800\times6.7\) turns.

Common mistakes

  • “Post-hoc power” computed from the observed effect.

  • Counting rows instead of independent users.

  • Picking the MDE to fit the budget.

Solutions

Variance structure:

user_variance = (
    user_effect_standard_deviation ** 2
)

episode_noise_variance = (
    episode_noise_standard_deviation ** 2
)

episode_outcome_variance = (
    user_variance
    + episode_noise_variance
)

user_mean_outcome_variance = (
    user_variance
    + episode_noise_variance
    / episodes_per_user
)

intraclass_correlation = (
    user_variance
    / episode_outcome_variance
)

design_effect = (
    1.0
    + (
        episodes_per_user - 1
    ) * intraclass_correlation
)

Sample-size plans:

z_sum_squared = (
    z_alpha + z_power
).square()

naive_episodes_per_arm = math.ceil(
    (
        2.0
        * episode_outcome_variance
        * z_sum_squared
        / minimum_detectable_effect ** 2
    ).item()
)

naive_users_per_arm = math.ceil(
    naive_episodes_per_arm
    / episodes_per_user
)

correct_users_per_arm = math.ceil(
    (
        2.0
        * user_mean_outcome_variance
        * z_sum_squared
        / minimum_detectable_effect ** 2
    ).item()
)

Simulation:

def simulate_power(
    users_per_arm,
    treatment_effect,
):
    total_users = 2 * users_per_arm

    candidate_indicator = torch.zeros(
        total_users
    )
    candidate_indicator[
        :users_per_arm
    ] = 1.0

    user_effects = (
        user_effect_standard_deviation
        * torch.randn(
            num_repetitions,
            total_users,
        )
    )

    episode_noise = (
        episode_noise_standard_deviation
        * torch.randn(
            num_repetitions,
            total_users,
            episodes_per_user,
        )
    )

    outcomes = (
        treatment_effect
        * candidate_indicator[
            None, :, None
        ]
        + user_effects[:, :, None]
        + episode_noise
    )

    user_mean_outcomes = outcomes.mean(
        dim=-1
    )

    candidate_user_outcomes = (
        user_mean_outcomes[
            :, :users_per_arm
        ]
    )

    control_user_outcomes = (
        user_mean_outcomes[
            :, users_per_arm:
        ]
    )

    estimated_effects = (
        candidate_user_outcomes.mean(
            dim=1
        )
        - control_user_outcomes.mean(
            dim=1
        )
    )

    standard_errors = torch.sqrt(
        candidate_user_outcomes.var(
            dim=1,
            correction=1,
        ) / users_per_arm
        +
        control_user_outcomes.var(
            dim=1,
            correction=1,
        ) / users_per_arm
    )

    lower_bounds = (
        estimated_effects
        - z_alpha * standard_errors
    )

    declarations = (
        lower_bounds > 0.0
    )

    return (
        declarations.to(
            torch.float64
        ).mean(),
        estimated_effects.mean(),
        standard_errors.mean(),
    )

The intraclass correlation is:

\[\rho = \frac{1}{1+1} = 0.5\]

With five episodes per user:

\[D = 1+4(0.5) = 3\]

The variance of one user’s average outcome is:

\[\sigma_{\bar Y}^2 = 1+\frac15 = 1.2\]

For a one-sided 5% test and 80% power:

\[z_{0.95}\approx1.645, \qquad z_{0.80}\approx0.842\]

Correct planning therefore needs:

\[n \approx \frac{ 2(1.2)(1.645+0.842)^2 }{ 0.2^2 } \approx371\]

users per arm.

The naive planner treats episodes as independent and requests only about 124 users per arm. With correct cluster-aware analysis, that plan’s real MDE is approximately:

\[0.346\]

Its power for a true 0.20 effect is only about 42%. The correctly planned canary should achieve approximately 80% power.

A correctly analyzed underpowered test still has approximately a 5% false-positive rate. Its problem is excessive false negatives—not invented positive effects. Naive row-level analysis, as seen in Session 124, can inflate false positives too.

Check answers

  1. The effect appears squared in the denominator, so replacing \(\Delta\) with \(\Delta/2\) multiplies the requirement by four.

  2. New users add new independent user effects. Extra episodes mostly average down episode noise while leaving shared user variation.

  3. Power is the probability of detecting a real target effect; the false-positive rate is the probability of declaring improvement when the null is true.

  4. Plan for the hardest prespecified gate, incorporate multiplicity into its critical value, and ensure rare groups receive enough independent units. Oversampling is possible, but aggregate estimates must then restore deployment weights.

Retrieval answers

  1. For \(m\) equally sized observations per cluster, \(D=1+(m-1)\rho\).

  2. Equal cluster sizes preserve the same weighted mean difference, while clustering reduces the number of independent units used to estimate uncertainty.

Takeaway: choose the smallest practically meaningful effect, estimate variance at the randomization unit, and commit to the sample size before seeing outcomes. More logged rows cannot rescue a canary that lacks independent users.
