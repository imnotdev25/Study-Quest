🧩 Analogy: “make coffee” is one decision

You decide “make coffee” once. Then a dozen small actions happen (grind, pour, wait) without you re-deciding to make coffee each second. Options are multi-step actions like that: a high-level policy picks a routine (“research this topic”), and a low-level policy runs it until it decides to stop.

2. A complete tool routine can be one high-level action

A tool agent may repeatedly execute recognizable routines:

  • search, open result, extract evidence;

  • write code, run tests, inspect failure;

  • query database, validate rows, summarize;

  • request approval, wait, continue.

Hierarchical RL represents such a routine as an option. An option has:

  • an initiation rule: where it can start;

  • an internal policy \(\pi_o(a\mid s)\);

  • a termination rule \(\beta_o(s)\).

The high-level policy chooses:

\[o_t\sim\mu_\theta(o\mid s_t)\]

The option then executes \(k\) primitive actions before returning control.

Its accumulated discounted reward is:

\[R_t^{(o)} = \sum_{j=0}^{k-1} \gamma^j r_{t+j}\]

The high-level SMDP target is:

\[y_t^{(o)} = R_t^{(o)} + \gamma^k (1-\text{terminated}) V(s_{t+k})\]

Using only \(\gamma\) for every option treats a one-step calculation and a ten-step research routine as having equal temporal distance from the next decision.

The high-level option log-probability occurs once:

\[L_{\text{high}} = -\log\mu_\theta(o_t\mid s_t) \hat A_t^{(o)}\]

Repeating this same log-probability at every internal tool step weights long options more heavily. Internal actions need their own log-probabilities and credit if their policy is also trained with RL.

Tensor shapes:

  • primitive rewards and masks: [B, T];

  • option durations: [B];

  • option rewards and targets: [B];

  • selected-option log-probabilities: [B];

  • primitive-action log-probabilities: [B, T].

DPO can rank complete option traces, but it remains fixed-data preference optimization. Online hierarchical RL can explore which option to choose, how to execute it and when to terminate it.

🔍 Deeper: options and their targets

An option is \(o=(I_o,\pi_o,\beta_o)\): where it can start, its internal policy, and its termination probability. For an option that ran \(k\) steps from \(s\) to \(s'\): \[Q_\Omega(s,o)\leftarrow Q_\Omega(s,o)+\alpha\Big[\textstyle\sum_{i=0}^{k-1}\gamma^ir_{t+i+1}+\gamma^kV_\Omega(s')-Q_\Omega(s,o)\Big].\] This is SMDP Q-learning (Topic 68) with \(\tau=k\). Aggregate the inner rewards once and bootstrap across the whole duration.

🔑 Key ideas

  • Choose an option once, aggregate its rewards once, bootstrap across its duration.

  • Keep high-level and primitive credit paths separate.

🚶 Walkthrough: option target

Option ran 4 steps with rewards \((0,0,1,0)\), \(\gamma=0.9\), \(V_\Omega(s')=2\). Inner sum \(=0.9^2=0.81\). Target \(=0.81+0.9^4\cdot2=0.81+1.312=2.12\).

Common mistakes

  • Bootstrapping with \(\gamma\) instead of \(\gamma^k\).

  • Updating \(Q_\Omega\) at every primitive step as if the option were re-chosen.

  • Letting an option run forever (no termination).

Hints

  • Duration is the mask sum across time.

  • Replace padded rewards with zero before reduction.

  • Use gamma ** positions for within-option rewards.

  • Use the logarithmic form for boundary discounts.

  • The buggy target applies only one factor of gamma.

  • Detach targets before using them as critic labels.

  • Repeating a summed high-level loss multiplies its effective weight by the duration.

Debugging experiments

Remove safe_rewards. The padded values of 99 dominate short-option returns.

Replace boundary_discounts with a scalar gamma. Long options receive excessive bootstrap value.

Use an undiscounted sum for internal rewards while using discounted boundary value. That defines a different objective and may create inconsistent option comparisons.

Finally, train a termination policy without logging option duration. A policy that immediately terminates every option can look numerically stable while eliminating all useful temporal abstraction.

Solutions

Option durations:

durations = primitive_mask.sum(
    dim=1
)

Within-option rewards:

within_option_discounts = (
    gamma ** positions
)

safe_rewards = torch.where(
    primitive_mask,
    primitive_rewards,
    torch.zeros_like(primitive_rewards),
)

option_rewards = (
    safe_rewards
    * within_option_discounts[None, :]
).sum(dim=1)

Boundary discounts:

boundary_discounts = torch.exp(
    math.log(gamma)
    * durations.to(
        primitive_rewards.dtype
    )
)

Targets:

correct_targets = (
    option_rewards
    + boundary_discounts
    * (~terminated).to(
        primitive_rewards.dtype
    )
    * next_values.detach()
)

buggy_targets = (
    option_rewards
    + gamma
    * (~terminated).to(
        primitive_rewards.dtype
    )
    * next_values.detach()
)

High-level weights:

option_advantages = (
    correct_targets
    - option_values
)

correct_high_level_weights = (
    option_advantages.detach()
)

repeated_high_level_weights = (
    option_advantages.detach()
    * durations
)

The option rewards are:

\[R_0^{(o)} = 0.2+0.9(0.3) = 0.47\]

\[R_1^{(o)} = 0.2+0.9(0.1)+0.9^2(0.1)+0.9^3(0.1) = 0.4439\]

The first nonterminal target is:

\[0.47+0.9^2(4)=3.71\]

The four-step option target is:

\[0.4439+0.9^4(4) \approx3.0683\]

Using a single discount incorrectly gives approximately \(4.04\) for the four-step option.

The terminal option receives no bootstrap value:

\[y_2^{(o)} = 0+0+0.9^2(1) = 0.81\]

Retrieval answers

  1. It is the remaining future-value multiplier after the action’s elapsed duration.

  2. The same numerical duration means different elapsed time in seconds, minutes or environment ticks, changing the effective objective.

Takeaway: choose an option once, aggregate its internal rewards once and bootstrap across its full duration. Keep high-level and primitive-level credit paths distinct.
