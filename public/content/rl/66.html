🧩 Analogy: game over vs the café closing

A board game ends because someone won: there’s nothing after that. Or it ends because the café is closing, but the position on the board still has a likely winner. Termination means future value is 0. Truncation means the future is unobserved but real, so you estimate it with \(V\). Topic 47 had the idea. This topic is about the plumbing that breaks it.

2. “Done” hides two different events

A trajectory can stop because:

  • Termination: the task truly ended, such as success, failure or an absorbing state.

  • Truncation: data collection stopped, such as a step limit, context limit or infrastructure timeout.

For a one-step TD target:

\[y_t = r_t+ \gamma \left(1-\text{terminated}_t\right) V(s_{t+1})\]

At a true terminal state, there is no future value:

\[y_t=r_t\]

At an artificial truncation, the underlying process may continue:

\[y_t=r_t+\gamma V(s_{t+1})\]

Treating every timeout as terminal systematically underestimates states near the collection limit.

Tool-agent semantics matter. A network timeout may be an artificial truncation. Exhausting a real user-defined tool budget may instead be task failure and therefore termination.

GAE needs two masks:

\[\delta_t = r_t+ \gamma(1-\text{terminated}_t)V(s_{t+1}) - V(s_t)\]

\[\hat A_t = \delta_t+ \gamma\lambda C_t\hat A_{t+1}\]

where:

\[C_t = 1- (\text{terminated}_t \lor \text{truncated}_t)\]

The bootstrap mask allows the boundary-state value after truncation. The continuation mask prevents the GAE recursion from crossing into padding or another episode.

Tensor shapes:

  • rewards and values: [B, T];

  • terminated, truncated and valid masks: [B, T];

  • TD targets, deltas and advantages: [B, T].

Detach bootstrap values and targets when training the critic. Otherwise, the network can reduce loss by moving both the prediction and its own target.

DPO has no critic or bootstrap target. However, labeling every timed-out trace as a rejected response can still teach infrastructure failures as behavioral preferences.

🔍 Deeper: auto-reset environments

Gymnasium’s step returns (obs, reward, terminated, truncated, info). Vectorized environments auto-reset, so when an episode ends, the returned obs is already the next episode’s first observation. The real final observation is in info["final_observation"] (or similar, depending on the version). Bootstrap target at a truncation: \(r+\gamma V(s_{\text{final}})\), using the true final observation, never the reset one. Storage: reset recurrent state and trajectory buffers on either flag. Zero the bootstrap only on terminated.

🔑 Key ideas

  • Reset storage at both events, but zero bootstrapping only at true termination.

  • Fetch the real final observation from the auto-reset info.

🚶 Walkthrough: one terminal trace, one truncated

\(\gamma=0.9\), last reward 1. Terminal: target \(=1\). Truncated with \(V(s_{\text{final}})=4\): target \(=1+3.6=4.6\). Truncated but using the reset observation with \(V(s_0^{\text{new}})=0.5\): \(1.45\), which is wrong.

Common mistakes

  • done = terminated or truncated used in the target.

  • Bootstrapping from the reset observation.

  • Treating a context-limit stop as success or failure without saying so.

Debugging experiments

Use ~terminated as both the bootstrap and GAE-continuation mask. Bootstrapping becomes correct, but the recurrence may cross a truncation boundary into padding or the next packed episode.

Remove valid from the reverse recursion. The padded values of 99 contaminate trace 1.

Let next_values require gradients and omit .detach() in a real critic. Inspect how gradients flow into both sides of the TD target.

Finally, classify a real tool-call budget as truncation. If exhausting that budget actually means task failure, bootstrapping invents value beyond a boundary where the agent cannot continue.

Solutions

Bootstrap masks:

bootstrap_mask = (
    ~terminated
).to(rewards.dtype)

buggy_bootstrap_mask = (
    ~done
).to(rewards.dtype)

TD targets:

correct_targets = (
    rewards
    + gamma
    * bootstrap_mask
    * next_values.detach()
)

buggy_targets = (
    rewards
    + gamma
    * buggy_bootstrap_mask
    * next_values.detach()
)

TD residuals:

correct_deltas = (
    correct_targets - values
) * valid

buggy_deltas = (
    buggy_targets - values
) * valid

GAE continuation mask:

continuation_mask = (
    valid
    & ~terminated
    & ~truncated
).to(rewards.dtype)

Reverse recursion:

for time in reversed(range(rewards.shape[1])):
    correct_running = (
        correct_deltas[:, time]
        + gamma
        * gae_lambda
        * continuation_mask[:, time]
        * correct_running
    )

    buggy_running = (
        buggy_deltas[:, time]
        + gamma
        * gae_lambda
        * continuation_mask[:, time]
        * buggy_running
    )

    correct_running = (
        correct_running
        * valid[:, time]
    )

    buggy_running = (
        buggy_running
        * valid[:, time]
    )

    correct_advantages[:, time] = (
        correct_running
    )

    buggy_advantages[:, time] = (
        buggy_running
    )

The naturally terminated transition has:

\[y=1\]

The truncated transition should retain its estimated future:

\[y = 1+0.9(5) = 5.5\]

The buggy calculation instead gives:

\[y_{\text{buggy}}=1\]

This changes the boundary delta from:

\[5.5-2=3.5\]

to:

\[1-2=-1\]

The agent therefore receives negative credit where the correct estimate is positive.

Check answers

  1. Artificial collection limits do not erase the environment’s remaining future return.

  2. TD may bootstrap from a truncated boundary state, while GAE must still stop its sampled recursion at that boundary.

  3. When the limit is part of the task and no continuation is available, such as exhausting a hard user budget.

  4. Log termination and truncation counts separately, boundary TD errors, advantages by final-step type, padding leakage and value estimates near time limits.

Retrieval answers

  1. PPO also requires identical histories, hidden-state initialization and action masks; unchanged weights alone are insufficient.

  2. Burn-in reconstructs the recurrent state from preceding observations before loss-bearing timesteps.

Takeaway: reset trajectory storage at both termination and truncation, but zero value bootstrapping only when the task itself truly ends.
