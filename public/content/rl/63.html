🧩 Analogy: free throws vs “eventually”

A basketball player who hits 30% of free throws will “eventually” score if you give them 10 tries. Saying “they score 97% of the time (pass@10)” hides that one shot usually misses. Users usually get one attempt, so report both numbers.

Very different single-shot reliabilities can look similar at large \(k\).

2. More retries can hide unreliable behavior

For prompt \(x\), let a stochastic agent produce success indicators:

\[S_{x,j}\in\{0,1\}\]

The single-run success probability is:

\[p_x=P(S=1\mid x)\]

With \(k\) independent attempts, define:

\[\mathrm{pass}@k = P(\text{at least one success})\]

Then:

\[\mathrm{pass}@k = 1-(1-p_x)^k\]

If \(p_x=0.2\), then:

\[\mathrm{pass}@8 = 1-0.8^8 \approx0.832\]

The agent still fails on about 80% of individual attempts. Pass@8 describes a retry product; it does not describe first-attempt reliability.

For an agent, report both:

  • one-shot success or per-run reliability;

  • pass@\(k\);

  • tool-call count, latency and cost;

  • failure categories such as invalid action, timeout, wrong answer and unsafe behavior;

  • prompt-level slices, such as easy versus hard tasks.

Compute metrics per prompt first. Repeated rollouts for the same prompt are nested observations, so confidence intervals should bootstrap prompts rather than pretend all \(P\times K\) runs are independent.

For independent attempts conditional on a prompt:

  • success: [P, K];

  • per-prompt reliability: [P];

  • per-prompt pass@\(k\): [P];

  • aggregate metric: scalar.

DPO preference accuracy does not directly measure pass@\(k\). DPO trains on fixed pairs; fresh rollouts are required to measure stochastic agent success.

Keep evaluation metrics detached from training. Fixed termination rules, padding masks and invalid-action masks must be identical across compared systems. A success reward should not silently include a tool-use bonus.

🔍 Deeper: an unbiased pass@k estimator

With \(n\) samples per task and \(c\) successes: \[\widehat{\text{pass@}k}=1-\frac{\binom{n-c}{k}}{\binom nk} .\] The naive \(1-(1-c/n)^k\) is biased upward for small \(n\), because it plugs a noisy \(\hat p\) into a nonlinear function. Pass@\(k\) also assumes independent attempts with a perfect selector. If the user must pick which attempt to trust, the real success rate is lower.

🔑 Key ideas

  • Report pass@1 for user experience and pass@\(k\) for retry systems.

  • Use the unbiased combinatorial estimator.

🚶 Walkthrough: \(n=10\), \(c=3\), \(k=5\)

Unbiased: \(1-\binom75/\binom{10}5=1-21/252=0.917\). Naive: \(1-0.7^5=0.832\). The two disagree here because the naive form treats draws as with replacement, while the combinatorial one samples without replacement from the 10 you actually have.

Common mistakes

  • \(k>n\) (undefined, so draw more samples).

  • Reporting only pass@\(k\) to users.

  • Counting retries that reuse one failed tool state as independent.

Hints

  • Convert Boolean success to floating point before taking means.

  • Use success[:, :k].any(dim=1) for empirical pass@\(k\).

  • The theoretical formula is 1 - (1 - prompt_probs).pow(k).

  • Use hard and easy to slice prompt-level metrics.

  • Bootstrap with per_prompt_reliability[bootstrap_indices].

  • Use torch.quantile with probabilities [0.025, 0.975].

Debugging experiments

  • Shuffle success rows between prompts before computing pass@\(k\). This destroys prompt difficulty and can hide hard-prompt failures.

  • Compute 1 - (1 - per_prompt_reliability).pow(k) from the same eight samples. This plug-in estimate is different from observing whether at least one sampled attempt succeeded.

  • Treat padded or timed-out traces as successes by omitting the termination mask. Pass@\(k\) becomes artificially high.

  • Use the same random seed for every policy variant. Shared rollout randomness can make differences look smaller than they are; completely unrelated seeds can also add evaluation noise.

  • For extremely small \(p\), evaluate \(1-(1-p)^k\) with log1p and expm1 to reduce cancellation.

Solutions

One-shot and per-prompt reliability:

one_shot_rate = (
    success[:, 0]
    .to(torch.float64)
    .mean()
)

per_prompt_reliability = (
    success
    .to(torch.float64)
    .mean(dim=1)
)

Empirical pass@\(k\):

pass_at_k = {
    k: (
        success[:, :k]
        .any(dim=1)
        .to(torch.float64)
    )
    for k in ks
}

Theoretical pass@\(k\):

theoretical_pass_at_k = {
    k: (
        1.0
        - (1.0 - prompt_probs).pow(k)
    )
    for k in ks
}

Group metrics:

group_metrics = {
    "hard_reliability":
        per_prompt_reliability[hard].mean().item(),

    "easy_reliability":
        per_prompt_reliability[easy].mean().item(),

    "hard_pass_at_8":
        pass_at_k[8][hard].mean().item(),

    "easy_pass_at_8":
        pass_at_k[8][easy].mean().item(),
}

Prompt-level bootstrap interval:

reliability_ci = torch.quantile(
    bootstrap_means,
    torch.tensor([0.025, 0.975]),
)

For \(p=0.2\):

\[\mathrm{pass}@8 = 1-0.8^8 \approx0.832\]

For \(p=0.9\), pass@8 is approximately \(1-0.1^8\), nearly one.

Check answers

  1. More attempts create more chances for at least one success, even when the policy itself has not improved.

  2. Users may need retries, fallback selection or best-of-\(k\) serving; individual attempts remain unreliable.

  3. The same prompt contributes several correlated measurements. Prompt difficulty is shared across its rollouts.

  4. Log invalid tool calls, timeouts, wrong final answers, unsafe actions, tool count, latency and monetary cost.

Retrieval answers

  1. The multiplier adapts the penalty until observed cost approaches the budget; a guessed value may overconstrain or underconstrain learning.

  2. Shaping and tool bonuses can rise while actual task quality falls. Raw success and cost reveal the real objective.

Takeaway: evaluate both reliability and retry performance. Pass@\(k\) is useful for systems that may retry, while one-shot success reveals what a user experiences on a single attempt.
