🧩 Analogy: a thermostat

A thermostat doesn’t decide what temperature is good; you set the target. It turns the heat up when the room is too cold and down when it’s too warm. Adaptive KL control is a thermostat for policy drift: raise \(\beta\) when KL is above target, lower it when below. It controls how far you move, not whether the movement is good.

Stylized: KL starts off target, the controller adjusts \(\beta\), and KL settles into the band.

2. KL coefficient as an adjustable brake

Online RLHF often optimizes:

\[J(\theta) = \mathbb E_{y\sim\pi_\theta}[R(y)] - \beta\, D_{\mathrm{KL}} (\pi_\theta\Vert\pi_{\mathrm{ref}})\]

Reward pulls the policy toward high-scoring responses. KL keeps it near the reference policy.

A fixed \(\beta\) is difficult to tune:

  • too small: the policy may drift, exploit rewards or lose capabilities;

  • too large: learning barely changes the policy;

  • reward-scale changes alter the effective strength of the same \(\beta\).

Treat \(\beta\) like a thermostat:

\[\beta \leftarrow \beta \exp\left[ \eta\left( \frac{D_{\mathrm{KL}}}{D_{\text{target}}}-1 \right) \right]\]

If observed KL exceeds the target, increase \(\beta\). If KL is too low, decrease it.

Usually clamp both the controller error and \(\beta\):

\[e= \operatorname{clip} \left( \frac{D_{\mathrm{KL}}}{D_{\text{target}}}-1, -e_{\max},e_{\max} \right)\]

This prevents one noisy rollout batch from making the penalty explode.

For categorical actions:

\[D_{\mathrm{KL}}(\pi\Vert\pi_{\mathrm{ref}}) = \sum_a \pi(a) \left[ \log\pi(a)-\log\pi_{\mathrm{ref}}(a) \right]\]

Tensor shapes:

  • policy and reference logits: [actions]

  • probabilities and log-probabilities: [actions]

  • reward, KL, objective and \(\beta\): scalar

The controller update is an outer-loop rule, not part of actor backpropagation. Use a detached KL diagnostic.

DPO also contains a reference-relative scale commonly called \(\beta\), but ordinary DPO does not collect online rollouts and adjust that coefficient from observed rollout KL.

🔍 Deeper: a proportional controller

A common rule, from Ziegler et al. (2019): \[e_t=\operatorname{clip}\Big(\frac{\mathrm{KL}_t-\mathrm{KL}_{\text{target}}}{\mathrm{KL}_{\text{target}}},-0.2,0.2\Big),\qquad\beta_{t+1}=\beta_t\,(1+K_\beta\,e_t).\]

  • The error is relative and clipped, so one noisy KL reading can’t swing \(\beta\) wildly.

  • The update is multiplicative, which keeps \(\beta>0\).

  • Update \(\beta\) outside backprop. It’s a controller, not a learned parameter.

Watch the whole KL distribution: a mean on target can hide a few prompts with huge KL.

🔑 Key ideas

  • Adaptive \(\beta\) regulates movement, not quality.

  • Clip the controller’s error and monitor KL per prompt, not only the average.

🚶 Walkthrough: two controller steps

Target 6, \(K_\beta=0.1\), \(\beta=0.1\). KL measured 9: \(e=\operatorname{clip}(0.5)=0.2\), so \(\beta\gets0.1\cdot1.02=0.102\). KL measured 3: \(e=\operatorname{clip}(-0.5)=-0.2\), so \(\beta\gets0.102\cdot0.98=0.09996\).

Common mistakes

  • Putting \(\beta\) into the optimizer as a parameter.

  • Updating in the wrong direction (lowering \(\beta\) when KL is too high).

  • Measuring KL per token and comparing it with a sequence-level target.

⚙️ Algorithm: Adaptive KL controller
Input: target KL, gain \(K_\beta\) (e.g. \(0.1\)), initial \(\beta_0\)
\(\beta\gets\beta_0\)
for each PPO iteration do
run the PPO update with KL penalty \(\beta\)
measure \(\mathrm{KL}_t\) on the batch (sequence-total, response tokens only)
\(e\gets\operatorname{clip}\big((\mathrm{KL}_t-\text{target})/\text{target},-0.2,0.2\big)\)
\(\beta\gets\beta\,(1+K_\beta e)\) ▷ outside autograd: a controller, not a parameter
end

Hints

  • Use log_softmax, then exponentiate.

  • Expected reward is sum(probability * reward).

  • Forward KL weights each log-ratio by the current policy.

  • The optimizer minimizes, so negate the objective.

  • Detach KL before updating the controller.

  • Clamp \(\beta\) to a positive, finite range.

Debugging experiments

Reverse the controller sign:

beta = beta * torch.exp(
    -controller_rate * clipped_error
)

Now excessive KL reduces the penalty, creating positive feedback: more drift causes a weaker brake.

Next, remove the error clamp. A noisy high-KL batch can multiply \(\beta\) sharply and stall learning.

Finally, multiply rewards by 100. The policy pressure becomes much stronger, so the controller must raise \(\beta\) substantially. Advantage normalization does not automatically normalize every reward-versus-KL tradeoff.

4. Checks for understanding

  1. Why must the controller use detached KL?

  2. Can a target KL guarantee that the policy is safe or correct?

  3. Why should KL be logged by prompt category and token position?

  4. What happens if the target KL is unrealistically small?

Solutions

Policy quantities:

policy_log_probs = policy_logits.log_softmax(
    dim=-1
)

probabilities = policy_log_probs.exp()

Expected reward:

expected_reward = (
    probabilities * action_rewards
).sum()

Forward KL:

kl = (
    probabilities
    * (
        policy_log_probs
        - reference_log_probs
    )
).sum()

Actor objective:

objective = (
    expected_reward - beta * kl
)

loss = -objective

Controller:

relative_error = (
    kl.detach() / target_kl - 1.0
)

clipped_error = relative_error.clamp(
    -maximum_error,
    maximum_error,
)

beta = (
    beta
    * torch.exp(
        controller_rate * clipped_error
    )
).clamp(
    min=1e-4,
    max=100.0,
)

Action 2 gains probability because it has the highest reward. As KL exceeds the target, \(\beta\) increases and makes further movement away from the reference more expensive.

The controller and actor continually react to each other, so finite learning rates can produce oscillation. Real RLHF adds sampling noise and delayed measurements; implementations commonly smooth KL over rollout batches and adjust \(\beta\) slowly.

Check answers

  1. The controller is a hyperparameter update, not part of the actor objective. Differentiating through it introduces an unintended gradient path.

  2. No. KL measures distributional distance from the reference, not factuality, safety or task success.

  3. An acceptable mean can hide extreme drift on rare prompts or late tokens.

  4. The controller drives \(\beta\) upward until policy updates become very small, potentially preventing useful learning.

Retrieval answers

  1. Dividing by a tiny group standard deviation turns small—and possibly noisy—reward gaps into order-one advantages.

  2. Scaling reward scales its gradient, but does not scale the KL gradient; their relative strength therefore changes.

Takeaway: adaptive KL control regulates policy movement, not policy quality. Update its coefficient outside actor backpropagation, clamp noisy controller changes, and monitor both independent evaluation metrics and the full distribution of KL—not merely its mean.
