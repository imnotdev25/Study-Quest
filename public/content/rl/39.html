🧩 Analogy: 4.9 stars from 8 reviews

Would you trust a restaurant with 4.9 stars from 8 reviews over one with 4.6 stars from 3,000? The first has a higher point estimate, but a huge uncertainty. Bootstrapping asks “if I’d gotten a different random sample of reviews, how different would the score be?” A deployment decision should look at the worst plausible case, not just the average.

A 95% interval of about \([-0.009,0.069]\) (shaded) includes 0, so the improvement could be harmful. Don’t ship on the mean alone.

2. Estimate uncertainty, not only value

Suppose off-policy evaluation produces:

\[\hat V^\pi=0.71\]

That number alone does not reveal whether the plausible range is [0.70, 0.72] or [0.45, 0.97].

For per-example evaluation contributions \(z_i\):

\[\hat V=\frac1N\sum_i z_i\]

A nonparametric bootstrap repeatedly resamples the \(N\) logged examples with replacement:

\[\mathcal D_b^* = \{z_{i_1},\ldots,z_{i_N}\}\]

and recalculates:

\[\hat V_b^* = \frac1N\sum_{j=1}^N z_{i_j}\]

The empirical 2.5% and 97.5% quantiles form a percentile 95% confidence interval.

For doubly robust evaluation, each contribution is:

\[z_i = \sum_a\pi(a\mid x_i)\hat Q(x_i,a) + \rho_i \left[ r_i-\hat Q(x_i,a_i) \right]\]

A conservative deployment rule can use the lower confidence bound:

\[\operatorname{LCB}_{95\%}(\pi) > V_{\text{required}}\]

This asks whether the policy still clears the requirement under an unfavorable estimate—not merely whether its point estimate does.

Resample the independent unit

If eight LLM responses were generated for one prompt, those responses share the same prompt and are correlated. Resampling them as eight independent examples creates an overly narrow interval.

Usually resample:

  • prompts, when each prompt has multiple generations;

  • complete episodes, for agents;

  • users or conversations, when observations share a user;

  • experimental seeds, when comparing training runs.

Bootstrap intervals measure sampling uncertainty. They do not repair reward-model bias, missing support, benchmark leakage or an incorrect logging policy.

Tensor shapes:

  • DR contributions: [B]

  • bootstrap indices: [bootstraps, B]

  • bootstrap estimates: [bootstraps]

  • confidence bounds: scalar

The same principle applies when evaluating PPO, GRPO or DPO policies: policy-training loss is not an uncertainty estimate of real task performance.

🔍 Deeper: bootstrap the right units

Algorithm: resample the \(n\) independent units (prompts or episodes) with replacement \(B\) times, recompute the estimate each time, and take the 2.5% and 97.5% percentiles.

Resample prompts, not tokens. Tokens within a response are correlated. If each prompt has \(m\) correlated samples with intra-cluster correlation \(\rho\), the variance is inflated by \(1+(m-1)\rho\) (the design effect). Resampling tokens ignores this and gives intervals that are falsely narrow.

Deployment gate: ship only if the lower confidence bound exceeds 0 (or a safety margin), and if the IS diagnostics (ESS, max weight) look healthy.

🔑 Key ideas

  • Report a distribution, not a single number.

  • Resample whole independent units and decide on the lower bound when harm is costly.

🚶 Walkthrough: bootstrap by hand

Per-prompt differences \(d=(0.2,-0.1,0.0,0.3)\), mean \(0.1\). Resample 1: \((0.2,0.2,-0.1,0.3)\), mean \(0.15\). Resample 2: \((-0.1,0.0,-0.1,0.3)\), mean \(0.025\). Repeat about 2000 times and take percentiles. With only 4 prompts the interval is wide, and that’s honest.

Common mistakes

  • Resampling tokens or turns instead of whole prompts or users.

  • Using \(B=50\) and reading the 2.5th percentile.

  • Shipping on the mean when tail risk matters.

⚙️ Algorithm: Bootstrap confidence interval and deployment gate
Input: per-unit scores \(d_1,\dots,d_n\) (one per independent prompt or episode), resamples \(B\), level \(\alpha\), margin \(m\)
for \(b=1,\dots,B\) do
draw \(n\) indices with replacement; \(\hat\theta_b\gets\) mean of the \(d\) values drawn
end
\(L\gets\) the \(\alpha/2\) quantile of \(\{\hat\theta_b\}\); \(U\gets\) the \(1-\alpha/2\) quantile
if \(L>m\) and the IS diagnostics (ESS, max weight) are healthy then
deploy
else
hold and collect more evidence
end

3. PyTorch exercise — build a conservative deployment gate

from torch.distributions import Categorical

torch.manual_seed(7)

true_reward_means = torch.tensor([

    reward_means

# Resample complete logged examples.

    0,
    batch_size,
    (num_bootstraps, batch_size),
)

# TODO 4: Recalculate the mean for every bootstrap dataset.

# TODO 5: Percentile confidence interval.

ci_low = confidence_bounds[0]

)

    target_probs[contexts]

).sum(dim=-1)

true_value = true_terms.mean()

print("True value:", true_value.item())
print("DR point estimate:", point_estimate.item())

    "Bootstrap standard error:",
    bootstrap_standard_error.item(),
)

    "95% bootstrap interval:",
    (ci_low.item(), ci_high.item()),
)

    "Deployment floor:",
    deployment_floor,
)
print(
    "Pass conservative gate:",
    bool(safe_to_deploy),
)

    "Importance-weight ESS:",

Debugging experiments

Resample individual tokens from an LLM response instead of complete responses. The resulting interval treats correlated tokens as independent and will be misleadingly narrow.

Then accidentally reuse one bootstrap index row:

bootstrap_estimates = (
    dr_contributions[
        bootstrap_indices[0]
    ].mean()
).repeat(num_bootstraps)

Every bootstrap estimate becomes identical, producing standard error zero—a clear implementation bug.

Finally, clip large ratios before constructing dr_contributions. The interval may shrink, but it now describes a biased clipped estimator. A narrow interval around the wrong quantity is not safety.

Solutions

Importance ratios:

chosen_behavior_probs = behavior_probs[
    contexts,
    actions,
]

chosen_target_probs = target_probs[
    contexts,
    actions,
]

ratios = (
    chosen_target_probs
    / chosen_behavior_probs
)

Direct terms:

direct_terms = (
    target_probs[contexts]
    * estimated_q[contexts]
).sum(dim=-1)

Doubly robust contributions:

chosen_estimated_q = estimated_q[
    contexts,
    actions,
]

dr_contributions = (
    direct_terms
    + ratios
    * (
        rewards
        - chosen_estimated_q
    )
)

Bootstrap estimates:

bootstrap_estimates = (
    dr_contributions[
        bootstrap_indices
    ].mean(dim=1)
)

Confidence interval:

confidence_bounds = torch.quantile(
    bootstrap_estimates,
    torch.tensor([
        0.025,
        0.975,
    ]),
)

The expected target value is:

\[V^\pi = \frac{ [0.1(0.2)+0.9(0.8)] + [0.9(0.7)+0.1(0.3)] }{2} = 0.70\]

The point estimate should be near 0.70, although noisy rewards and rare high-ratio actions can move it noticeably.

It is entirely possible to observe:

point estimate > 0.65
lower confidence bound < 0.65

In that case, the candidate looks promising but the available logged data is not strong enough for the conservative deployment rule.

Check answers

  1. Its uncertainty may be large enough that plausible values include unacceptable performance.

  2. They share the same prompt difficulty and context, so treating them as independent exaggerates the effective sample size.

  3. No. In frequentist terms, the interval-producing procedure has approximately 95% long-run coverage under its assumptions.

  4. Incorrect independence assumptions, benchmark leakage, reward-model bias, missing support, ratio clipping or bootstrapping the wrong unit.

Retrieval answers

  1. A reward-model prediction plus an importance-weighted correction using the observed reward residual.

  2. No. Missing behavior-policy support remains an identification failure; the reward model cannot be validated on unseen actions.

Takeaway: report distributions, not just point estimates. Bootstrap complete independent units, inspect importance-weight diagnostics, and use lower confidence bounds when an uncertain improvement could cause an unsafe deployment.
