2. Oversample strategically, then restore deployment weights

Suppose deployment contains groups with probabilities \(p_g\), conditional reward means \(\mu_g\), and variances \(\sigma_g^2\). The deployment value is:

\[J=\sum_g p_g\mu_g\]

If evaluation deliberately collects \(n_g\) episodes from each group, estimate:

\[\hat J=\sum_g p_g\bar R_g\]

Its variance is approximately:

\[\operatorname{Var}(\hat J) = \sum_g \frac{p_g^2\sigma_g^2}{n_g}\]

With a fixed budget \(N=\sum_g n_g\), the variance-minimizing Neyman allocation is:

\[n_g \propto p_g\sigma_g\]

So allocation depends on both:

  • deployment importance \(p_g\);

  • outcome variability \(\sigma_g\).

A common group with nearly deterministic outcomes may need fewer evaluations than proportional sampling suggests. A rare, noisy group may deserve oversampling.

Crucially, after oversampling, do not report the raw pooled reward. Reweight the group means using deployment probabilities \(p_g\).

Tensor shapes:

  • deployment probabilities, means, variances and allocations: [G]

  • simulated success counts: [R, G]

  • repeated value estimates: [R]

In practice, estimate \(\sigma_g\) from a frozen pilot and impose minimum counts. Neyman allocation optimizes precision for the aggregate value; subgroup safety gates may require larger group-specific floors.

DPO dataset sampling has the same distinction: oversampling difficult preference pairs changes the training distribution. It does not mean those pairs should receive their sampling frequency as their deployment evaluation weight.

# Allocate integer counts whose sum equals the budget.
def allocate_budget(weights):
    normalized = weights / weights.sum()
    raw_counts = evaluation_budget * normalized

    counts = torch.floor(
        raw_counts
    ).to(torch.long)

    remainder = (
        evaluation_budget
        - counts.sum().item()
    )

    if remainder > 0:
        fractional_parts = (
            raw_counts - counts
        )

        selected = torch.topk(
            fractional_parts,
            k=remainder,
        ).indices

        counts[selected] += 1

    return counts

Hints

  • A Bernoulli variable has variance \(\mu(1-\mu)\).

  • Proportional weights are target_probabilities.

  • Equal weights are torch.ones_like(target_probabilities).

  • Neyman weights are target_probability * group_standard_deviation.

  • Sample success counts with torch.distributions.Binomial.

  • The stratified estimate multiplies sampled group means by target probabilities.

  • RMSE is the square root of mean squared error around the exact target value.

Debugging experiments

  • Oversample rare groups, then report the unweighted pooled mean.

  • Calculate Neyman weights from reward means rather than standard deviations.

  • Estimate variances using evaluation outcomes and repeatedly redesign the same study.

  • Permit a group to receive zero samples because its pilot variance was zero.

  • Rescale rewards but continue using stale pilot variances.

  • Optimize aggregate precision while forgetting a required rare-group safety gate.

Solutions

Population quantities:

exact_target_value = (
    target_probabilities
    * true_group_values
).sum()

group_variances = (
    true_group_values
    * (1.0 - true_group_values)
)

group_standard_deviations = (
    group_variances.sqrt()
)

Evaluation designs:

proportional_allocation = allocate_budget(
    target_probabilities
)

equal_allocation = allocate_budget(
    torch.ones_like(
        target_probabilities
    )
)

neyman_weights = (
    target_probabilities
    * group_standard_deviations
)

neyman_allocation = allocate_budget(
    neyman_weights
)

Theoretical uncertainty:

def theoretical_standard_error(allocation):
    allocation = allocation.to(
        torch.float64
    )

    variance = (
        target_probabilities.square()
        * group_variances
        / allocation
    ).sum()

    return variance.sqrt()


proportional_theoretical_se = (
    theoretical_standard_error(
        proportional_allocation
    )
)

equal_theoretical_se = (
    theoretical_standard_error(
        equal_allocation
    )
)

neyman_theoretical_se = (
    theoretical_standard_error(
        neyman_allocation
    )
)

Simulation:

def simulate(allocation):
    float_allocation = allocation.to(
        torch.float64
    )

    total_counts = (
        float_allocation[None, :]
        .expand(num_repetitions, -1)
    )

    probabilities = (
        true_group_values[None, :]
        .expand(num_repetitions, -1)
    )

    successes = torch.distributions.Binomial(
        total_count=total_counts,
        probs=probabilities,
    ).sample()

    group_sample_means = (
        successes / total_counts
    )

    target_value_estimates = (
        group_sample_means
        * target_probabilities[None, :]
    ).sum(dim=1)

    raw_pooled_estimates = (
        successes.sum(dim=1)
        / float_allocation.sum()
    )

    return (
        target_value_estimates,
        raw_pooled_estimates,
    )


proportional_estimates, _ = simulate(
    proportional_allocation
)

equal_estimates, _ = simulate(
    equal_allocation
)

(
    neyman_estimates,
    neyman_raw_pooled_estimates,
) = simulate(
    neyman_allocation
)

The exact deployment value is:

\[J = 0.8(0.995)+0.15(0.5)+0.05(0.5) = 0.896\]

Proportional allocation gives:

\[[480,\;90,\;30]\]

But group 0 has standard deviation:

\[\sqrt{0.995(0.005)}\approx0.071\]

while the other groups have standard deviation 0.5. Neyman allocation is therefore approximately:

\[[216,\;288,\;96]\]

Typical theoretical standard errors are:

  • proportional: approximately 0.0095;

  • equal: approximately 0.0069;

  • Neyman: approximately 0.0064.

All three target-weighted estimators remain centered near 0.896. The raw pooled Neyman estimate instead approaches:

\[\frac{ 216(0.995)+288(0.5)+96(0.5) }{600} \approx0.678\]

That severe bias comes from confusing the deliberately constructed evaluation mixture with deployment traffic.

Check answers

  1. Proportional allocation ignores that conditional reward variance differs between groups.

  2. Oversampling changes data-collection frequency, not the deployment estimand.

  3. Reject it when subgroup guarantees, safety floors, collection costs or robustness to inaccurate pilot variances matter more than aggregate variance.

  4. No. Allocation must occur before or during collection. Once a required group has zero observations, analysis alone cannot restore support.

Retrieval answers

  1. Sampling uncertainty concerns imperfect estimates from observed data; identification uncertainty concerns outcomes the data never reveal.

  2. Collect data under the missing condition, narrow the target population, or introduce a clearly defended assumption restricting the missing outcome.

Takeaway: evaluation traffic should be designed for information, then reweighted for deployment. Oversample noisy or decision-critical groups—but never let the sampling mixture silently redefine the value you claim to estimate.
