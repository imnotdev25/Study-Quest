🧩 Analogy: homework with an answer key

Grading an essay needs a human opinion. Grading \(17\times23\) needs only the answer key: 391 or not. Verifiable rewards are answer keys: exact-match math, unit tests for code, a game’s win condition. They’re clean and cheap, but a student who notices the grader only checks the last line will learn to write just the last line.

2. Reward without a learned judge

Some tasks have outcomes that can be checked automatically:

  • mathematics: does the final answer match?

  • code: does it pass hidden tests?

  • tool use: did the requested state change occur?

  • structured output: does it satisfy the schema?

  • theorem proving: does the proof checker accept it?

A deterministic verifier produces:

\[R(x,y)= \begin{cases} 1,&\text{if }V(x,y)\text{ passes}\\ 0,&\text{otherwise} \end{cases}\]

Unlike a learned reward model, a reliable verifier does not merely predict whether a response looks correct. It executes a check.

The policy objective remains:

\[J(\theta) = \mathbb E_{y\sim\pi_\theta(\cdot\mid x)} [R(x,y)]\]

and a basic policy-gradient estimator is:

\[L_{\text{policy}} = -\frac1B\sum_b \left(R_b-\bar R\right) \log\pi_\theta(y_b\mid x_b)\]

The verifier’s output is detached. We do not backpropagate through sampled tokens or through a test runner.

Sparse rewards

A verifier often returns only pass or fail. It may provide no information about how close a failed solution was.

If all sampled responses fail:

\[R_b=0\quad\forall b\]

then the centered advantages are all zero and no policy update occurs. Exploration, sufficiently large sample groups, curricula or trustworthy process rewards can help.

What the verifier does not measure

A final-answer checker may give equal reward to:

5

and:

2 + 3 = 5

It may ignore explanation quality, safety and whether the reasoning was genuine. A flawed checker can also be exploited—for example, weak code tests may accept hard-coded outputs.

For \(K\) possible responses and batch size \(B\):

  • policy logits: [K]

  • sampled response IDs: [B]

  • rewards and advantages: [B]

  • policy loss: scalar

Verifiable-reward training is online RL when the current policy repeatedly generates new attempts. DPO remains offline preference optimization over fixed response pairs.

🔍 Deeper: binary rewards: where the signal lives

If a prompt is solved with probability \(p\), then \(R\sim\text{Bernoulli}(p)\): \(\mathbb E[R]=p\) and \(\operatorname{Var}[R]=p(1-p)\). Prompts that are always solved or never solved give zero learning signal.

Learning signal peaks at \(p=0.5\). Pass@k \(=1-(1-p)^k\) rises fast, which is why RL often improves pass@1 more than pass@k.

The checker defines the task: if it accepts a wrong answer with probability \(f\), RL optimizes \(p_{\text{true}}+f\cdot(\text{wrong-but-accepted})\), not \(p_{\text{true}}\).

🔑 Key ideas

  • Verifiers swap “looks good” for “passed a check.”

  • The best training prompts are the ones solved about half the time.

🚶 Walkthrough: pass@k and signal

\(p=0.2\). pass@1 \(=0.2\), pass@4 \(=1-0.8^4=0.590\), pass@16 \(=0.972\). Signal \(4p(1-p)=0.64\). A checker that also accepts 5% of wrong answers turns the measured \(p\) into \(0.2+0.8(0.05)=0.24\), and RL will chase that extra 4%.

Common mistakes

  • Lenient parsing (“any number in the output”).

  • Reusing the training checker as the only evaluation.

  • Keeping prompts the model always or never solves (zero gradient).

⚙️ Algorithm: RL with verifiable rewards (RLVR)
Input: prompts with reference answers or tests, checker \(C(y,\text{ref})\in\{0,1\}\), policy \(\pi_\theta\)
for each iteration do
sample prompts \(x\) and responses \(y\sim\pi_\theta(\cdot|x)\)
\(R\gets C(y,\text{ref})\) ▷ exact match, unit tests, game win
\(A\gets R-b(x)\) ▷ e.g. \(b(x)\) = running solve rate of that prompt
masked policy-gradient update (Topic 25) or PPO/GRPO update
track solve rate per prompt; drop prompts with solve rate \(\approx0\) or \(\approx1\)
end

Hints

  • Equality with the target produces a Boolean tensor; convert it to float.

  • Subtract the batch reward mean.

  • Normalize using population standard deviation plus 1e-8.

  • Use policy.log_prob.

  • Gradient descent requires a leading negative sign.

Debugging experiment

Introduce a broken verifier:

rewards = (
    sampled_answers >= target_answer
).float()

Now the incorrect answer 7 also passes. Training will correctly optimize the implemented reward while producing incorrect task behaviour.

This distinction is crucial:

RL bug: optimization fails to increase reward
Specification bug: reward increases, but desired behaviour does not

Solutions

Fresh samples and verifier:

sampled_responses = policy.sample(
    (batch_size,)
)

rewards = (
    sampled_answers == target_answer
).float()

Advantages:

advantages = rewards - rewards.mean()

advantages = advantages / (
    rewards.std(unbiased=False) + 1e-8
)

Policy loss:

selected_log_probs = policy.log_prob(
    sampled_responses
)

policy_loss = -(
    selected_log_probs
    * advantages.detach()
).mean()

Initially the policy is uniform:

\[\pi=[0.25,0.25,0.25,0.25]\]

Two of four responses pass, so:

\[P(\text{correct})=0.25+0.25=0.5\]

Training should move probability away from actions 0 and 3 and toward actions 1 and 2.

However, the verifier assigns both correct responses reward one:

\[R(1)=R(2)=1\]

It provides no expected gradient preference between them. Sampling noise may cause one to dominate, but that does not mean it is better according to the intended qualities absent from the verifier.

If every sample receives the same reward:

\[R_b-\bar R=0\]

so all advantages and policy gradients become zero. This commonly happens after policy collapse or when successes are extremely rare.

Check answers

  1. They directly test an observable property instead of predicting quality from learned correlations.

  2. Most attempts may receive identical failure rewards, providing no direction for improvement.

  3. No. A final-answer checker can accept guessing, invalid reasoning or a hard-coded exploit.

  4. Use hidden and adversarial tests, test-coverage measurement, held-out problem families, manual audits and separate process-quality evaluation.

Retrieval answers

  1. The ratio corrects for using tokens generated by an older policy and clipping limits excessively beneficial-looking changes during data reuse.

  2. The policy can exploit scorer errors or sacrifice qualities the reward model does not measure.

Takeaway: verifiable rewards replace “this response looks good” with “this outcome passed a check.” That can provide cleaner supervision, but RL will exploit the exact checker supplied—so verifier coverage is part of the learning algorithm, not merely evaluation infrastructure.
