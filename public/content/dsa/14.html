👋 Intro

Algorithms for data too big or too fast to store: shuffling and sampling (Fisher–Yates, reservoir, weighted, alias), probabilistic data structures (Bloom filters, count-min sketch, HyperLogLog), similarity at scale (MinHash, LSH, SimHash), random projections, and the MapReduce patterns used to process training data.

Shuffling

Fisher–Yates shuffle

for \(i \gets n-1\) down to 1 do
\(j \gets\) uniform random integer in \([0, i]\) ▷ inclusive of \(i\)
swap \(A[i], A[j]\)
end
❓ Why

Position \(n-1\) receives each element with probability \(1/n\); given that, position \(n-2\) receives each remaining element with probability \(1/(n-1)\), and so on, so all \(n!\) permutations have probability \(1/n!\). The classic bug, choosing \(j\) from \([0, n-1]\) every time, produces \(n^n\) equally likely sequences, which cannot divide evenly into \(n!\) permutations, so some orders are more likely.

Reservoir Sampling

🌱 Beginner

You are handed cards one at a time and do not know how many are coming. You may hold only \(k\). Reservoir sampling tells you when to swap a new card in so that, whenever the stream stops, every card seen had an equal chance to be in your hand.

Reservoir sampling (\(k\) items from a stream)

\(R \gets\) the first \(k\) items
for \(i \gets k+1, k+2, \dots\) (the \(i\)-th item \(x\)) do
\(j \gets\) uniform random integer in \([1, i]\)
if \(j \le k\) then
\(R[j] \gets x\)
end
end
return \(R\)
❓ Why

Claim: after \(n\) items, each is in \(R\) with probability \(k/n\). Induction: item \(i\) enters with probability \(k/i\). At each later step \(t\), it is evicted only if \(j \le k\) (probability \(k/t\)) and \(j\) hits its slot (probability \(1/k\)), so it survives with probability \(1 - 1/t = (t-1)/t\). Product: \(\frac{k}{i}\cdot\frac{i}{i+1}\cdots\frac{n-1}{n} = \frac{k}{n}\). Time: \(O(n)\) Space: \(O(k)\). Distributed version: assign each item a random key and keep the \(k\) smallest keys per shard; merge shards by keeping the global \(k\) smallest.

Weighted Sampling

🔧 Intermediate

  • CDF + binary search: prefix sums of weights, draw \(u \sim U(0, W)\), find the first prefix \(> u\). \(O(n)\) setup, \(O(\log n)\) per sample. (“Random pick with weight.”)

  • Alias method: \(O(n)\) setup into \(n\) buckets, each holding at most two outcomes with a split probability; sample in \(O(1)\): pick a bucket uniformly, then flip a biased coin. Used for word2vec’s negative sampling table and for sampling from large static categorical distributions.

  • Weighted reservoir (A-Res): give each item key \(u^{1/w}\) with \(u \sim U(0,1)\) and keep the \(k\) largest keys (a min-heap). One pass, weighted sampling without replacement from a stream.

  • Gumbel-max trick: \(\arg\max_i (\log p_i + g_i)\) with \(g_i\) Gumbel noise is an exact sample from \(p\); taking the top \(k\) gives sampling without replacement. This is how sampling from softmax logits can be done without normalizing, and why “Gumbel-softmax” allows differentiable sampling.

Bloom Filters

A Bloom filter: no false negatives, tunable false positives.

🔧 Intermediate

A bit array of \(m\) bits and \(k\) hash functions. Insert sets \(k\) bits; a query returns “maybe present” if all \(k\) bits are set, “definitely absent” otherwise. With \(n\) items, the false-positive rate is about \((1 - e^{-kn/m})^k\), minimized at \(k = \frac{m}{n}\ln 2\), giving about \(0.6185^{m/n}\): roughly 10 bits per item for 1%, 14.4 bits for 0.1%. Deletion is impossible (use a counting Bloom filter or a cuckoo filter). Uses: avoid disk reads for absent keys in LSM databases, “has this URL been crawled,” cache-miss filters, and checking membership of a token sequence in a huge set before an expensive lookup.

Count-Min Sketch

🔧 Intermediate

A \(d \times w\) counter table with one hash function per row. Increment adds to one counter per row; a query returns the minimum across rows. Collisions only add, so estimates never underestimate; with \(w = \lceil e/\epsilon\rceil\) and \(d = \lceil\ln(1/\delta)\rceil\), the overestimate is at most \(\epsilon N\) with probability \(1-\delta\) (\(N\) = total count). Combined with a small heap it finds heavy hitters (most frequent items) in a stream with fixed memory: trending queries, hot keys, top tokens. The Misra–Gries algorithm finds items with frequency \(> n/k\) deterministically using \(k-1\) counters (generalizing Boyer–Moore majority vote).

HyperLogLog: Counting Distinct Items

🔧 Intermediate

Hash every item. In a uniform random hash, a prefix of \(r\) leading zeros appears about once per \(2^r\) distinct values, so the maximum observed run of leading zeros estimates \(\log_2\) of the number of distinct items. HyperLogLog splits hashes into \(m\) buckets by their first bits, tracks the max leading zeros per bucket, and combines with a harmonic mean, giving a standard error of about \(1.04/\sqrt m\): roughly 2% error with 12 KB of memory, for billions of distinct items. Sketches merge by taking per-bucket maxima, so per-day or per-shard sketches combine into totals. Used for unique users, distinct n-grams in a corpus, and cardinality estimates in query planners.

Streaming Quantiles

🔧 Intermediate

Exact percentiles need all the data. Sketches keep an approximation: t-digest clusters values with finer resolution near the tails (accurate p99s), KLL gives guaranteed rank error, and DDSketch gives guaranteed relative value error with log-spaced buckets. All are mergeable, so p99 latency across thousands of servers can be computed from per-server sketches. Averaging per-server p99s is wrong.

Similarity at Scale: MinHash and LSH

🌱 Beginner

Finding near-duplicate documents among billions by comparing every pair is impossible. Instead, give each document a short “fingerprint” designed so that similar documents usually get matching fingerprints, then only compare documents whose fingerprints collide.

MinHash signatures and LSH banding

for each document \(d\) do
\(S_d \gets\) set of shingles (e.g. word 5-grams) of \(d\)
for \(i \gets 1\) to \(K\) do ▷ \(K\) independent hash functions
\(sig_d[i] \gets \min_{s \in S_d} h_i(s)\)
end
end
split each signature into \(b\) bands of \(r\) rows (\(K = br\))
for each band do
bucket documents by the hash of their \(r\) values in that band
end
candidate pairs \(\gets\) documents sharing at least one bucket; verify with estimated Jaccard
❓ Why

For one random hash, \(\Pr[\min h(A) = \min h(B)] = \frac{|A\cap B|}{|A\cup B|}\), the Jaccard similarity \(J\): the minimum over \(A\cup B\) is equally likely to be any element, and it is shared exactly when that element is in the intersection. So the fraction of matching signature positions estimates \(J\). With banding, two documents become candidates with probability \(1 - (1 - J^r)^b\), an S-curve that is near 0 below a threshold of about \((1/b)^{1/r}\) and near 1 above it. Choosing \(b\) and \(r\) tunes the threshold (e.g. \(b = 20\), \(r = 5\) targets \(J \approx 0.55\)).

🔧 Intermediate

SimHash (Charikar) produces a 64-bit fingerprint where similar documents have small Hamming distance (each bit is the sign of a weighted sum of feature hashes); used historically by Google for near-duplicate web pages. Random hyperplane LSH hashes vectors by the signs of random projections; the probability two vectors agree on a bit is \(1 - \theta/\pi\), so it approximates cosine similarity. Modern vector search mostly uses graph indexes (HNSW) instead, but LSH remains common for deduplication.

🤖 ML connection

Near-duplicate removal with MinHash + LSH is a standard step in building LLM pre-training corpora (documents with Jaccard similarity above roughly 0.7–0.8 on n-gram shingles are clustered and all but one dropped). Deduplication improves training efficiency, reduces memorization, and helps prevent benchmark contamination. Chapter 16 covers the full data pipeline.

Random Projections

🔧 Intermediate

The Johnson–Lindenstrauss lemma: any \(n\) points in high dimension can be projected to \(k = O(\log n / \epsilon^2)\) dimensions with a random Gaussian (or \(\pm 1\)) matrix while preserving all pairwise distances within a factor of \(1 \pm \epsilon\). The target dimension does not depend on the original dimension. This justifies random-projection dimensionality reduction, sketching for least squares, and some embedding compression. Count sketch and the hashing trick are sparse random projections.

MapReduce Patterns

MapReduce: map emits (key, value), the shuffle groups by key, reduce aggregates.

🔧 Intermediate

  • Word / n-gram count: map emits (word, 1); a combiner pre-sums on each mapper to cut shuffle volume; reduce sums.

  • Distributed sort: sample keys to choose range boundaries, partition by range, sort each partition locally (TeraSort).

  • Joins: reduce-side (shuffle both tables by join key) or broadcast (copy a small table to every mapper). Skewed keys (one user with millions of rows) overload one reducer: salt the hot key into sub-keys and combine afterward.

  • Inverted index: map emits (term, doc id); reduce builds posting lists.

  • Global top-\(k\): local top-\(k\) per mapper, then one reducer merges.

Spark, Beam, and Ray Data implement these with in-memory execution; the same patterns apply.

🎤 Interview: Random sample of 1 million rows from a 10-billion-row table

One machine with a stream: reservoir sampling, one pass, \(O(k)\) memory. Distributed: each worker assigns each row a random 64-bit key and keeps its local 1M smallest keys in a heap; a coordinator merges to the global 1M smallest, which is a uniform sample without replacement. If an approximate size is fine, Bernoulli sampling (keep each row with probability \(10^{-4}\)) is trivially parallel. For a stratified sample (balanced labels), run the same per stratum. For reproducibility, derive keys from a hash of the row ID plus a seed instead of a random generator.

🔑 Takeaways

  • Fisher–Yates and reservoir sampling are short algorithms with exact uniformity proofs.

  • Bloom filters, count-min, and HyperLogLog trade small errors for tiny, mergeable memory.

  • MinHash estimates Jaccard similarity; LSH banding finds near duplicates without all pairs.

  • MapReduce thinking (map, combine, shuffle, reduce, handle skew) is how data pipelines scale.
