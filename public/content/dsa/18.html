👋 Intro

How low-level (object-oriented) design rounds and multi-part “practical coding” rounds work, the principles and patterns that score well, a concurrency primer, and complete designs for classic problems (LRU cache, rate limiter, key-value store with transactions and TTL, task scheduler, pub/sub) and ML-flavored problems (dynamic batching inference server, feature store, tool executor for agents, experiment tracker).

What the Round Looks Like

🌱 Beginner

A system design round asks “which boxes and arrows?” A low-level design round asks “which classes, methods, and data structures inside one box?” It is closer to real day-to-day engineering: clean interfaces that are easy to extend when the interviewer adds a new requirement every ten minutes.

🔧 Intermediate

Typical flow (45–60 minutes):

  1. Clarify requirements and the API (5 min). Write the public interface first.

  2. Identify entities, responsibilities, and relationships (5–10 min).

  3. Choose data structures and complexities for each operation.

  4. Implement the core path (20 min), with tests.

  5. Extensions arrive: “now add TTL,” “now make it thread-safe,” “now persist it,” “now support transactions.” Good structure makes each one small.

Scoring: correctness, API clarity, separation of concerns, extensibility, testing, handling of edge cases and concurrency, and explaining trade-offs.

Principles That Interviewers Look For

🔧 Intermediate

  • Single responsibility: a class has one reason to change (eviction policy separate from storage).

  • Open/closed: add behavior by adding a class, not editing a switch statement (a new sampling strategy implements Sampler).

  • Liskov substitution: subclasses must work wherever the base does.

  • Interface segregation: small interfaces (Readable, Writable) rather than one huge one.

  • Dependency inversion: depend on abstractions and inject them (pass a Clock so TTL logic is testable without sleeping).

  • Composition over inheritance; immutability for shared values; explicit error handling; no global state.

Design patterns worth knowing, with ML uses

Concurrency Primer

🔧 Intermediate

  • Race condition: the result depends on thread interleaving (two threads read a counter, both write \(+1\), one update is lost). Protect shared mutable state with a lock, or use atomic operations.

  • Deadlock needs four conditions: mutual exclusion, hold and wait, no preemption, circular wait. Prevent it by always acquiring locks in a global order, or with timeouts.

  • Condition variables: wait for a condition while releasing the lock; always re-check the condition in a while loop (spurious wake-ups).

  • Read-write locks, semaphores (limit concurrency to \(N\)), thread pools, and futures.

  • Async I/O (event loops) for many concurrent network calls; threads or processes for CPU work (Python’s GIL limits CPU parallelism in threads).

Bounded blocking queue (producer–consumer)

function Put(\(item\))
acquire \(lock\)
while \(|buffer| = capacity\) do
wait on \(notFull\) ▷ releases \(lock\) while waiting
end
append \(item\); signal \(notEmpty\); release \(lock\)
end
function Take()
acquire \(lock\)
while \(|buffer| = 0\) do
wait on \(notEmpty\)
end
\(item \gets\) pop front; signal \(notFull\); release \(lock\)
return \(item\)
end

🧠 Expert

Design choices to talk through. Expiry: lazy (check on read; cheap but expired keys use memory) plus periodic sampling cleanup (Redis’s approach), or a min-heap of expiry times. Counting values (“how many keys have value \(v\)”) needs a second map updated on every set and delete, including inside transactions. Thread safety: one lock is correct and simple; striped locks by key hash scale better; transactions per client need per-connection stacks. Persistence: an append-only log of operations replayed on startup, with periodic snapshots to bound replay time (the same design as databases’ write-ahead logs). Each extension maps to one new component, which is the point of starting with clean boundaries.

Classic Problem: Rate Limiter

🔧 Intermediate

Interface: allow(clientId, cost=1) -> bool. Strategy pattern over algorithms: TokenBucket (capacity, refill rate, tokens, lastRefill: refill lazily on each call as \(\min(cap, tokens + rate\cdot\Delta t)\)), SlidingWindowLog (a deque of timestamps per client; pop old ones), SlidingWindowCounter. A map from client to limiter state, with idle-state cleanup. Inject the clock. For thread safety lock per client. For a distributed version the state moves to a shared store with an atomic script (see the System Design book’s rate limiting chapter). For LLM APIs the cost is the token count, reserved up front and refunded after the response.

Classic Problem: Task Scheduler with Dependencies

🔧 Intermediate

Requirements: submit tasks with dependencies, run with up to \(N\) workers, retry failures with backoff, report status. Design: Task (id, function, deps, retries, state machine PENDING \(\to\) READY \(\to\) RUNNING \(\to\) DONE / FAILED); Scheduler keeps in-degree counts and a ready queue (Kahn’s algorithm, Chapter 8), a thread pool of \(N\) workers, and on completion decrements dependents and enqueues those that become ready. Cycle detection at submission. Failures: retry with exponential backoff and jitter up to a limit, then mark dependents as cancelled. Extensions: priorities (ready queue becomes a heap), timeouts per task, persistence of state for restarts (durable execution), idempotency keys for tasks with side effects.

Classic Problem: In-Memory Pub/Sub

🔧 Intermediate

publish(topic, msg), subscribe(topic, handler) -> Subscription, unsubscribe. Observer pattern with a map from topic to subscribers. Decisions: synchronous delivery (simple, a slow handler blocks the publisher) vs a queue and worker per subscriber (isolation, needs backpressure: bounded queue and drop or block policy); ordering per topic; at-least-once delivery requires acknowledgements and redelivery; wildcard topics need a trie of topic segments.

ML Problem: Dynamic Batching Inference Server

Dynamic batching trades a few milliseconds of latency for much higher throughput.

Batcher loop

loop
\(batch \gets\) [ first request from the queue (blocking) ]; \(deadline \gets now + T\)
while \(|batch| < B\) and \(now < deadline\) do
\(r \gets\) take from the queue with timeout \(deadline - now\)
if \(r\) exists then
append \(r\)
end
end
drop requests whose own deadline has passed ▷ do not waste compute
pad inputs to a common shape; run the model once; split outputs
complete each request’s future with its output (or its error)
end
🧠 Expert

Points that distinguish senior answers: the bounded queue gives backpressure (reject with 429/503 when full rather than letting latency grow without bound); choose \(B\) and \(T\) from a latency budget (p99 latency \(\approx\) queue wait \(+ T +\) batch compute); group requests by shape or sequence length to reduce padding waste; one error in a batch should fail only that request (validate inputs before batching); expose metrics (queue depth, batch size histogram, latency). For LLMs, request-level batching is replaced by continuous batching at every decode step because outputs have very different lengths.

ML Problem: Feature Store (Point-in-Time)

🔧 Intermediate

API: write(entity, feature, value, timestamp), get_online(entity, features) (latest values, low latency), get_training(events) (point-in-time values for each (entity, timestamp), Chapter 16). Storage: per (entity, feature) a time-sorted list of (timestamp, value). Online read = last element (\(O(1)\)); historical read = binary search for the last timestamp \(\le t\) (\(O(\log n)\)), or a merge for a sorted batch of events. Extensions: TTL for stale features, feature definitions shared by batch and online paths (avoid training–serving skew), backfills, and versioning of feature definitions.

ML Problem: Tool Executor for an Agent

🔧 Intermediate

Components: Tool interface (name, JSON schema for arguments, run(args, context), a risky flag, required permissions); ToolRegistry (register, look up, list schemas for the model); Executor that (1) validates arguments against the schema and business rules in code, (2) checks the caller’s permissions, (3) requests human approval for risky tools, (4) runs with a timeout and an idempotency key derived from (run id, step, tool), (5) retries transient failures with backoff, (6) truncates large outputs before returning them to the model, and (7) records every call for tracing. A Budget object caps steps, tokens, wall time, and cost; the agent loop stops cleanly when any limit is reached. Treat tool output as untrusted data, never as instructions.

ML Problem: Experiment Tracker

🔧 Intermediate

Entities: Experiment \(\to\) many Runs; a run has parameters (immutable after start), metrics (time series of (step, value), append-only), artifacts (paths plus content hashes), tags, and status. API: start_run, log_param, log_metric(key, value, step), log_artifact, end_run, query(filter, order_by). Concerns: buffered asynchronous logging so training is not slowed (flush on a timer and at exit), idempotent metric writes (key + step), resuming a crashed run, and comparing runs (best metric per run).

⚠️ Pitfall

  • Writing code before agreeing on the interface and requirements.

  • God classes that do storage, policy, and I/O at once, so every extension touches everything.

  • Calling the real clock or network inside logic, making behavior untestable.

  • Ignoring concurrency until asked, then bolting a lock onto every method.

  • Leaving no tests; in practical rounds, tests are often explicitly scored.

🔑 Takeaways

  • Start from the API, then entities, then data structures and complexity per operation.

  • Strategy, observer, decorator, and state machines cover most extensions.

  • Know locks, condition variables, and the bounded queue cold.

  • ML-flavored LLD (batching server, feature store, tool executor) reuses the same algorithms in this book.
