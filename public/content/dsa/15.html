👋 Intro

Data is the part of ML that interviews probe most and candidates prepare least. This chapter covers data structures for ML data (tensors, sparse matrices, columnar files, sharded datasets), labeling and agreement, splitting strategies, every common form of leakage, sampling and imbalance, point-in-time feature correctness, data quality and drift, and the pipeline used to build LLM training and evaluation data.

Data Structures for ML Data

Sparse matrix–vector product with CSR

Input: \(rowPtr[0..R]\), \(colIdx\), \(val\) of a CSR matrix; dense vector \(x\)
for \(r \gets 0\) to \(R-1\) do
\(y[r] \gets 0\)
for \(p \gets rowPtr[r]\) to \(rowPtr[r+1]-1\) do ▷ only the non-zeros of row \(r\)
\(y[r] \gets y[r] + val[p]\cdot x[colIdx[p]]\)
end
end
return \(y\)
🔧 Intermediate

Cost \(O(\text{nnz})\) instead of \(O(RC)\). A bag-of-words matrix with 1M documents and a 100K vocabulary has \(10^{11}\) cells but perhaps \(10^8\) non-zeros. Streaming data loaders for large-scale training must: shard data so each of \(N\) workers reads different files; shuffle with a buffer (read several shards, shuffle within a buffer of a few thousand examples) because a global shuffle of terabytes is impractical; resume deterministically from a checkpoint (record shard and offset); and keep GPUs fed (prefetching, parallel decoding).

Collecting and Labeling Data

🔧 Intermediate

Sources of labels: natural labels from user behavior (clicks, purchases, watch time, with delays and biases), human annotation, weak supervision (heuristic labeling functions combined by a label model, as in Snorkel), model distillation (labels from a stronger model, including LLMs as annotators), and synthetic data.

Measuring annotation quality with Cohen’s kappa, which corrects raw agreement for chance: \[\kappa = \frac{p_o - p_e}{1 - p_e}\] where \(p_o\) is observed agreement and \(p_e\) the agreement expected if both annotators labeled randomly with their own label frequencies. Example: two annotators agree on 85% of items; one labels 70% positive, the other 60%, so \(p_e = 0.7\cdot0.6 + 0.3\cdot0.4 = 0.54\) and \(\kappa = (0.85-0.54)/0.46 \approx 0.67\) (substantial). For more than two annotators use Fleiss’ kappa or Krippendorff’s alpha. Low agreement means the labeling guidelines, not the annotators, usually need work.

🔧 Intermediate

Active learning spends the labeling budget on the most useful examples: uncertainty sampling (lowest max-probability, smallest margin between top two classes, or highest entropy), query-by-committee (where an ensemble disagrees), and diversity sampling (cover the embedding space, e.g. \(k\)-center greedy) to avoid labeling many near-identical uncertain items.

Splitting Data

🌱 Beginner

A test set is a final exam. If students see the exam questions while studying, their score says nothing about what they learned. Every splitting rule exists to keep information about the exam out of studying.

Split How Use when
Random shuffle and cut (e.g. 80/10/10) i.i.d. data with no groups or time
Stratified preserve label proportions in each split imbalanced classes, small datasets
Group all rows of a group (user, patient, document, session) in one split multiple rows per entity; otherwise the model memorizes entities
Temporal train on the past, validate and test on later periods anything deployed into the future: recommendations, fraud, forecasting
\(k\)-fold CV rotate \(k\) validation folds small data; report mean and variance
Nested CV inner loop tunes, outer loop evaluates honest estimates when tuning on small data

Splitting strategies

Deterministic group split by hashing

for each row do
\(u \gets \text{hash}(\text{groupId} \Vert \text{salt}) \bmod 1000\) ▷ same group \(\to\) same bucket
if \(u < 800\) then
assign to train
else if \(u < 900\) then
assign to validation
else  
assign to test
end
end
❓ Why

Hashing the group key makes the split deterministic (re-running a pipeline or adding new data never moves an old group between splits) and group-consistent without a lookup table. New users land in splits by the same rule, so the test set stays stable over time. The salt allows a fresh, independent split when needed.

🔧 Intermediate

Temporal splits need care: leave a gap between train and test when labels take time to arrive (a fraud label 30 days later) or features use windows, so the last training examples do not peek at the test period. Walk-forward validation retrains on an expanding window and evaluates on the next period, repeatedly, to estimate how performance varies over time.

Leakage: The Most Common Way to Fool Yourself

🔧 Intermediate

Leakage is any information available during training or evaluation that will not be available at prediction time. Signs: validation results that are too good, a single feature that dominates importance, and a big drop in production.

  1. Target leakage: a feature derived from the label or from events after the prediction time (“refund issued” when predicting fraud; “discharge code” when predicting hospital readmission at admission).

  2. Temporal leakage: random splits on time-dependent data, so the model trains on the future and tests on the past.

  3. Group / duplicate leakage: the same user, patient, or near-duplicate document in train and test; the model recognizes the entity.

  4. Preprocessing leakage: fitting a scaler, imputer, vocabulary, PCA, or feature selection on the whole dataset before splitting. Fit on the training fold only, then apply to validation and test.

  5. Target encoding leakage: replacing a category with its mean label computed on rows that include the row itself. Use out-of-fold encoding.

  6. Test set reuse: tuning many models against the same test set makes it a validation set. Keep a final holdout untouched.

  7. Benchmark contamination for LLMs: evaluation questions present in pre-training data (below).

Out-of-fold target encoding

Input: training rows with category \(c\) and label \(y\); folds \(F_1..F_K\); prior strength \(m\)
\(\mu \gets\) global mean of \(y\)
for each fold \(F_k\) do
compute, on rows not in \(F_k\): \(n_c\) and \(s_c\) = count and label sum per category
for each row in \(F_k\) with category \(c\) do
\(enc \gets (s_c + m\,\mu)/(n_c + m)\) ▷ smoothed toward the prior for rare categories
end
end
for validation/test rows, use statistics from all training rows

Point-in-Time Correctness

A training row must use the latest feature values available at its timestamp.

Point-in-time (“as of”) join

Input: events \(E\) (entity, \(t_e\), label); feature log \(F\) (entity, \(t_f\), value)
sort \(E\) and \(F\) by (entity, time)
for each entity, with pointer \(p\) into its feature rows do
for each event \(e\) in time order do
while next feature row has \(t_f \le t_e - \text{delay}\) do
advance \(p\)
end
attach \(F[p].value\) to \(e\) (or null if none) ▷ latest value known at \(t_e\)
end
end
🔧 Intermediate

This two-pointer merge (Chapter 3) is what feature stores implement for training data. The delay models how long a feature takes to be computed and available in production; ignoring it leaks seconds or hours of future information. Training–serving skew happens when training features are computed by a batch pipeline and serving features by different online code; the fixes are one feature definition used in both places, logging served features and training on the logs, and monitoring feature distributions in both.

Sampling, Imbalance, and Negatives

🔧 Intermediate

Class imbalance (fraud 0.1%, clicks 2%):

  • Use the right metrics: PR-AUC, recall at a fixed precision, not accuracy.

  • Class weights in the loss (weight \(\propto 1/\text{frequency}\)), or focal loss \(-(1-p_t)^\gamma\log p_t\), which down-weights easy examples.

  • Downsample negatives for training speed, then correct calibration: if negatives were kept with rate \(r\), the trained odds are inflated by \(1/r\), so the true probability is \(p = \frac{q}{q + (1-q)/r}\) where \(q\) is the model output. Ads CTR models must do this or bids are wrong.

  • Oversampling / SMOTE (synthetic minority points by interpolation) helps some tabular models but can cause overfitting; prefer weighting with tree ensembles.

Negative sampling for retrieval and recommendation (where every non-interaction is a negative): random negatives are easy; hard negatives (items close in embedding space or shown but not clicked) teach fine distinctions but can include false negatives; in-batch negatives reuse other examples’ positives in the same batch, and need a log-Q correction (subtract \(\log\) of each item’s sampling probability from its logit) because popular items appear as negatives more often. Word2vec sampled negatives from the unigram distribution raised to the \(3/4\) power, which up-weights rare words.

Importance weighting: if training data comes from distribution \(q\) but you care about \(p\), weight each example by \(p(x)/q(x)\); this underlies off-policy evaluation of recommendation policies (inverse propensity scoring) and correcting position bias in click logs.

Data Quality

🔧 Intermediate

  • Validation: schema checks (types, ranges, allowed categories, null rates) on every pipeline run; block training when they fail.

  • Missing values: “missing” is often informative; add an indicator feature and impute with training statistics (median for skewed numerics, a dedicated “unknown” category for categoricals). Tree models (XGBoost, LightGBM) learn a default direction for missing values.

  • Outliers: robust scaling (median and IQR), clipping to percentiles, or log transforms for heavy tails; check whether outliers are errors or the most important cases (fraud).

  • Label noise: confident learning estimates the joint distribution of noisy and true labels from out-of-fold predicted probabilities and flags examples whose given label disagrees with a confident prediction; review or drop them. Cross-validated loss ranking finds the same issues.

  • Deduplication: exact (hash of normalized content) then near-duplicate (MinHash/LSH, Chapter 15; or embedding similarity for images and semantic duplicates).

Drift and Monitoring

🔧 Intermediate

Covariate shift (\(p(x)\) changes), label shift (\(p(y)\) changes), concept drift (\(p(y|x)\) changes). Detection compares a reference window to a recent window per feature:

  • PSI (population stability index): \(\sum_b (a_b - e_b)\ln(a_b/e_b)\) over bins of expected (\(e\)) and actual (\(a\)) proportions. Rule of thumb: \(< 0.1\) stable, \(0.1\)–\(0.25\) moderate, \(> 0.25\) significant.

  • KS test for continuous features, chi-square for categoricals; with huge samples everything is “significant,” so use effect sizes like PSI.

  • Domain classifier: train a model to distinguish reference from recent data; AUC near 0.5 means no detectable shift, and its feature importances show what changed.

  • Monitor prediction distributions and, when labels arrive, the actual metric.

Feature Engineering Essentials

🔧 Intermediate

  • Numeric: standardize (fit on train), log-transform heavy tails, bucketize (quantile bins) for linear models.

  • Categorical: one-hot for low cardinality; embeddings, the hashing trick, or target encoding (out-of-fold) for high cardinality.

  • Crosses: products of categorical features (country \(\times\) device) let linear models learn interactions; deep models (DCN, wide-and-deep) learn them automatically.

  • Aggregates: counts and rates over time windows (clicks in the last 1h/24h/7d per user and per item), computed point-in-time; ratios such as user CTR smoothed with a prior.

  • Text and images: pre-trained embeddings are usually the strongest starting features.

Data for LLMs

A typical pre-training data pipeline.

🔧 Intermediate

  • Quality filtering: heuristics (length, symbol ratios, repeated lines, stop-word presence) and model-based scoring (a classifier trained to recognize high-quality reference text, or an LLM-rated “educational value” score used to select subsets).

  • Deduplication: URL and exact-hash dedup, then MinHash/LSH fuzzy dedup, sometimes exact-substring dedup with suffix arrays (Chapter 14).

  • Decontamination: remove training documents that share long n-grams (e.g. 13-grams) with evaluation benchmarks, or report contamination analysis.

  • Data mixture: proportions of web, code, math, books, multilingual, and synthetic data are tuned with small proxy-model experiments; mixtures often change over training (higher-quality data later).

  • Post-training data: instruction–response pairs (SFT), preference pairs (chosen vs rejected) for DPO/RLHF, and verifiable tasks (math with answers, code with tests) for reinforcement learning. Quality and diversity beat volume.

  • Synthetic data: generated by stronger models, filtered by verifiers or judges. Risks: amplifying the generator’s errors and biases, low diversity, and degradation when models train recursively on their own outputs (“model collapse”); mitigate by mixing real data and filtering aggressively.

🧠 Expert

Evaluation datasets for LLM applications: build a golden set from real user queries (sampled, de-identified, stratified by intent and difficulty), add adversarial and edge cases, label expected behaviors or rubrics, and keep it versioned. Split into a development set you iterate on and a held-out set you check rarely, so prompt tuning does not overfit. Track per-slice metrics (language, task type, length), since averages hide regressions. Public benchmarks saturate and leak; private, task-specific evals are what product decisions should rest on.

🎤 Interview: “Our offline AUC is 0.97 but production performance is poor. Why?”

Structure the answer as a checklist. (1) Leakage: features computed after the prediction time, target-encoded without out-of-fold, or a random split on temporal data; check feature importances for a suspicious top feature. (2) Split mismatch: users or duplicates shared across train and test; re-split by group and time. (3) Training–serving skew: compare logged online feature values to training values for the same entities; look for different defaults, units, or missing-value handling. (4) Distribution shift: PSI on features and predictions between the training period and now. (5) Metric mismatch: AUC rewards ranking, but production uses a threshold, or the business metric depends on calibration; check calibration and precision at the operating point. (6) Feedback loops: the deployed model changes which data gets labeled. Propose the fix for each and the experiment that distinguishes them.

🔑 Takeaways

  • Use CSR for sparse data and sharded, buffer-shuffled streams for large training sets.

  • Split by group and time when the deployment does; hash group keys for stable splits.

  • Leakage comes from the future, the label, shared entities, or preprocessing fit on everything.

  • Point-in-time joins, out-of-fold encodings, and calibration correction after downsampling are must-know algorithms.

  • LLM data quality comes from filtering, deduplication, decontamination, and careful mixtures.
