🚀 Starting point

A feedback controller measures an output, compares it with a target, and adjusts an input to close the gap, like a thermostat. Here the output is the measured KL, the target is \(k^*\), and the input is the penalty \(\beta\). \(\beta\) is controller state, not a parameter trained by gradients.

Total: 20 minutes

1. Retrieval + concept refresh — 5 minutes

Quick retrieval:

  1. Why must KL-shaped rollout rewards be detached during policy optimization?

  2. Why can a sampled \(k_1=\log\pi_{\text{old}}-\log\pi_\theta\) value be negative?

A fixed KL coefficient:

\[L = L_{\text{reward}} + \beta D_{\mathrm{KL}}\]

may be too weak early in training and too strong later. An adaptive controller treats \(\beta\) as feedback state rather than a gradient-trained parameter.

Let:

\[\hat k_n\in\mathbb{R}\]

be the globally aggregated observed KL at update \(n\), and let \(k^*\) be the target. Define relative error:

\[e_n= \operatorname{clip} \left( \frac{\hat k_n}{k^*}-1, -c,c \right)\]

A multiplicative controller is:

\[\beta_{n+1} = \beta_n\exp(\eta e_n)\]

Therefore:

  • \(\hat k_n>k^*\): increase \(\beta\);

  • \(\hat k_n<k^*\): decrease \(\beta\);

  • multiplicative updates guarantee \(\beta>0\).

Because minibatch KL is noisy, use a smoothed measurement:

\[m_n = \rho m_{n-1} + (1-\rho)\hat k_n\]

and compute the controller error from \(m_n\).

The controller should use a sufficiently aggregated exact KL or stable estimate. Feeding individual \(k_1\) samples into it is dangerous because they may be negative. In distributed training, aggregate numerator and valid-token count globally before updating one shared controller state.

✏️ Derivation: the multiplicative controller

Step 1. Error \(e_n=\operatorname{clip}(m_n/k^*-1,-c,c)\), where \(m_n\) is a smoothed KL.

Step 2. Update \(\beta_{n+1}=\beta_n e^{\eta e_n}\), i.e. \(\log\beta_{n+1}=\log\beta_n+\eta e_n\): a step in log space, so \(\beta\) stays positive and changes by percentages.

Step 3. Fixed point: \(\beta\) stops changing iff \(e_n=0\iff m_n=k^*\).

Step 4. Direction: KL too high \(\Rightarrow e>0\Rightarrow\beta\) rises \(\Rightarrow\) stronger penalty \(\Rightarrow\) KL falls. Negative feedback.

Step 5. Smoothing: \(m_n=\rho m_{n-1}+(1-\rho)\hat k_n\) averages over about \(1/(1-\rho)\) updates and suppresses noise. The clip \(c\) bounds the change per update to a factor of \(e^{\pm\eta c}\).

Step 6. Don’t feed raw \(k_1\) samples: they can be negative and noisy. Use aggregated exact KL or \(k_3\).

⚙️ Algorithm: adaptive KL controller
Input: target \(k^*\), gain \(\eta\), clip \(c\), smoothing \(\rho\), \(\beta_0\)
\(\beta\gets\beta_0\); \(m\gets k^*\)
for each update \(n\) do
\(\hat k_n\gets\) global masked mean KL (all-reduce numerator and token count)
\(m\gets\rho m+(1-\rho)\hat k_n\)
\(e\gets\operatorname{clip}(m/k^*-1,-c,c)\); \(\beta\gets\beta e^{\eta e}\) ▷ outside autograd
end

Solution — open after attempting

def run_controller(update_sign):
    beta = initial_beta.clone()
    smoothed_kl = target_kl.clone()

    history = []

    for step in range(steps):
        raw_observed_kl = (
            plant_scale / beta
            + noise[step]
        )

        measured_kl = raw_observed_kl.clamp_min(0.0)

        smoothed_kl = (
            ema_decay * smoothed_kl
            + (1.0 - ema_decay) * measured_kl
        )

        relative_error = (
            smoothed_kl / target_kl
            - 1.0
        )

        clipped_error = torch.clamp(
            relative_error,
            -max_relative_error,
            max_relative_error,
        )

        beta = beta * torch.exp(
            update_sign
            * controller_gain
            * clipped_error
        )

        history.append(torch.stack([
            beta,
            measured_kl,
            smoothed_kl,
            clipped_error,
        ]))

    return torch.stack(history)

The toy equilibrium satisfies:

\[0.02\approx\frac{0.04}{\beta}\]

so:

\[\beta\approx2\]

Initially, \(\beta=0.2\), giving KL near:

\[\frac{0.04}{0.2}=0.2\]

This is ten times the target, so the correct controller increases \(\beta\).

With the wrong sign, excessive KL reduces \(\beta\). That weakens regularization, which raises KL further, producing positive feedback and runaway behavior.

For the spike:

\[e_{\text{raw}} = \frac{2}{0.02}-1 = 99\]

Without clipping, the multiplier is:

\[\exp(0.2\cdot99)\]

which is enormous. Clipping at \(0.5\) limits it to:

\[\exp(0.2\cdot0.5) \approx1.105\]

Check answers:

  1. Multiplicative updates preserve positivity and operate naturally on the coefficient’s relative scale.

  2. Relative error is zero, so the multiplier is one and \(\beta\) remains unchanged.

  3. Worker-local batches may have different lengths, prompts, and sampling noise. Independent updates would create inconsistent controller states.

  4. The feedback sign is probably reversed, or old/new KL terms were subtracted in the wrong order.

  5. Smoothing rejects noise but adds control delay. A stale estimate may allow KL to overshoot before \(\beta\) reacts.

Retrieval answers:

  • KL-shaped rewards and returns are fixed rollout targets; differentiating through them adds an unintended product-rule path.

  • Individual sampled log-ratio terms may be negative even though their correctly sampled expectation is a nonnegative KL divergence.
