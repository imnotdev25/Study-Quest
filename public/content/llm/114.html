🚀 Starting point

An agent loop needs three things written down before it starts: a goal (the outcome, not the steps), a definition of done that a program can check, and a budget (steps, tokens, time, money). Without the second, the agent decides when it is finished, and models stop early or wander. Real-life version: “clean the kitchen” versus “the counters are clear, the dishwasher is running, and the bin is out. Back in 30 minutes.”

Goal specification template

Goal: Users can reset their password by email.
Context: Auth lives in src/auth/; email goes through src/mail/send.py. See AGENTS.md.
Constraints: no new dependencies; keep the public API of src/auth/__init__.py unchanged.
Done when:
  - tests/test_password_reset.py exists and passes (write it first)
  - make test and make lint pass
  - tokens expire after 30 minutes and are single-use (covered by tests)
Budget: stop and report after 40 tool calls or if the same test fails 3 times in a row.
Report: what changed, why, and anything you could not verify.

Loop patterns

Pattern How it runs
Verify–fix act, run the checks, feed failures back, repeat until green or the budget ends
Test-first the agent writes failing tests from the spec, you review them, then it implements until they pass
Plan–act–check a written plan with checkboxes in a file; the agent updates it as it goes, so a fresh session can resume
Evaluator–optimiser a second model (or the same with a rubric) grades the draft; loop on the critique
Spec-driven requirements \(\to\) design \(\to\) task list, each reviewed by a human before the next
Fresh-context loop a shell loop restarts the agent with the same prompt file each iteration; all state lives in files and git (sometimes called the “Ralph” loop). Each run starts clean, so context never rots
Fan-out a lead agent splits work (files, sub-questions) across parallel subagents and merges the summaries
Long-running an initialiser session sets up the environment, a progress log and a feature list; later sessions read them, do one item, test, commit and update the log

Guardrails for loops

  • Stop conditions: step and cost caps, “same error three times” detection, wall-clock limits.

  • Checkpoints: commit after each verified step, so a bad step is one git revert away.

  • Blast radius: sandbox the shell; no production credentials in the agent’s environment; human approval for deletes, pushes, deploys and spending money.

  • Reward hacking: an agent optimising “tests pass” may weaken the tests or special-case them. Protect test files, review diffs of tests separately, and keep some checks hidden from the agent. This is the RLHF over-optimisation problem from the post-training book, in a loop.
