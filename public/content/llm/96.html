🚀 Starting point

Why plain PyTorch breaks. model.generate serves one batch at a time, pads every sequence to the longest, reserves KV memory for the maximum length, and can’t add a request until the batch ends. A serving engine fixes all four.

Iteration-level scheduling (Orca)

Orca’s idea: schedule at the granularity of one model step, not one request. Each step, the scheduler builds a batch of tokens: one decode token for each running sequence plus chunks of prompts from new ones, up to a token budget. Finished sequences leave immediately and their slots are reused on the next step.

⚙️ Algorithm: One engine step (vLLM-style scheduler)
Input: running list \(R\) (oldest first), waiting queue \(W\), token budget \(\beta\), KV block pool
for each \(s\in R\) do ▷ decode and unfinished prefills first
\(n\gets\min(\text{uncomputed}(s),\beta)\)
while not enough free blocks for \(n\) tokens do
preempt the newest sequence in \(R\): free its blocks, push it to the front of \(W\)
end
schedule \((s,n)\); \(\beta\gets\beta-n\)
end
while \(W\ne\emptyset\), \(\beta>0\), \(|R|<\) max sequences do
\(s\gets W.\text{front}\); reuse cached prefix blocks; \(n\gets\min(\text{uncomputed}(s),\beta)\)
if blocks are available: move \(s\) to \(R\), schedule \((s,n)\), \(\beta\gets\beta-n\); else stop
end
run one forward pass over all scheduled tokens; sample for sequences that caught up

A sequence’s “uncomputed” tokens are its prompt at the start (prefill, maybe chunked over several steps) and exactly one token afterwards (decode). That unifies prefill and decode in one budget. The token budget trades TTFT for ITL: a bigger budget finishes prompts sooner but makes each step slower for everyone decoding. Fairness comes from the order: running sequences first, waiting ones in FIFO order, and preemption of the newest arrival.

Reading engine metrics

vLLM exposes Prometheus metrics at /metrics: running and waiting request counts, KV cache usage, prefix cache hit rate, and histograms of TTFT, ITL and E2E. Waiting rising while KV usage sits near 100% means memory-bound admission; waiting rising with low KV usage means the token budget or max-sequences limit is too low.
