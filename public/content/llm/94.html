🚀 Starting point

Starting point. Generating one token runs the whole network: embed, then per layer RMSNorm \(\to\) Q, K, V \(\to\) causal attention \(\to\) MLP, then a final norm, the logits \(z=W_{\text{out}}h\), and a sample from \(\operatorname{softmax}(z/T)\). The output token is appended and the loop repeats. That loop is why LLM inference is autoregressive: token \(t+1\) cannot start before token \(t\) exists.

Prefill and decode are different workloads

  • Prefill processes the whole prompt in one pass. Thousands of tokens share every weight read: big matrix–matrix products, compute-bound. It sets the time to first token.

  • Decode produces one token per sequence per step. Each step reads every weight to do a matrix–vector product per sequence: memory-bound. It sets the time per output token.

✏️ Derivation: What the KV cache saves

Step 1. At step \(t\), attention for the new token needs \(k_s,v_s\) for every \(s\le t\). They depend only on tokens \(\le s\), so they never change once computed.

Step 2. Without a cache, step \(t\) recomputes all \(t\) positions: total work \(\sum_{t=1}^n t=O(n^2)\) token-passes through the network.

Step 3. With a cache, step \(t\) runs the network on one token and reads \(t\) cached K/V vectors: \(O(n)\) network passes, plus attention reads that grow linearly.

Step 4. The cost is memory: \(\text{KV bytes per token}=2\cdot L\cdot n_{kv}\cdot d_h\cdot\text{bytes}\). For Llama-3.1-8B (\(L=32,n_{kv}=8,d_h=128\), bf16): \(2\cdot32\cdot8\cdot128\cdot2=131{,}072\) B \(=128\) KiB per token, so 1 GiB per 8k-token request.

✏️ Derivation: Decode is memory-bound: the roofline

Step 1. A decode step at batch \(B\) does about \(2PB\) FLOPs (one multiply-add per parameter per sequence) and reads \(2P\) bytes of bf16 weights.

Step 2. Arithmetic intensity \(I=2PB/2P=B\) FLOP/byte.

Step 3. H100: \(989\) TFLOP/s over \(3.35\) TB/s gives a ridge at \(\approx295\) FLOP/byte. Below it, the step time is \(2P/\text{bandwidth}\) whatever \(B\) is: \(16\,\text{GB}/3.35\,\text{TB/s}\approx4.8\) ms for an 8B model.

Step 4. So batching is nearly free until \(B\approx300\): throughput grows linearly with batch while latency stays flat. Every engine trick in this part exists to keep \(B\) large without running out of KV memory.

"""Inference ch. 'Prefill, Decode, KV Cache and Memory': memory math, the roofline, and timing a cache."""
import time

import torch

from tiny_gpt import Cfg, TinyGPT, generate_cached, generate_naive

GiB = 2**30
# name: (params, layers, kv_heads, head_dim) ; MLA stores (latent + rope) per layer instead of 2*kv*hd
MODELS = {"Llama-3.1-8B": (8.0e9, 32, 8, 128), "Qwen3-32B": (32.8e9, 64, 8, 128),
          "Llama-3.1-70B": (70.6e9, 80, 8, 128), "DeepSeek-V3 (MLA)": (671e9, 61, None, 512 + 64)}


def kv_bytes_per_token(layers, kv, hd, bytes_=2):
    return layers * (hd if kv is None else 2 * kv * hd) * bytes_


print("[mem] model               weights bf16   KV/token   KV tokens on 1xH100 (80 GB, 90%, 2 GiB act.)")
for name, (P, L, kv, hd) in MODELS.items():
    w = P * 2
    per = kv_bytes_per_token(L, kv, hd)
    free = 0.9 * 80e9 - w - 2 * GiB
    fit = f"{int(free / per):,} tokens = {int(free / per / 4096)} x 4k requests" if free > 0 else "weights do not fit"
    print(f"[mem] {name:19s} {w / GiB:8.1f} GiB  {per / 1024:6.0f} KiB   {fit}")

# Roofline: H100 SXM, dense bf16 ~989 TFLOP/s, HBM3 ~3.35 TB/s -> ridge at ~295 FLOP/byte.
peak, bw = 989e12, 3.35e12
print(f"[roof] ridge point {peak / bw:.0f} FLOP/byte")
print("[roof] decode batch   FLOP/byte (weights only)   bound      ideal step, 8B bf16")
P = 8.0e9
for B in (1, 8, 64, 256, 1024):
    intensity = 2 * P * B / (2 * P)                      # 2PB FLOPs over 2P bytes of weights
    t = max(2 * P * B / peak, 2 * P / bw)
    print(f"[roof] {B:5d}        {intensity:8.0f}                  {'compute' if intensity > peak / bw else 'memory ':8s}  "
          f"{t * 1e3:6.2f} ms -> {B / t:9,.0f} tok/s")

# Prefill vs decode on a tiny CPU model, and what the KV cache buys.
m = TinyGPT(Cfg(vocab=256, d=256, n_layers=4, n_heads=8, n_kv=2, dtype=torch.float32))
prompt = list(range(200))
t0 = time.perf_counter(); m.full(prompt); t_pre = time.perf_counter() - t0
t0 = time.perf_counter(); a = generate_cached(m, prompt, 64); t_c = time.perf_counter() - t0
t0 = time.perf_counter(); b = generate_naive(m, prompt, 64); t_n = time.perf_counter() - t0
print(f"[time] prefill 200 tokens in one pass: {t_pre * 1e3:.1f} ms ({t_pre / 200 * 1e3:.2f} ms/token)")
print(f"[time] decode 64 tokens with KV cache: {t_c * 1e3:.0f} ms   without cache: {t_n * 1e3:.0f} ms   "
      f"same tokens: {a == b}")

🔑 Key ideas

  • On the tiny CPU model, prefill costs 0.04 ms per token, and cached decode is several times faster than recomputing; both produce the same tokens.

  • Capacity is a subtraction: GPU memory \(\times\) utilisation \(-\) weights \(-\) activations, divided by KV bytes per token. A 32B model in bf16 leaves room for only about three 4k requests on one H100.
