🚀 Starting point

Starting point. A language model computes \(p(\text{output}\mid\text{context})\). A prompt is the part of the context you control, so prompting is choosing a context that makes the output you want likely. Every pattern below does one of three things: tells the model what the task is, shows it examples of the task, or gives it room to compute before it answers. Real-life version: briefing a smart new colleague. “Do X” works for easy tasks. For hard ones you show a finished example, explain why it matters, and let them think before answering.

Pattern What it is Use when
Zero-shot instruction only the task is common and clearly stated
Few-shot 2–8 input/output demonstrations before the query (as prior turns or in a tagged block) the format or labelling convention is unusual
Chain of thought ask for reasoning before the answer, or show worked examples (few-shot CoT) multi-step maths, logic, planning
Zero-shot CoT “think step by step” with no examples quick boost on non-reasoning models
Self-consistency sample several reasoning paths, majority-vote the final answers answers are short and checkable for equality
Role / system prompt who the model is, the audience, the constraints every production prompt
Structured output a JSON schema, enforced by the API or by grammar-constrained decoding a program reads the output
Decomposition least-to-most, plan-and-solve: split into sub-questions, solve in order long problems with clear sub-steps
Prompt chaining the output of one call is the input of the next, with checks between pipelines; each step stays simple
Generated knowledge, step-back first ask for relevant facts or the general principle, then the specific question knowledge-heavy questions
Meta-prompting ask a model to write or critique a prompt drafting prompts; then evaluate them

Why few-shot and chain of thought work

✏️ Derivation: Few-shot as inference over the task

Step 1. Treat the task as a hidden variable \(\tau\) (“translate”, “classify sentiment with labels A/B”, …). Then \(p(y\mid x,\text{demos})=\sum_\tau p(y\mid x,\tau)\,p(\tau\mid\text{demos})\).

Step 2. Each demonstration multiplies in a likelihood \(p(x_i,y_i\mid\tau)\), so \(p(\tau\mid\text{demos})\) concentrates on tasks consistent with all of them (Bayesian updating, Part III).

Step 3. So demonstrations mostly teach the format and label space, not new facts. Consistent, diverse examples matter more than many; examples that all share one surface feature teach that feature.

✏️ Derivation: Chain of thought buys serial computation

Step 1. A transformer does a fixed amount of computation per generated token (\(L\) layers).

Step 2. Answering immediately gives the problem one token’s worth of depth. Writing \(m\) reasoning tokens first gives \(m\) more passes, each able to read everything written so far: a scratchpad.

Step 3. That is the same idea as the tiny recursive model in Toolkit II: depth from iteration. Reasoning models are trained with RL (Parts on GRPO) to use this scratchpad well, which is why “think step by step” adds little to them: they already do. Give them the goal and the constraints, and set the reasoning effort or budget instead.

✏️ Derivation: When self-consistency helps, and when it hurts

Step 1. Each sample’s final answer is drawn from a distribution over answers; let the correct one have probability \(p_c\) and the most likely wrong one \(p_w\).

Step 2. With \(n\) samples, counts are multinomial; by the law of large numbers each answer’s share converges to its probability.

Step 3. So as \(n\to\infty\) the majority vote returns the mode. If the correct answer is the mode, accuracy goes to 1 even when \(p_c\) is only 0.4. If a wrong answer is the mode (a systematic error), voting makes things worse, approaching 0.

Step 4. Voting removes noise, not bias. The output shows both: 0.40 \(\to\) 0.98 in one case, 0.30 \(\to\) 0.12 in the other.

"""Agents ch. 'Prompting Patterns': prompt builders, answer parsing, and why voting helps or hurts."""
import json
import re

import numpy as np

rng = np.random.default_rng(0)
Q = "Pens cost $3 and notebooks $5. Ana buys 4 pens and 2 notebooks. How much does she pay?"


def zero_shot(q):
    return [{"role": "user", "content": q}]


def few_shot(q, examples):
    msgs = []
    for x, y in examples:                                  # demonstrations as real prior turns
        msgs += [{"role": "user", "content": x}, {"role": "assistant", "content": y}]
    return msgs + [{"role": "user", "content": q}]


def chain_of_thought(q):
    return [{"role": "user", "content": q + "\n\nWork it out step by step. End with a line 'Answer: <number>'."}]


def structured(q, schema):
    system = "Reply with one JSON object that matches this schema, and nothing else:\n" + json.dumps(schema)
    return [{"role": "system", "content": system}, {"role": "user", "content": q}]


SCHEMA = {"type": "object", "required": ["total", "currency"],
          "properties": {"total": {"type": "number"}, "currency": {"type": "string"}}}

for name, msgs in (("zero-shot", zero_shot(Q)),
                   ("few-shot", few_shot(Q, [("Apples cost $2. Tom buys 3. Total?", "Answer: 6")])),
                   ("chain-of-thought", chain_of_thought(Q)), ("structured", structured(Q, SCHEMA))):
    print(f"[prompt] {name:16s} {len(msgs)} messages, roles {[m['role'] for m in msgs]}")


def parse_answer(text):
    m = re.search(r"Answer:\s*\$?(-?\d+(?:\.\d+)?)\s*$", text.strip(), re.M)
    return float(m[1]) if m else None


def validate(obj, schema):
    """Tiny JSON-schema check: required keys and primitive types."""
    types = {"number": (int, float), "string": str}
    missing = [k for k in schema["required"] if k not in obj]
    wrong = [k for k, s in schema["properties"].items() if k in obj and not isinstance(obj[k], types[s["type"]])]
    return not missing and not wrong, missing, wrong


reply = "4 pens cost 4 x 3 = 12.\n2 notebooks cost 2 x 5 = 10.\n12 + 10 = 22.\nAnswer: 22"
print(f"[parse] CoT reply -> {parse_answer(reply)}   no answer line -> {parse_answer('It is 22 dollars.')}")
for raw in ('{"total": 22, "currency": "USD"}', '{"total": "22"}'):
    print(f"[schema] {raw:34s} valid/missing/wrong-type: {validate(json.loads(raw), SCHEMA)}")


# Self-consistency: sample n answers, take the most common. Simulated with a fixed answer distribution.
def vote_accuracy(probs, n, trials=100_000):
    """probs[0] = P(correct answer); others = distinct wrong answers. Ties broken at random."""
    counts = rng.multinomial(n, probs, size=trials).astype(float)
    counts += rng.random(counts.shape) * 1e-3
    return np.mean(counts.argmax(1) == 0)


cases = {"correct is the most likely answer (0.40 vs 0.12 x5)": [0.40] + [0.12] * 5,
         "one wrong answer is more likely (0.30 vs 0.45)": [0.30, 0.45, 0.25]}
for name, probs in cases.items():
    accs = "  ".join(f"n={n}: {vote_accuracy(probs, n):.3f}" for n in (1, 5, 15, 41))
    print(f"[vote] {name}\n[vote]   {accs}")

Writing prompts that work

  • Say what good looks like: audience, length, format, and what to do when unsure (“say you don’t know”; “ask one question if the request is ambiguous”).

  • Explain why. “Keep it under 100 words because it’s read on a phone” generalises better than “under 100 words”.

  • Separate instructions from data with tags or delimiters (<document>...</document>), and treat retrieved or user-supplied text as data that cannot change the instructions (prompt-injection defence).

  • Put long documents first, the question last in long-context prompts.

  • Prefer positive instructions (“write in flowing paragraphs”) over long lists of don’ts, and avoid shouting (ALL CAPS, “CRITICAL”): recent models follow instructions closely and over-apply emphasised rules.

  • Evaluate: a prompt is a hypothesis. Keep 20–100 test inputs with expected properties and re-run them on every change (the interval and paired-test chapters tell you when a change is real).
