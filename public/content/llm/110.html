🚀 Starting point

Starting point. A workflow runs model calls along a path you wrote in code. An agent lets the model choose the path: it decides which tool to call next, sees the result, and repeats until it decides it’s done. Agents trade predictability for flexibility, so start with the simplest workflow that works and add autonomy only where the path can’t be known in advance.

Workflows

  • Augmented LLM: one call with retrieval, tools and memory. The building block of everything else.

  • Prompt chaining: fixed sequence of calls with programmatic checks (“gates”) between them.

  • Routing: classify the input, send it to a specialised prompt or a cheaper model.

  • Parallelisation: sectioning (independent sub-tasks at once) or voting (the same task several times; self-consistency, multiple reviewers).

  • Orchestrator–workers: a lead model splits the task at run time and delegates to workers, then merges.

  • Evaluator–optimiser: one call drafts, another critiques against criteria, loop until it passes.

ReAct: reason, act, observe

⚙️ Algorithm: ReAct agent loop
Input: goal \(g\), tools \(\mathcal T\), step limit \(S\), verifier \(V\)
context \(\gets\) system prompt + tool descriptions + memory files + \(g\)
for \(s=1,\dots,S\) do
model reads context, writes a thought and either a tool call \((t,\text{args})\) or a final answer
if final answer then
if \(V\) passes then return answer
else  append “verification failed: …” and continue
end
end
check \(t\in\mathcal T\), validate args, check permissions
observation \(\gets t(\text{args})\), or the error message if it failed; truncate if long
append thought, call and observation to the context; compact if the context is too long
end
return “step limit reached” with a summary of progress

The two halves need each other. Reasoning without acting (pure CoT) can’t check facts and hallucinates; acting without reasoning can’t plan or recover. Writing the thought down before each action also makes the run debuggable: you can read why it did what it did.

The rest of the family

Pattern Idea
Plan-and-execute write a plan first, then execute steps (often with a cheaper model), re-plan when a step fails
Reflexion after a failed attempt, write a short lesson (“the test needs the file closed”) into memory, then retry with it
Tree of Thoughts explore several partial solutions, score them, expand the best (search over thoughts)
CodeAct actions are code snippets executed in a sandbox instead of JSON tool calls: loops, variables and libraries for free
Tool learning (Toolformer) train the model to insert API calls itself where they reduce loss
Subagents a lead agent hands a self-contained task to a fresh agent with its own context; only the summary comes back
Multi-agent debate several agents argue, a judge or vote decides; helps on some reasoning tasks, costs many tokens
Human-in-the-loop the agent pauses for approval at risky actions or at checkpoints
✏️ Derivation: Why long agent runs fail, and what verification buys

Step 1. A task of \(s\) steps, each right with probability \(q\), independently: success \(q^s\). At \(q=0.95\), 10 steps succeed 60% of the time, 100 steps 0.6%.

Step 2. Add a check after each step that catches a wrong step with probability \(d\), and allow up to \(r\) attempts. A step now fails only if a wrong attempt slips through, or all \(r\) attempts are wrong and caught: \(P_{\text{fail}}=\sum_{i=0}^{r-1}((1-q)d)^i(1-q)(1-d)+((1-q)d)^r\).

Step 3. With \(d=0.9,r=3\): per-step success 0.995, and 100 steps succeed 59% of the time instead of 0.6% (computed in the benchmarks chapter). Cheap, reliable checks (tests, type checkers, schema validation, a second model) are the highest-leverage part of an agent.
