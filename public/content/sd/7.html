👋 Intro

Why transactions across services are hard, two-phase commit, the saga pattern (choreography and orchestration), durable execution engines, and consensus algorithms like Raft.

The Problem

🌱 Beginner

Booking a holiday needs a flight, a hotel, and a car. If the car rental fails after you paid for the flight and hotel, you want all three cancelled, not a flight to a city where you have nowhere to sleep. Inside one database, a transaction gives this “all or nothing” for free. Across three companies’ systems, you have to build it yourself.

🔧 Intermediate

Local transactions give ACID: Atomicity, Consistency, Isolation, Durability. Once data is split across services, each with its own database (as microservices recommend), there is no single transaction manager. Options:

  1. Avoid it: redraw service boundaries so the invariant lives in one service.

  2. Two-phase commit (strong, blocking).

  3. Sagas (eventual consistency with compensation).

Two-Phase Commit (2PC)

Two-phase commit: prepare (vote), then commit.

🧠 Expert

2PC guarantees atomicity but is blocking: if the coordinator crashes after participants vote YES, they hold locks until it recovers, since they cannot decide alone. Latency is at least two round trips with locks held, and availability is the product of every participant’s availability. It works inside a single database vendor’s distributed engine (Spanner, CockroachDB run 2PC over Raft-replicated groups, so a participant is never really “down”) and in XA transactions across a few databases, but is rarely used across independently owned microservices. 3PC adds a phase to reduce blocking but does not handle network partitions, so it is mostly of academic interest.

The Saga Pattern

🌱 Beginner

A saga is a to-do list where every step has an “undo” written next to it. Do each step in order. If a step fails, walk back up the list doing each undo.

A saga runs local transactions in sequence; on failure it runs compensations in reverse.

Choreography vs Orchestration

Choreography: services react to each other’s events. Orchestration: a central coordinator issues commands.

Choreography Orchestration
Control Decentralized events Central workflow definition
Coupling Low between services Services coupled to orchestrator API
Visibility Flow is implicit, hard to trace Flow explicit, easy to inspect
Best for 2–4 steps, simple flows Many steps, branching, timeouts, human approval

Saga coordination styles

🔧 Intermediate

Durable execution engines have become the standard way to implement orchestrated sagas: Temporal, AWS Step Functions, Azure Durable Functions, Restate, DBOS, Inngest. You write the workflow as ordinary code; the engine persists each step’s result, so a crash resumes exactly where it left off, with built-in retries, timers, and compensation.

@workflow.defn
class OrderSaga:
    @workflow.run
    async def run(self, order):
        compensations = []
        try:
            await workflow.execute_activity(reserve_stock, order, retry_policy=RETRY)
            compensations.append(release_stock)
            await workflow.execute_activity(charge_card, order, retry_policy=RETRY)
            compensations.append(refund_card)
            await workflow.execute_activity(create_shipment, order, retry_policy=RETRY)
        except ActivityError:
            for undo in reversed(compensations):
                await workflow.execute_activity(undo, order, retry_policy=RETRY_FOREVER)
            raise
🧠 Expert

Sagas are ACD, not ACID: there is no isolation. Other transactions can see intermediate states (stock reserved, card not yet charged). Countermeasures:

  • Semantic locks: status fields like PENDING that other operations respect.

  • Commutative updates: design operations so order does not matter.

  • Pivot transaction: order steps so the point of no return (e.g. shipping) comes after all steps that can fail; steps after the pivot must be retriable until they succeed.

  • Reread value: verify data has not changed before overwriting.

Compensations must be idempotent and must eventually succeed (retry forever, alert humans). Some actions cannot be undone (an email sent); compensate semantically (send a correction).

📦 Use case: Travel booking

Orchestrated saga: reserve flight \(\to\) reserve hotel \(\to\) reserve car \(\to\) charge card \(\to\) confirm all. Reservations are holds with expiry times, so even if compensation is delayed the holds lapse on their own.

📦 Use case: Bank transfer between two banks

Debit source account (local TX, record transfer_id) \(\to\) send via payment network \(\to\) credit destination. If the credit is rejected, a compensating credit refunds the source. Every step is keyed by transfer_id so retries never double-move money. A daily reconciliation job double-checks ledgers.

📦 Use case: AI agent with real-world actions

An agent that books meetings and sends invoices runs inside a durable workflow. Each tool call is an activity with retries; if the LLM provider times out mid-task the agent resumes from its last completed step instead of re-sending invoices. Human approval steps are workflow signals.

Consensus: Raft and Paxos

🔧 Intermediate

Consensus lets a group of nodes agree on one value (or an ordered log) even if some fail. Raft elects a leader by majority vote with randomized election timeouts; the leader appends entries to its log and replicates them; an entry is committed once a majority has it. With \(2f+1\) nodes the cluster tolerates \(f\) failures (3 nodes tolerate 1, 5 tolerate 2). Used by etcd (Kubernetes), Consul, CockroachDB, TiKV, Kafka KRaft.

🧠 Expert

Consensus is used for metadata and coordination: leader election, distributed locks, configuration, membership, shard maps. A lock service needs fencing tokens: monotonically increasing numbers checked by the storage layer, because a paused process (GC, VM migration) may still believe it holds an expired lock. This is why a Redis lock (Redlock) is not safe for correctness-critical mutual exclusion without fencing.

Clocks and Ordering

🌱 Beginner

Two people send letters from different cities with handwritten timestamps. If their watches disagree by five minutes, the timestamps cannot tell you which letter was written first. Distributed systems have the same problem, so they track “what could have caused what” instead of trusting wall clocks.

🔧 Intermediate

Physical clocks drift (tens of parts per million) and are corrected by NTP, which can jump them forward or backward. Typical skew between servers is milliseconds, sometimes much worse. Never use wall-clock timestamps alone to order events across machines, to decide which write wins, or to expire locks.

Lamport clocks: each node keeps a counter; increment it on every event, attach it to messages, and on receive set counter = max(local, received) + 1. If event \(a\) caused \(b\), then \(L(a) < L(b)\). The converse is not true, but ties broken by node ID give a total order consistent with causality, enough for things like ordering operations in a replicated log.

Vector clocks: each node keeps a vector of counters, one per node. Comparing two vectors tells you whether one event happened before the other or they are concurrent (neither vector dominates). Dynamo used them to detect conflicting versions of a shopping cart and return both to the application to merge (Part (cases)). Their size grows with the number of writers, so systems prune them or use version vectors per replica.

Hybrid logical clocks (HLC) combine a physical timestamp with a logical counter: close to wall-clock time for humans, yet causally consistent. CockroachDB and YugabyteDB use HLC; Spanner instead bounds physical uncertainty with TrueTime.

Leader Election, Locks, and Leases

🔧 Intermediate

Leader election picks one node to coordinate (a primary database, a scheduler partition owner). Use a consensus system rather than inventing one: etcd or ZooKeeper (create an ephemeral key or node; the holder is leader; others watch it), Kubernetes Lease objects, or Raft built into the database. Leases are locks with an expiry: the holder must renew before it expires, so a crashed holder’s lock frees itself. The danger is a holder that is paused (GC, VM freeze) past its lease and then acts as if it still holds it. Fencing tokens fix this: the lock service returns an increasing number with each grant, and the protected resource rejects requests carrying a token lower than one it has already seen. Redis Redlock acquires a lock on a majority of independent Redis nodes with a timeout; it is fine for efficiency (avoid duplicate work) but, as Martin Kleppmann argued, unsafe for correctness without fencing because it depends on timing assumptions.

Gossip, Membership, and Distributed Hash Tables

Gossip Protocols

🔧 Intermediate

Each node periodically picks a few random peers and exchanges state (membership lists, heartbeats, versions). Information spreads like an epidemic, reaching all \(N\) nodes in about \(O(\log N)\) rounds, with no central coordinator and graceful handling of failures. SWIM adds failure detection: ping a random member; if no reply, ask \(k\) others to ping it indirectly; mark it suspect, then dead if suspicion is not refuted. Used by Cassandra (membership and schema), Consul and Serf, Uber’s Ringpop, and Redis Cluster. Trade-off: eventual convergence (seconds) instead of immediate agreement.

Metadata Service and Node Discovery

🔧 Intermediate

Distributed stores need to know which nodes exist and which node owns which data. Two designs: a central metadata service (strongly consistent, built on Raft or Paxos: HDFS NameNode, Kafka’s KRaft controller, Bigtable’s master with Chubby, etcd for Kubernetes), which is simple to reason about but must be highly available and is kept off the data path by client caching; or decentralized membership via gossip with consistent hashing (Dynamo, Cassandra), where every node can route. New nodes discover the cluster through seed nodes or DNS, then learn the rest. Clients cache the routing map and refresh on “wrong node” errors.

Distributed Hash Tables

🔧 Intermediate

A DHT spreads key ownership across many peers with no central directory, each peer knowing only a few others. Chord places nodes and keys on a hash ring; each node keeps a finger table of nodes at distances \(2^0, 2^1, \dots, 2^{m-1}\) around the ring, so a lookup halves the remaining distance each hop: \(O(\log N)\) hops. Kademlia measures distance as the XOR of IDs and keeps buckets of contacts per distance range; lookups query several nodes in parallel. Used in BitTorrent’s trackerless mode, IPFS, and Ethereum’s node discovery. Inside a datacenter, systems usually prefer one-hop routing (every node knows the full ring, as in Dynamo) because membership is small and latency matters.

Deep Dive: Raft Step by Step

Raft roles.

🔧 Intermediate

Terms. Time is divided into numbered terms; each has at most one leader. Any message with a higher term makes the receiver step down.

Election. A follower that hears no heartbeat for a randomized timeout (e.g. 150–300 ms) increments the term, votes for itself, and asks others. A node grants its vote only if it has not voted this term and the candidate’s log is at least as up to date as its own. Randomized timeouts make split votes rare.

Replication. Clients send writes to the leader, which appends them to its log and sends AppendEntries to followers. An entry is committed once stored on a majority; the leader then applies it and replies. Each AppendEntries carries the index and term of the previous entry; a follower rejects it if its log does not match, and the leader backs up until logs agree, overwriting the follower’s conflicting suffix.

Why it is safe. Two majorities always overlap, so any new leader must have received a vote from a node holding every committed entry, and the “log at least as up to date” rule ensures it already has them.

🧠 Expert

Practical details: linearizable reads need the leader to confirm it is still leader (a heartbeat round, “ReadIndex,” or time-based leases with bounded clock drift) or a stale ex-leader could serve old data. Membership changes use joint consensus or single-server changes to avoid two disjoint majorities. Log compaction via snapshots keeps logs bounded. Performance: each write costs one round trip to a majority, so a 5-node cluster across three regions pays cross-region latency per commit; that is why Spanner and CockroachDB let you place replicas to keep quorums local. Multi-Raft: systems like TiKV and CockroachDB run thousands of small Raft groups (one per data range) rather than one giant one, spreading leaders across nodes.

Deep Dive: Designing a Saga You Can Trust

🔧 Intermediate

A checklist for every saga step:

  1. Is the step idempotent? (Use the saga ID plus step name as an idempotency key.)

  2. What is its compensation, and is that idempotent and always eventually successful?

  3. Is this step before or after the pivot (the point of no return)?

  4. What do other users see while this step’s result is visible but the saga is unfinished? Add a PENDING state if that view is harmful.

  5. What is the timeout, and what happens on timeout: retry, compensate, or ask a human?

  6. How will you find sagas stuck mid-way? (Durable engines show them; with choreography you need a tracking table and an alert.)

🔑 Takeaways

  • First try to avoid cross-service transactions via better boundaries.

  • 2PC is strong but blocking; fine inside one database system.

  • Sagas trade isolation for availability; design compensations and pivots carefully.

  • Durable execution engines make sagas and long-running agents reliable.
