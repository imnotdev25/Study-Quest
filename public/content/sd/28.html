👋 Intro

Seven AI systems: DeepSeek’s large-scale MoE inference, Character.AI’s inference cost reductions, OpenAI’s Kubernetes clusters for training, LinkedIn’s GenAI product architecture, Uber’s on-call copilot, Netflix’s foundation model for recommendations, and DoorDash’s tools for AI agents.

The common thread.

AI systems are distributed systems with an unusual resource: GPU memory, which holds both weights and the KV cache. The production winners are teams that treat KV cache, batching, and routing as first-class design problems, and that build evaluation into every step.

Case: DeepSeek: Serving a 671B MoE Model at Scale

📋 Case facts

Domain: LLM inference
Scale: Hundreds of H800 GPU nodes serving V3/R1; reported 608B input tokens in one day
Concepts: Mixture of experts, expert parallelism, prefill/decode disaggregation, KV cache on disk, load balancing
Source: DeepSeek, “DeepSeek-V3/R1 Inference System Overview” (Open Source Week, 2025)

The model.

DeepSeek-V3 is a Mixture-of-Experts model with 671B total parameters but only about 37B active per token: each token is routed to a few of 256 experts per layer. It uses Multi-head Latent Attention (MLA), which compresses the KV cache into a small latent vector, making long contexts cheaper.

DeepSeek’s disaggregated MoE serving (as reported).

The serving design.

  • Prefill and decode on separate clusters (disaggregation), each with a different degree of expert parallelism: prefill units span 4 nodes, decode units span 18 nodes, so in decode each GPU holds only a few experts.

  • Large-scale expert parallelism increases batch size per expert (each expert sees tokens from many sequences), raising GPU efficiency, and reduces memory per GPU. The cost is all-to-all communication between GPUs.

  • Overlapping compute and communication: each batch is split into two micro-batches, so one computes while the other communicates.

  • Load balancing at three levels: prefill (balance tokens and attention compute across GPUs), decode (balance KV cache use), and experts (replicate popular experts across GPUs).

  • KV cache on disk: the KV of previous requests is stored on a distributed SSD filesystem (3FS), giving a reported 56% cache hit rate on input tokens, which makes multi-turn conversations and shared prefixes cheap.

  • Elastic capacity: during the day all nodes serve inference; at night, when traffic is low, nodes shift to research and training.

Numbers reported.

Average throughput per H800 node of about 73.7K input tokens/s during prefill (including cache hits) and 14.8K output tokens/s during decode.

📚 Lesson

  • MoE models make expert parallelism and expert load balancing central to serving.

  • Prefix caching at disk scale turns repeated context into a large cost saving.

  • Disaggregation lets prefill and decode use different parallelism and scale independently.

  • Diurnal traffic means inference capacity can double as training capacity at night.

Case: Character.AI: Cutting Serving Cost 33\(\times\)

📋 Case facts

Domain: Consumer conversational AI
Scale: Over 20,000 inference queries per second (2024)
Concepts: KV cache reduction, attention architecture, inter-turn caching, quantization
Source: Character.AI blog, “Optimizing AI Inference at Character.AI” (June 2024)

The problem.

Character.AI’s workload is long, multi-turn chat. Each reply needs the whole conversation history in context, so KV cache size and prefill of long histories dominate cost.

The techniques.

  • Multi-Query Attention (all heads share one KV head) cut KV cache size by about 8\(\times\) compared to grouped-query attention.

  • Hybrid attention: most layers use local attention over a short sliding window; only a few layers use global attention over the whole context. KV for local layers stays small regardless of length.

  • Cross-layer KV sharing: adjacent layers share the same KV cache, reducing it further. Combined, the KV cache shrank by more than 20\(\times\).

  • Stateful inter-turn caching: the KV cache of each conversation is kept in host memory between turns, in a radix-tree-like structure keyed by message prefix. When the user sends the next message, only the new tokens need prefill. Requests are routed with sticky sessions so a conversation returns to the server holding its cache. Reported cache hit rate: about 95%.

  • int8 quantization of weights, activations, and KV cache, with the model trained in int8 so there is no accuracy loss from post-training quantization.

They reported serving cost fell by a factor of 33 between late 2022 and mid-2024.

📚 Lesson

  • For chat, the conversation’s KV cache is state; cache it and route sessions back to it.

  • Architecture choices (MQA, local attention, KV sharing) are inference cost decisions.

  • Quantization-aware training avoids the quality loss of quantizing later.

Case: OpenAI: Scaling Kubernetes to 7,500 Nodes

📋 Case facts

Domain: ML training infrastructure
Scale: Single clusters of 7,500 nodes (2021)
Concepts: Kubernetes at extreme scale, networking, gang scheduling, control-plane tuning
Source: OpenAI blog, “Scaling Kubernetes to 7,500 nodes” (2021)

The workload.

Large training jobs span many nodes, each pod often using all GPUs on a node, communicating with MPI or NCCL. This is very different from typical web workloads: few, huge, tightly coupled jobs where one slow node slows the whole job.

What they changed.

  • Networking: moved from overlay networking (Flannel) to native pod networking on Azure for throughput; most training traffic uses InfiniBand or high-speed networks outside Kubernetes’ normal path.

  • API servers and etcd: dedicated nodes for etcd and API servers, and avoiding expensive LIST/WATCH patterns from many clients; monitoring was tuned so Prometheus and other tools did not overload the API server.

  • Scheduling: gang scheduling (all pods of a job start together or none do) via a coscheduling plugin, and a “team taint” scheme with balloon pods to reserve capacity per team.

  • Health checks for GPUs: automated detection of bad GPUs and network faults, which cordon nodes, because a single faulty GPU can stall a job running across thousands.

📚 Lesson

  • Large training is gang-scheduled and failure-sensitive; detect and remove bad hardware automatically.

  • At large scale, the Kubernetes control plane needs dedicated capacity and careful client behavior.

  • Do not force high-performance training traffic through general-purpose cluster networking.

Case: LinkedIn: Building Generative AI Product Features

📋 Case facts

Domain: Professional network
Scale: GenAI features across feed, jobs, and profiles for hundreds of millions of members
Concepts: Routing, RAG, tool use (“skills”), structured output, evaluation
Source: LinkedIn engineering blog, “Musings on building a Generative AI product” (2024)

The architecture.

LinkedIn’s AI-assisted features (such as asking “am I a good fit for this job?”) follow a three-step pipeline:

  1. Routing: a smaller model decides which specialized “agent” should handle the question (jobs, posts, learning).

  2. Retrieval: the agent calls internal APIs (wrapped as “skills” with LLM-friendly descriptions) and search to gather facts about the member, the job, and the company.

  3. Generation: a model writes the answer from the collected context.

Practical lessons they reported.

  • Structured output: the team found YAML was less verbose than JSON and led to fewer formatting errors from the model; combined with a defensive parser that fixed common mistakes, formatting errors dropped from about 10% to about 0.01%.

  • Evaluation was the hardest part: they built guidelines for human raters and used both humans and automated evaluation.

  • The last 20%: reaching 80% of the target experience took about a month; the remaining improvements took many more months.

  • Capacity and latency: GPU capacity and streaming were constraints; they streamed responses and ran parts of the pipeline in parallel.

📚 Lesson

  • Route first, then retrieve, then generate: small models for routing save cost and latency.

  • Wrap existing APIs as tools with clear descriptions instead of building new data paths.

  • Budget most of the effort for evaluation and the last-mile quality.

Case: Uber Genie: An On-Call Copilot with RAG

📋 Case facts

Domain: Internal developer support
Scale: Questions across many Slack help channels; reported thousands of engineering hours saved
Concepts: RAG over internal docs, data ingestion pipelines, evaluation, feedback loops
Source: Uber engineering blog, “Genie: Uber’s Gen AI On-Call Copilot” (2024)

The problem.

Platform teams at Uber answered the same questions over and over in Slack support channels. Answers existed in wikis and docs, but people did not find them.

The design.

  • Ingestion: a Spark pipeline pulls internal wikis, Stack Overflow (internal), and engineering docs, chunks them, creates embeddings, and writes them to a vector store. Data sources are scoped per channel, so each team’s bot answers from its own docs.

  • Answering: when a question is posted in a channel, Genie retrieves relevant chunks and asks an LLM to answer with links to sources.

  • Feedback: users rate answers in Slack; low-rated answers are reviewed, and missing or bad documents are identified.

  • Evaluation: an LLM-as-judge pipeline scores answers and highlights which source documents are unclear or outdated, giving teams a concrete list of docs to fix.

  • Security: data sources were reviewed so that no restricted information is indexed.

📚 Lesson

  • Internal support is one of the highest-return RAG use cases.

  • A RAG system is a documentation quality detector; feed its failures back to doc owners.

  • Scope retrieval per audience to keep answers relevant and data safe.

Case: Netflix: A Foundation Model for Recommendations

📋 Case facts

Domain: Recommendations
Scale: Hundreds of millions of members, billions of interactions
Concepts: Large sequence models, embeddings, model consolidation, fine-tuning
Source: Netflix TechBlog, “Foundation Model for Personalized Recommendation” (2025)

The problem.

Netflix ran many separate recommendation models (for different rows, pages, and use cases), each trained on overlapping data. Improvements in one did not carry over to others, and maintenance cost grew with the number of models.

The approach.

Inspired by LLMs, Netflix trained a large foundation model on members’ full interaction histories, treating each interaction (a play, a search, a rating) as a “token” in a sequence and learning to predict next interactions. Key ideas from their description:

  • Interaction tokenization: merging related events (like several plays of the same show) to keep sequences manageable.

  • Sparse attention and sliding windows to handle long histories within latency budgets.

  • Cold start for new titles by using metadata-based embeddings, since a new show has no interaction history.

  • Downstream use: the model can be used directly for predictions, as a source of user and item embeddings, or fine-tuned for specific products.

📚 Lesson

  • Consolidating many task-specific models into one foundation model can raise quality and cut maintenance.

  • Sequence modeling ideas from LLMs transfer to user behavior data.

  • Embeddings from a central model become shared infrastructure for many teams.

Case: DoorDash: A Toolbox for AI Agents

📋 Case facts

Domain: Internal AI platform
Scale: Many internal teams building agents
Concepts: Agent platform, tool registry, guardrails, evaluation, reusable components
Source: DoorDash engineering blog and ByteByteGo coverage, “How DoorDash Built a Toolbox for AI Agents”

The problem.

As teams started building LLM agents (support automation, internal assistants, data analysis), each team rebuilt the same pieces: model access, tool definitions, retrieval, guardrails, logging, and evaluation.

The approach.

A central platform provides building blocks so teams assemble agents rather than build them from scratch:

  • A model gateway for access to multiple LLM providers with budgets, logging, and fallbacks.

  • A tool registry: shared, reviewed tools (query a data warehouse, look up an order, search docs) with clear schemas and permissions.

  • Shared retrieval infrastructure over internal knowledge.

  • Guardrails applied consistently (PII handling, policy checks).

  • Evaluation and tracing built in, so every agent can be measured and debugged the same way.

📚 Lesson

  • Once several teams build agents, a platform for tools, models, and evals pays off quickly.

  • A reviewed tool registry is where security and least privilege get enforced.

  • Standard tracing and evals make agents from different teams comparable and debuggable.
