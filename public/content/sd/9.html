👋 Intro

How data actually gets onto disk and back: the constraints every storage engine faces, building a key-value store step by step (file-backed dictionary, binary format, append-only log, Bitcask, LSM tree), immutable versioned files, and the architecture of a large object store such as S3: partitioned metadata, an append-only stream layer, durability through replication and erasure coding, and end-to-end checksums.

The Constraints

🌱 Beginner

A disk is like a library where walking to a new shelf is slow but reading along a shelf is fast. Good storage engines arrange work so they mostly read and write “along the shelf” (sequentially) and rarely walk around (random access). They also assume the power can be cut at any moment.

🔧 Intermediate

  • Sequential vs random I/O: sequential writes are far faster than random writes on HDDs, and still meaningfully faster on SSDs (fewer write amplification effects in the SSD’s own flash translation layer).

  • Durability costs fsync: a write in the OS page cache is lost on power failure until fsync completes, which can take milliseconds. Engines batch many writes per fsync (group commit).

  • Torn writes: a crash can leave a half-written record. Every record needs a length and checksum so recovery can detect and discard it.

  • Three amplifications (the RUM conjecture: Read, Update, Memory, you can optimize two at the cost of the third):

    • write amplification: bytes written to disk per byte of user data;

    • read amplification: disk reads per lookup;

    • space amplification: disk space per byte of live data.

Building a Key-Value Store Step by Step

Step 1: A File-Backed Dictionary

🔧 Intermediate

Keep a hash map in memory; on every write, serialize the whole map to a file. Simple and correct for tiny data, but each write costs \(O(\text{dataset size})\), and a crash in the middle of writing corrupts the file. Fix the corruption: write to a temporary file, fsync it, then atomically rename it over the old file (rename is atomic on POSIX file systems), then fsync the directory. This write-temp-then-rename trick is how many config stores and SQLite’s rollback journal avoid half-written files.

Step 2: A Custom Binary Record Format

A length-prefixed, checksummed record (Bitcask’s format).

🔧 Intermediate

Design rules for a binary format: put a magic number and version at the start of each file so readers can reject or migrate old formats; length-prefix variable fields (no delimiters to escape); fix the byte order (little-endian is common); include a checksum per record (CRC32C is hardware-accelerated); use a special value or flag for tombstones (deletions); and leave reserved fields or a flags byte for future extensions. Text formats (JSON lines) are easier to debug; binary formats are smaller and faster to parse.

Step 3: Log-Structured Storage

🔧 Intermediate

Instead of rewriting the file, append each put or delete as a record to the end of a log. Writes become sequential and fast; a crash can only damage the last record. The cost moves to reads: without an index, finding the latest value of a key means scanning the whole log, and the log grows forever with overwritten values. Every log-structured engine adds two things: an index and compaction.

Step 4: Bitcask

Bitcask (the storage engine from Basho’s Riak).

🔧 Intermediate

Bitcask keeps a hash table (the keydir) of every key in memory, mapping to the file and byte offset of its latest value. A read is one hash lookup plus at most one disk read. A write appends to the active file and updates the keydir. When the active file reaches a size limit it is closed (immutable) and a new one is opened. Compaction (merge) reads old files, keeps only live values, and writes new files plus hint files (key \(\to\) offset) so that startup can rebuild the keydir quickly without scanning all data. Trade-offs: excellent read and write latency and simple crash recovery, but all keys must fit in RAM and range queries are impossible (hash index). Good fit: many small values with frequent updates and a bounded key count (sessions, counters).

Step 5: The LSM Tree

The LSM write path.

🔧 Intermediate

Write path: append to the write-ahead log (for crash recovery), then insert into the in-memory memtable, a sorted structure such as a skip list. When the memtable is full it becomes immutable and is flushed to disk as an SSTable (sorted string table): a file of sorted key–value pairs split into blocks, followed by an index block, a Bloom filter, and a footer. After the flush, that portion of the WAL can be deleted.

Read path: check the memtable, then the immutable memtable, then SSTables from newest to oldest. For each SSTable: check its Bloom filter (skip the file if the key is definitely absent), binary search the sparse index (one entry per block, e.g. the first key of every 4 KB block) to find a block, read and search that block (often cached in a block cache). Range scans merge sorted iterators from all levels. Deletes write tombstones that hide older values until compaction removes both.

🧠 Expert

Compaction strategies and amplification.

  • Size-tiered (Cassandra’s default, early HBase): merge several SSTables of similar size into one bigger one. Lower write amplification, but a key can exist in many files (higher read amplification) and a merge temporarily needs extra space roughly equal to the inputs (up to 2\(\times\) space amplification).

  • Leveled (LevelDB, RocksDB default): each level is about 10\(\times\) larger than the previous and holds non-overlapping SSTables, so a lookup checks at most one file per level. Reads and space are efficient; write amplification can reach 10–30\(\times\) because data is rewritten at each level.

  • Hybrids (RocksDB universal, ScyllaDB incremental) trade between them.

Compaction competes with foreground traffic for I/O; if writes outpace compaction, L0 files pile up and reads slow, so engines stall writes. That was one of Discord’s Cassandra problems (Part (cases)). Tombstone-heavy workloads (queues on Cassandra) are a known anti-pattern because reads must skip many tombstones.

Immutable Versioned Data Files

🔧 Intermediate

Data lakes take immutability further. Table formats such as Apache Iceberg and Delta Lake store data in immutable columnar files (Parquet) on object storage. A table version is a manifest: a list of the data files that make up the table at that moment, plus statistics. A write creates new data files and a new manifest, then atomically swaps a single pointer (catalog entry or log record) to the new version. Consequences: readers always see a consistent snapshot, time travel queries read an old manifest, concurrent writers use optimistic concurrency on the pointer swap, and deletes are either rewrites of affected files or “delete files” merged at read time. Old files are garbage-collected after a retention period.

Object Storage vs a Database

Object store (S3, GCS) Database
Unit whole object, written once (overwrite = new version) row or document, updated in place
Queries get by key, list by prefix indexes, joins, transactions
Size bytes to terabytes per object small records
Latency tens of ms first byte sub-ms to ms
Cost very cheap per GB expensive per GB
Use images, video, backups, logs, data lake files, model weights metadata, state, anything queried
🔧 Intermediate

The standard pattern: bytes in the object store, metadata in a database. A photo row in Postgres holds the owner, caption, dimensions, and the object key; the image itself lives in S3 and is served through a CDN. Never store large blobs in the primary database: they bloat backups, replication, and the buffer cache.

Architecture of an Object Store

Layered object storage, following the published design of Windows Azure Storage (Calder et al., SOSP 2011).

🔧 Intermediate

Amazon has not published S3’s internals in detail, but Microsoft’s paper on Windows Azure Storage describes the same kind of system and is the clearest public reference. It has three layers:

  1. Front end: stateless servers that authenticate requests and route them, caching the partition map.

  2. Partition layer: holds the object index (bucket, key, version \(\to\) location of the bytes, size, checksum, metadata). The index is split into key ranges, each served by one partition server. A partition manager assigns ranges to servers, splits hot or large ranges, merges cold ones, and records the assignment in a partition map table, which front ends cache.

  3. Stream layer: stores bytes in large append-only extents (hundreds of MB to GB) replicated across storage nodes. An extent is appended to until it reaches its size limit, then sealed (immutable). Sealed extents can be erasure-coded and moved freely.

Range Partitioning vs Consistent Hashing for Storage

🔧 Intermediate

Object stores must support listing by prefix (list photos/2026/10/), which requires keys in sorted order: range partitioning keeps nearby keys on the same server, so a list is a sequential scan of one or a few ranges. Consistent hashing would scatter a prefix across every node. The cost of range partitioning is hot ranges: sequential keys (timestamps, incrementing IDs) all land in the last range. The partition manager splits hot ranges automatically, and S3 documentation historically advised spreading load across prefixes; S3 now scales a prefix to thousands of requests per second and splits automatically, but very sudden spikes on a new prefix can still see throttling while it scales.

Metadata Database Design

CREATE TABLE buckets (
  bucket_id   BIGINT PRIMARY KEY,
  name        TEXT UNIQUE NOT NULL,
  owner_id    BIGINT NOT NULL,
  versioning  BOOLEAN NOT NULL DEFAULT FALSE,
  created_at  TIMESTAMPTZ NOT NULL
);
CREATE TABLE objects (
  bucket_id   BIGINT NOT NULL,
  object_key  TEXT   NOT NULL,          -- sorted: enables prefix listing
  version_id  BIGINT NOT NULL,          -- newer versions sort first (store negated)
  is_latest   BOOLEAN NOT NULL,
  is_delete_marker BOOLEAN NOT NULL DEFAULT FALSE,
  size_bytes  BIGINT NOT NULL,
  checksum    BYTEA  NOT NULL,          -- e.g. SHA-256 or CRC32C of content
  locations   JSONB  NOT NULL,          -- extent ids + offsets, or EC stripe ids
  PRIMARY KEY (bucket_id, object_key, version_id)
);
CREATE TABLE multipart_parts (
  upload_id   UUID   NOT NULL,
  part_number INT    NOT NULL,          -- 1..10000
  size_bytes  BIGINT NOT NULL,
  checksum    BYTEA  NOT NULL,
  locations   JSONB  NOT NULL,
  PRIMARY KEY (upload_id, part_number)
);
🔧 Intermediate

A PUT writes the bytes to the stream layer first, then commits one metadata row; the object becomes visible only when the row commits, which is how an object store gives atomic, all-or-nothing uploads. A failure after the bytes are written leaves orphaned bytes, which a garbage collector reclaims by comparing extents with live metadata. Consistency: S3 has provided strong read-after-write consistency for PUTs and DELETEs (including listing) since December 2020.

Durability and Replication

🔧 Intermediate

Replication keeps \(r\) full copies (typically 3) on different racks or zones: simple and fast to read and repair, 3\(\times\) storage. Erasure coding splits data into \(k\) data fragments plus \(m\) parity fragments; any \(k\) of the \(k+m\) reconstruct it. A \((6, 3)\) Reed–Solomon code tolerates 3 lost fragments at 1.5\(\times\) storage. Systems write new data replicated (low latency, appends are easy) and erasure-code sealed extents in the background. Placement spreads fragments across failure domains (disks, hosts, racks, zones), so one rack or zone failure loses at most what the code can tolerate.

Durability math depends on how quickly lost fragments are repaired: the risk is losing \(m+1\) fragments of the same stripe before repair finishes. Faster repair (spreading reconstruction across many nodes), more parity, and independent failure domains all increase durability. S3 advertises 99.999999999% (11 nines) annual durability for its standard class.

End-to-End Checksums

🌱 Beginner

Data can be silently damaged anywhere: a flipped bit in RAM, a buggy network card, a disk returning the wrong sector. A checksum is a fingerprint computed when data is created and checked every time it is read or moved. If the fingerprint does not match, the system knows the copy is bad and uses another.

🔧 Intermediate

End to end means the checksum is computed by the client (or the first server) and travels with the data through every hop: front end, stream layer, disk, and back. Each hop verifies before acknowledging; storage nodes verify on read and during background scrubbing (periodically reading all data to find bit rot before a user does). TCP’s 16-bit checksum and disk ECC are not enough at petabyte scale; rare silent errors become daily events. S3 lets clients send CRC32C, CRC32, SHA-1, or SHA-256 checksums with uploads and stores them for verification on download. Large objects use per-part checksums plus a checksum of checksums.

📦 Use case: Facebook Haystack: many small photos

Storing billions of small photos as individual files made metadata lookups (inode reads) the bottleneck: several disk seeks per photo. Haystack (OSDI 2010) packs many photos into large append-only volume files and keeps a compact in-memory index (photo id \(\to\) offset, size) per volume, so a read is one seek. Deleted photos are flagged and reclaimed by compaction. This is Bitcask’s idea applied to blobs, and the same idea behind byte-range indexed object storage in general.

📦 Use case: Interview: design a key-value store

Start with the API and data size. If keys fit in memory and range queries are not needed: Bitcask-style log plus hash index. If data is larger than RAM or range scans are needed: LSM tree (write-heavy) or B-tree (read-heavy). Then add a WAL, checksummed records, compaction, and snapshots. For distribution: partition (consistent hashing or ranges), replicate (leader-based or leaderless quorums), and choose a consistency model (Chapter (data), Dynamo in Part (cases)).

⚠️ Pitfall

  • Forgetting fsync, or trusting a write that only reached the page cache.

  • Overwriting files in place without temp-file-and-rename.

  • Records without lengths and checksums, so recovery cannot find torn writes.

  • Storing large blobs in the primary database.

  • Sequential keys on range-partitioned stores without planning for hot ranges.

🔑 Takeaways

  • Append-only logs make writes fast and crash-safe; indexes and compaction make them practical.

  • Bitcask: hash index in RAM, one seek per read, no range scans. LSM: memtable, WAL, SSTables, Bloom filters, compaction.

  • Object stores separate a range-partitioned metadata index from an append-only byte layer.

  • Durability comes from replication or erasure coding across failure domains, fast repair, and end-to-end checksums.
