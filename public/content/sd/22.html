👋 Intro

Fourteen stories of how real companies stored, sharded, cached, and migrated data as they grew from thousands to billions of users. Each case follows the same shape: the problem, the design, why it works, the numbers, and the lessons you can reuse. Numbers come from the companies’ own engineering blogs and papers; treat them as “as reported at the time.”

How to read these cases.

Do not memorize the architectures. Look for the forcing function: the specific limit (disk, IOPS, GC pauses, vacuum, connection count, fan-out) that made the old design fail. Real systems change when a measured limit is hit, almost never because a new technology is fashionable. Every case in this part names that limit.

Case: Discord: Storing Trillions of Messages

📋 Case facts

Domain: Chat, wide-column storage
Scale: Trillions of messages; 177 Cassandra nodes shrunk to 72 ScyllaDB nodes
Concepts: Partitioning, hot partitions, GC pauses, request coalescing, consistent hashing, data migration
Source: Discord engineering blog, “How Discord Stores Trillions of Messages” (2023)

The problem.

Discord stored messages in Cassandra, partitioned by (channel_id, time bucket) and clustered by a Snowflake message ID, so reading a channel’s history is a single-partition range scan. The cluster grew from 12 nodes in 2017 to 177 nodes by early 2022, and became an operational burden that the on-call team called “high-toil.” Three forces combined:

  • Hot partitions. A huge public server with a sudden burst of activity concentrates reads on one partition. Because reads and writes used quorum consistency, every query touching the slow node slowed down, and latency spread to unrelated channels.

  • Compaction. Cassandra is an LSM-tree database: writes are cheap appends, but background compaction must merge files. When compaction fell behind, reads had to check more SSTables and got slower, which made compaction fall further behind.

  • JVM garbage collection. Long GC pauses caused latency spikes, and sometimes the team had to reboot nodes and babysit them back to health.

Discord’s message storage after 2022.

The design.

Discord did two things, and the first matters more.

  1. A data services layer in Rust sits between the API and the database. Each service exposes roughly one gRPC endpoint per query and holds no business logic. Its key trick is request coalescing: if several users ask for the same row at the same moment, only the first request starts a database query; later requests subscribe to that in-flight task and get the same result. Requests are routed with consistent hashing on channel_id, so every request for one channel reaches the same service instance. That is what makes coalescing effective: duplicates meet in the same process.

  2. ScyllaDB, a Cassandra-compatible database written in C++ with no garbage collector and a shard-per-core design, replaced Cassandra.

The migration.

ScyllaDB’s Spark-based migrator was estimated at three months. Instead the team extended their Rust data-service library into a migrator in an afternoon: it read token ranges, checkpointed progress in a local SQLite database, and wrote to ScyllaDB at up to 3.2 million messages per second, finishing in about nine days. It stalled at 99.9999% because the final token ranges contained huge ranges of uncompacted tombstones (deletion markers); compacting that range fixed it in seconds. Before cutover, a small percentage of reads went to both databases and results were compared automatically.

Numbers.

Historical message fetch p99 fell from 40–125 ms to 15 ms; insert p99 fell from 5–70 ms to a steady 5 ms. Node count dropped from 177 to 72 (each node holding about 9 TB instead of 4 TB). The system handled the 2022 World Cup final, where goals were visible as spikes in the message graph.

Why it works.

Hot partitions are a workload problem, not a database problem. Coalescing collapses duplicate reads before they reach storage, so the hot partition sees one query instead of thousands. The database change removed GC pauses (a tail latency problem) and reduced per-node overhead, which allowed fewer, denser nodes.

📚 Lesson

  • Put a thin data-access layer in front of your database; it is where coalescing, routing, rate limiting, and migrations become possible.

  • Route duplicate work to the same place (consistent hashing) so it can be deduplicated.

  • Validate migrations with shadow reads that compare old and new results.

  • Tombstones and compaction debt are a hidden cost of LSM databases.

Case: Figma: Scaling Postgres Nearly 100\(\times\)

📋 Case facts

Domain: Collaborative design SaaS
Scale: Database stack grew almost 100\(\times\) since 2020
Concepts: Vertical partitioning, horizontal sharding, colocation, query proxy, logical vs physical sharding
Source: Figma blog, “How Figma’s databases team lived to tell the scale” (2024)

The problem.

In 2020 Figma ran one Postgres instance on the largest machine AWS offered. The team first did vertical partitioning: moving groups of related tables (files, organizations, and so on) into their own databases, ending up with about a dozen. That bought time, but a single table is the smallest unit you can move that way. Some tables reached several terabytes and billions of rows. Postgres VACUUM (which reclaims dead row versions) became unreliable and the databases approached the IOPS ceiling of Amazon RDS.

Options considered.

CockroachDB, TiDB, Spanner, Vitess, and NoSQL were evaluated. With only months of runway, a complex relational data model, and deep RDS Postgres expertise, Figma chose to build horizontal sharding on top of existing RDS Postgres instead of migrating to a new database.

Figma’s DBProxy routes SQL to the right shard.

The design.

  • Colos (colocations). Tables that share a shard key (UserID, FileID, or OrgID) are grouped and sharded together. Joins and transactions within a colo work as long as they stay on one shard key.

  • Hash routing. Rows are routed by a hash of the shard key, avoiding hotspots from sequential IDs, at the cost of slower range scans.

  • DBProxy, a Go service, parses SQL into an AST, works out which logical shards a query touches, maps them to physical databases, and rewrites the query. It also does load shedding, request hedging, and observability. Topology changes propagate in under a second.

  • Logical before physical sharding. First, each “shard” was a Postgres view on the still-unsharded table, each behind its own connection pool. This could be rolled out by percentage with feature flags and rolled back in seconds; views added under 10% overhead in the worst case. Only after logical sharding was proven did they physically split databases (a 1-to-N failover).

  • Shadow readiness checks. Candidate sharding schemes were run through the planner against live production queries and logged for offline analysis, showing product teams exactly which queries would break.

Numbers.

The first table took about nine months to shard and shipped in September 2023 with ten seconds of partial availability on primaries and none on replicas. The supported query subset covers about 90% of queries; queries without a shard key fall back to scatter-gather across all shards.

📚 Lesson

  • Exhaust cheap options first (bigger box, replicas, vertical partitioning), but know their hard limits.

  • Separate the logical change (routing) from the physical change (moving data); make the logical step reversible.

  • Restricting the query language is a feature: it keeps the sharded system predictable.

  • Test new routing against real traffic in shadow mode before it matters.

Case: Notion: Sharding Postgres by Workspace

📋 Case facts

Domain: Docs and wikis SaaS
Scale: 480 logical shards on 32 physical Postgres databases
Concepts: Shard key choice, logical shards, double writes, backfill, dark reads
Source: Notion blog, “Herding elephants: lessons learned from sharding Postgres at Notion” (2021)

The problem.

Everything in Notion is a block: a paragraph, a to-do, an image, a page. The block table in a single Postgres monolith grew so large that VACUUM kept stalling and Postgres approached transaction ID wraparound. Postgres uses 32-bit transaction IDs; if vacuum cannot freeze old rows fast enough, the database stops accepting writes to protect data. That is a hard deadline.

Choosing the shard key.

Every block belongs to exactly one workspace, so space_id was chosen as the shard key. All tables reachable from block by foreign keys (space, discussion, comment, …) were sharded with it, so nearly all queries stay within one shard.

Why 480 shards?

480 has many divisors. 32 hosts \(\times\) 15 shards is even; the fleet can grow to 40 hosts (12 each) or 48 (10 each) without uneven shards. With 512 shards, the next even step after 32 hosts would be 64. Each logical shard is a Postgres schema (schema001.block) rather than native partitioning.

Notion’s migration: double write, backfill, verify, cut over.

The migration.

  1. Double writes via an audit log table plus a catch-up script that replayed writes into the shards. Logical replication was rejected because it could not keep up with block writes during the initial snapshot.

  2. Backfill of historical data took about three days on a 96-CPU machine. Each record’s version was compared so newer data was never overwritten, which meant backfill and catch-up could run in any order.

  3. Verification: a script compared random UUID ranges between old and new; dark reads fetched from both, logged mismatches, and discarded the sharded result. Different engineers wrote the migration and the verification code, so one person’s bug would not hide in both.

  4. Cutover with about five minutes of scheduled downtime.

📚 Lesson

  • Shard earlier than feels necessary; a forced migration under a deadline is harder.

  • Choose a shard key that matches the ownership boundary of your data (workspace, tenant).

  • Pick a logical shard count with many divisors.

  • Make writes idempotent with versions, so backfill and live replication can race safely.

Case: OpenAI: One Postgres Primary Behind ChatGPT

📋 Case facts

Domain: Consumer AI
Scale: Hundreds of millions of weekly users; one primary with dozens of read replicas
Concepts: Read replicas, connection pooling, cache stampede protection, workload isolation, write offloading
Source: OpenAI engineering blog, “Scaling PostgreSQL” (2026)

The surprise.

Many expect ChatGPT’s metadata to live in an exotic distributed database. OpenAI reported instead that a large share of it runs on a single Azure Postgres primary with close to fifty read replicas across regions, serving millions of queries per second. The design works because the workload is overwhelmingly reads.

How they keep one primary alive.

  • Push reads to replicas and keep the primary for writes and reads that must be fresh.

  • Offload write-heavy, shardable workloads to a horizontally scalable store (Azure Cosmos DB), and stop adding new tables to the main Postgres cluster.

  • Connection pooling with PgBouncer: Postgres uses one process per connection, so thousands of app pods connecting directly would exhaust memory. Pooling multiplexes many clients onto few server connections.

  • Cache stampede protection: when a cache entry expires, only one request is allowed to rebuild it (a lock or lease); others wait or use stale data, so a cache miss storm cannot flatten the database.

  • Rate limiting at several layers (application, pooler, proxy, query) and workload isolation: noisy, low-priority traffic is sent to separate instances so it cannot starve critical paths.

  • Careful writes: backfills are rate-limited, and expensive multi-table joins are moved into the application.

The incident that tested it.

A viral launch of image generation brought a sudden flood of new sign-ups and a burst of writes. The lesson reported was that write surges, not reads, are what threaten a single-primary design, which is why write-heavy workloads were moved off it.

📚 Lesson

  • A boring, well-tuned single primary goes much further than most teams expect.

  • Protect the database with pooling, stampede locks, and rate limits before sharding it.

  • Move only the workloads that do not fit (write-heavy, easily partitioned) to a different store.

Case: Instagram: Sharding and 64-bit IDs on Postgres

📋 Case facts

Domain: Social media
Scale: Thousands of logical shards on a few physical Postgres servers (2012)
Concepts: Logical shards, ID generation, time-sortable IDs
Source: Instagram engineering blog, “Sharding & IDs at Instagram” (2012)

The problem.

When data is sharded, you can no longer use one database’s auto-increment column for IDs. Instagram needed IDs that were unique across shards, sortable by time (so feeds can be ordered by ID), fit in 64 bits (for compact indexes), and did not need a central ID service.

Instagram’s 64-bit ID layout.

The design.

Data was split into several thousand logical shards, each a Postgres schema, mapped onto a few physical servers. Moving a logical shard to a new server is a copy, not a re-split. Each ID is generated inside Postgres by a PL/pgSQL function: 41 bits of milliseconds since a custom epoch (about 41 years of range), 13 bits for the logical shard (8,192 shards), and 10 bits from a per-shard sequence modulo 1,024 (1,024 IDs per shard per millisecond). Because the shard ID is embedded, you can find a row’s shard from its ID alone.

Compare: Twitter Snowflake.

Twitter’s Snowflake (2010) uses 41 bits of time, 10 bits of machine ID (data center plus worker), and 12 bits of sequence (4,096 per millisecond per machine), generated by a standalone service. Discord and many others use Snowflake-style IDs. Modern equivalents for general use are ULID and UUIDv7, which put a timestamp in the high bits so B-tree inserts stay at the “right edge” of the index. Shopify reported ULIDs cut insert time by half compared to random UUIDv4 in one system, because random keys scatter writes across the whole index.

📚 Lesson

  • Time-ordered IDs make indexes and feeds efficient; random UUIDv4 keys hurt B-tree write locality.

  • Embedding the shard in the ID removes a lookup on every read.

  • Many logical shards on few machines make future growth a copy operation.

Case: Uber: Schemaless, a Datastore on MySQL

📋 Case facts

Domain: Mobility
Scale: Trip data for billions of trips
Concepts: Append-only storage, sharding, asynchronous triggers, building on proven engines
Source: Uber engineering blog, “Designing Schemaless” (2016)

The problem.

In 2014 Uber’s trip data lived in a single Postgres instance that was projected to run out of capacity within months. They needed horizontal scale, high write availability (a trip must be recorded even during partial failures), and change notifications for downstream systems such as billing.

The design.

Schemaless is a sharded layer on top of many MySQL databases. Its data model is a sparse three-dimensional map: row key (a UUID, such as a trip), column name (such as BASE, STATUS), and ref key (a version number). A cell is an immutable JSON blob; updates write a new version rather than modifying in place. This append-only model makes replication and conflict handling simple. Writes are buffered to a secondary cluster if the primary is down. Triggers let consumers subscribe to changes in a column, so the billing system can react when a trip’s STATUS column gets a new cell. This is an early version of change data capture. Schemaless later evolved into Docstore, which added schemas and transactions.

📚 Lesson

  • Building a distributed layer on a battle-tested storage engine (MySQL/InnoDB) reduces risk.

  • Immutable, versioned records simplify replication, auditing, and event streams.

  • Change notifications built into storage remove dual-write bugs.

Case: Slack: Moving to Vitess

📋 Case facts

Domain: Workplace chat
Scale: Reported 2.3M peak QPS on Vitess (2020)
Concepts: Re-sharding, shard key change, MySQL middleware
Source: Slack engineering blog, “Scaling Datastores at Slack with Vitess” (2020)

The problem.

Slack originally sharded MySQL by workspace: one team’s data on one shard. That broke down in two ways. Enterprise customers (huge workspaces and cross-workspace channels with Enterprise Grid) made some shards very hot, and Slack Connect created channels shared between companies, which did not belong to a single workspace at all.

The design.

Slack adopted Vitess, the MySQL sharding middleware created at YouTube. Vitess puts a routing layer (VTGate) in front of many MySQL shards (each managed by VTTablet), stores the shard map in a topology service, and supports online resharding. Slack could choose a different shard key per table: messages by channel_id rather than by workspace, which spreads a large customer’s load across many shards.

Numbers.

Slack reported that by late 2020 nearly all query traffic ran on Vitess, peaking at about 2.3 million QPS with a median query latency of about 2 ms.

📚 Lesson

  • The right shard key can change as the product changes; plan for re-sharding.

  • Tenant-based sharding struggles when single tenants get huge or data is shared across tenants.

  • Proven middleware (Vitess, Citus) is often better than writing your own sharding layer.

Case: Stripe: Zero-Downtime Data Movement in DocDB

📋 Case facts

Domain: Payments
Scale: Reported over 5M queries/s across thousands of shards
Concepts: Online data migration, CDC, chunk-based sharding, traffic switching
Source: Stripe blog on DocDB and its Data Movement Platform (2024)

The problem.

Stripe runs DocDB, its own database-as-a-service built on MongoDB. Payments cannot tolerate downtime, yet shards constantly need splitting, merging, and rebalancing as merchants grow, and the fleet needs version upgrades.

The design.

Data is divided into chunks (key ranges) that can be moved between shards. A move works like this:

  1. Register the migration and prepare the target shard.

  2. Bulk import a snapshot of the chunk to the target.

  3. Asynchronous replication: stream ongoing changes from the source’s operation log (change data capture) to the target until it is nearly caught up.

  4. Correctness check: compare source and target point-in-time snapshots.

  5. Traffic switch: briefly block writes to the chunk at the routing layer, apply the final changes, update the routing metadata, and release. Stripe reported this pause takes on the order of a couple of seconds.

  6. Clean up the source.

📚 Lesson

  • Online migration = snapshot + change stream + verify + short write fence + route switch.

  • Make the routing layer the single place where “where does key X live” is decided.

  • Moving data must be routine and automated, not a heroic project.

Case: Shopify: Pods for Isolation

📋 Case facts

Domain: E-commerce platform
Scale: Millions of merchants; extreme Black Friday peaks
Concepts: Cell-based architecture, blast radius, tenant routing
Source: Shopify engineering blog posts on pods and flash-sale readiness

The problem.

A single merchant running a flash sale (a celebrity product drop) can generate a traffic spike larger than everyone else combined. In a shared database, that one merchant could slow down every other store.

The design.

Shopify splits its fleet into pods: each pod is a self-contained set of data stores (a MySQL shard, Redis, Memcached) holding all data for a group of shops. The Rails monolith is stateless and can serve any pod. An edge routing layer looks up which pod a shop belongs to and routes the request there. Shops can be moved between pods by a pod mover. A problem in one pod affects only the shops in it. This is the cell-based architecture pattern also used by AWS, Slack, and others.

📚 Lesson

  • Cells limit blast radius: a failure or noisy tenant only affects one cell.

  • Route by tenant at the edge; keep application servers stateless and shared.

  • Build tooling to move tenants between cells from day one.

Case: Meta TAO: A Cache for the Social Graph

📋 Case facts

Domain: Social network
Scale: Over a billion reads/s and millions of writes/s (2013 paper)
Concepts: Graph data model, read-through cache, cache tiers, eventual consistency
Source: Bronson et al., “TAO: Facebook’s Distributed Data Store for the Social Graph”, USENIX ATC 2013

The problem.

Rendering one Facebook page requires hundreds of small lookups: who are this user’s friends, which of them liked this post, how many comments does it have. Using memcache with ad-hoc keys in front of MySQL made application code complex and invalidation error-prone.

The design.

TAO exposes a simple graph API with two concepts: objects (users, posts, pages, with an ID and type) and associations (typed edges like LIKES or FRIEND, time-ordered). Queries are things like “the 50 most recent comments on post X” or “count of likes on X.” Data lives in sharded MySQL. In front sits a two-tier cache: follower caches serve reads in every region; a leader cache per shard handles writes and keeps followers consistent with invalidation messages. Remote regions read locally and forward writes to the master region for that shard. Consistency is eventual, with read-your-writes for the writing user.

📚 Lesson

  • A domain-specific data API (objects and edges) hides caching and sharding from product code.

  • For read-dominated workloads, a smart read-through cache can be the primary interface to data.

  • Leader/follower cache tiers keep invalidation traffic manageable.

Case: Facebook: Scaling Memcache

📋 Case facts

Domain: Social network
Scale: Billions of requests per second across clusters and regions
Concepts: Look-aside cache, leases, thundering herd, regional invalidation
Source: Nishtala et al., “Scaling Memcache at Facebook”, NSDI 2013

Key techniques.

This paper is a catalogue of caching problems from Chapter (caching), solved at extreme scale:

  • Leases solve both stale sets and thundering herds. On a miss, memcache gives the client a lease token. Only the token holder can fill the key, and a delete invalidates the token, so a slow reader cannot write stale data after a newer update. Memcache also hands out a lease for a key only every few seconds, so other clients wait briefly instead of all hitting the database.

  • mcrouter, a memcache proxy, handles routing, connection pooling, and replication of hot keys.

  • Batching and parallel fetches: a page’s keys are fetched as a DAG of dependencies in parallel, and UDP is used for gets to reduce overhead.

  • Gutter pool: when a cache server fails, its keys go to a small set of spare servers with short TTLs instead of rehashing onto healthy ones (which could cascade failures).

  • Invalidation via the database commit log: a daemon (mcsqueal) tails MySQL’s log and broadcasts deletes, so invalidation is reliable even if the web server crashes after writing.

  • Remote markers for cross-region consistency: after writing in a non-master region, a marker tells readers to go to the master region until replication catches up.

📚 Lesson

  • Leases are the cleanest fix for both stale-set races and stampedes.

  • Drive invalidation from the database log, not from application code.

  • Do not rehash a failed cache node’s keys onto healthy nodes during an outage.

Case: Amazon DynamoDB: Predictable Performance at Any Scale

📋 Case facts

Domain: Cloud database
Scale: Reported peak of over 100M requests/s during Prime Day 2022
Concepts: Partitioning, Multi-Paxos replication, admission control, adaptive capacity
Source: Elhemali et al., “Amazon DynamoDB: A Scalable, Predictably Performant…”, USENIX ATC 2022

The design.

A table is split into partitions by hash of the partition key. Each partition is replicated to three storage nodes in different Availability Zones; replicas form a Multi-Paxos group with a leader that handles writes and strongly consistent reads. Request routers look up partition locations in a metadata service and forward requests.

The interesting evolution.

Early DynamoDB divided a table’s provisioned throughput evenly across partitions. If a customer’s traffic was uneven (a hot key), the hot partition was throttled even though the table as a whole had spare capacity. The fix happened in stages: bursting (borrow unused capacity from the recent past), adaptive capacity (move capacity to hot partitions), and finally global admission control, which tracks capacity at the table level using token buckets independent of partitions. Hot partitions can also be split automatically by observed key ranges.

Why predictability matters.

The paper’s central message is that customers value consistent single-digit millisecond latency more than peak throughput. Many design decisions (avoiding cross-partition coordination, caching metadata in routers, limiting the size of a partition) exist to reduce variance rather than improve averages.

📚 Lesson

  • Uniform partitioning of capacity fails on real, skewed workloads; manage capacity globally.

  • Optimize for low variance, not just low average latency.

  • Every metadata dependency on the request path needs caching and a plan for when it fails (see Section (aws)).

Case: Instagram’s First Architecture

📋 Case facts

Domain: Photo sharing
Scale: About 14 million users within roughly a year, run by a handful of engineers (2011–2012)
Concepts: Boring technology, sharded Postgres, async fan-out, caching, object storage
Source: Instagram engineering blog, “What Powers Instagram: Hundreds of Instances, Dozens of Technologies” (2011)

The stack, as described in 2011.

Instagram around 2011.

  • Application: Django (Python) on Gunicorn behind nginx, on Amazon EC2; app servers were stateless and interchangeable.

  • Data: PostgreSQL for users, photo metadata, and tags, with streaming replication to replicas and connection pooling through Pgbouncer. As data grew, they sharded Postgres into thousands of logical shards on a few machines with IDs that embed the shard (the “Sharding and 64-bit IDs” case earlier in this chapter explains the scheme).

  • Photos: stored in S3, served through CloudFront.

  • Redis for the main feed lists and session data; Memcached as a general cache.

  • Async work: Gearman queues for fanning a new photo out to followers’ feeds and for notifications, so posting stayed fast.

  • Search: Solr for geo-tagged search; monitoring with Munin, Pingdom, and Sentry.

Why it worked.

Every component was mature and well understood, chosen so a tiny team could run it. They kept the design simple (one monolithic Django app), moved anything slow to queues, and scaled the one hard part, the database, by sharding only when needed. Their stated principles were roughly: keep it simple, do not reinvent the wheel, and use proven technologies.

📚 Lesson

  • A monolith on boring, proven components can carry a product to tens of millions of users.

  • Push fan-out and notifications to background queues from day one.

  • Plan the ID and sharding scheme before you need it; it is the hardest thing to change later.

Case: Amazon Dynamo: The 2007 Paper

📋 Case facts

Domain: E-commerce key-value store
Scale: Shopping cart and session state for Amazon’s retail site at holiday peak
Concepts: Consistent hashing, sloppy quorums, hinted handoff, vector clocks, Merkle trees, gossip
Source: DeCandia et al., “Dynamo: Amazon’s Highly Available Key-value Store”, SOSP 2007

The requirement.

The shopping cart must always accept writes: a customer adding an item should never see an error, even during server failures or network partitions. Amazon chose availability over consistency (an AP system, Chapter (foundations)) and pushed conflict resolution to the application.

Dynamo’s ring and preference list.

The techniques

(each addresses one problem):

Problem Dynamo’s technique
Partitioning consistent hashing with virtual nodes for even load and smooth rebalancing
High write availability sloppy quorum: write to the first \(N\) healthy nodes, not strictly the owners
Temporary failures hinted handoff: a stand-in node keeps the write with a hint and returns it to the owner when it recovers
Conflicting versions vector clocks; on read, concurrent versions are returned to the application to merge (a cart merges by union, which can resurrect deleted items)
Permanent failures / divergence anti-entropy with Merkle trees: replicas compare hash trees of key ranges and sync only differing branches
Membership and failure detection gossip; no central coordinator
Tunable consistency per-application \((N, R, W)\); a common setting was \((3, 2, 2)\)

Dynamo vs DynamoDB.

The paper’s ideas inspired Cassandra, Riak, and Voldemort. Amazon DynamoDB (2012) shares the name but not the design: it uses leader-based replication with Multi-Paxos per partition, offers strongly consistent reads and transactions, and avoids exposing conflicting versions to applications (the 2022 DynamoDB case above). Dynamo’s operational burden on teams was part of why.

📚 Lesson

  • Choose consistency per use case; “always writable” is a valid business requirement.

  • Hinted handoff and anti-entropy separate handling of temporary and permanent failures.

  • Pushing conflict resolution to applications is powerful but costly for developers; managed systems later moved away from it.
