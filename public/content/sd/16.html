👋 Intro

Metrics, logs, and traces with OpenTelemetry; SLOs and error budgets; authentication and authorization (OAuth 2.x, OIDC, JWT); zero trust; secrets; and multi-tenant isolation.

Observability

🌱 Beginner

Monitoring tells you that the car’s engine light is on. Observability lets you figure out why, even for a problem nobody predicted, by looking at the dashboard gauges (metrics), the trip log (logs), and the route you took (traces).

OpenTelemetry as a vendor-neutral pipeline for the three signals.

🔧 Intermediate

  • Metrics: cheap numeric time series. Use RED for services (Rate, Errors, Duration) and USE for resources (Utilization, Saturation, Errors). Avoid high-cardinality labels (user IDs).

  • Logs: structured JSON with a trace_id on every line.

  • Traces: a tree of spans following one request across services, linked by W3C traceparent headers. Sample intelligently (keep all errors and slow requests, a percentage of the rest).

  • Profiles: continuous profiling (eBPF-based) is becoming the fourth signal.

OpenTelemetry (OTel) is the standard for instrumentation; it includes GenAI semantic conventions for recording model name, token counts, and latency on LLM spans.

🧠 Expert

SLOs and error budgets. An SLO of 99.9% successful requests over 30 days allows 0.1% failures: the error budget. Alert on burn rate, not raw errors: page if the budget burns 14.4\(\times\) faster than sustainable over 1 hour (2% of budget gone), ticket if 6\(\times\) over 6 hours. Multi-window burn-rate alerts catch both sudden and slow problems with few false pages. When the budget is exhausted, freeze risky launches and prioritize reliability. For LLM features add SLIs for TTFT, tokens/s, and quality (eval pass rate, user feedback).

Security Fundamentals

🔧 Intermediate

Authentication (who you are) vs authorization (what you can do).

  • OAuth 2.x: delegated authorization. Use Authorization Code with PKCE for web and mobile apps, Client Credentials for service-to-service. OAuth 2.1 consolidates current best practice and drops the implicit flow.

  • OIDC: identity layer on OAuth; issues an ID token.

  • JWT: signed tokens verified locally with the issuer’s public keys (JWKS). Keep them short-lived (5–15 min) with refresh tokens; validate iss, aud, exp, and the algorithm.

  • Passkeys (WebAuthn): phishing-resistant passwordless login, now mainstream.

  • Authorization models: RBAC (roles), ABAC (attributes), ReBAC (relationships, Google Zanzibar style: OpenFGA, SpiceDB). Policy engines: OPA, Cedar.

🧠 Expert

Zero trust: no implicit trust from network location. Every request carries a verifiable identity: users via SSO plus device posture; workloads via SPIFFE IDs and mTLS. Secrets: in a manager (Vault, AWS Secrets Manager), injected at runtime, rotated automatically; prefer workload identity federation over long-lived keys. Encryption: TLS in transit, KMS-managed keys at rest, envelope encryption for sensitive fields. Multi-tenancy: enforce tenant ID at the data layer (row-level security) not just the API; test for IDOR (changing an ID in the URL). Follow the OWASP Top 10, and for AI features the OWASP Top 10 for LLM Applications (prompt injection, sensitive data disclosure, excessive agency, and more; see Chapter (genai)).

Incident Response

🔧 Intermediate

  1. Detect: SLO burn-rate alerts and user reports, routed to an on-call rotation.

  2. Declare and assign roles: an incident commander coordinates (does not debug), a communications lead updates status pages and stakeholders, subject-matter experts investigate. A dedicated channel and a running timeline.

  3. Mitigate first, diagnose later: roll back the last deploy or config change, flip a feature flag, fail over, shed load, block abusive traffic. Restoring service matters more than understanding it in the moment.

  4. Resolve and verify with metrics, not hope.

  5. Blameless postmortem within days: timeline, impact, root and contributing causes, what went well, and action items with owners and dates. Part (cases)’s outage chapter shows real ones.

Severity levels (SEV1–SEV4) define who gets paged and how fast. Practice with game days.

Backups, Restore, and Disaster Recovery

🔧 Intermediate

RPO (recovery point objective): how much data you can lose. RTO (recovery time objective): how long you can be down.

  • Backups: full snapshots plus continuous WAL or binlog archiving gives point-in-time recovery to any second. Follow 3-2-1: three copies, two media, one off-site, and at least one immutable copy (object lock) that ransomware or a compromised admin cannot delete. Encrypt backups and restrict who can delete them.

  • Restore testing: automate regular restores into a scratch environment and verify the data; measure how long it takes. GitLab’s 2017 incident (Part (cases)) is what untested backups look like. Replication is not a backup: it faithfully replicates a DROP TABLE.

Disaster recovery strategies, from cheapest to fastest:

Strategy Setup Typical RTO
Backup and restore backups copied to another region; rebuild from scratch hours to days
Pilot light data replicated; minimal core services idle in the DR region tens of minutes to hours
Warm standby a scaled-down full copy running; scale up on failover minutes
Active-active (multi-region) full capacity serving in several regions seconds to minutes

Infrastructure as code makes rebuilding a region realistic; run failover drills.

Data Retention, Deletion, and Privacy

🔧 Intermediate

  • Retention policy per data type (logs 30 days, analytics events 13 months, invoices 7 years for tax), enforced automatically with TTLs, partition drops, and object lifecycle rules.

  • User deletion (GDPR’s right to erasure, CCPA): a deletion request fans out to every system holding the user’s data (primary databases, caches, search indexes, analytics, data lake, ML training sets, third-party processors) through a tracked workflow, completed within the legal deadline, with proof. Keep a data map of where personal data lives; without it, deletion is guesswork.

  • Backups: deleting from immutable backups is impractical; common approaches are short backup retention and re-applying deletions after any restore, or crypto-shredding: encrypt each user’s data with a per-user key and delete the key to make all copies unreadable.

  • Minimize: do not collect what you do not need; pseudonymize analytics; restrict access and log it; keep data in the required region (data residency).

Security and Abuse Prevention

🔧 Intermediate

Abuse (spam, fake accounts, scraping, credential stuffing, promo fraud) is a product-scale problem, not just a security one. Layers: edge defenses (WAF, bot detection, IP reputation, rate limits by IP, account, device, and API key; Chapter (gateway)); friction that scales with risk (CAPTCHA, phone or email verification, step-up authentication); risk scoring models on signups, logins, and transactions with features like device fingerprint, velocity, and graph links between accounts; review queues and enforcement actions (warn, limit, suspend) with appeals; and feedback loops so detection improves from confirmed cases. Measure prevalence and false-positive rates, since blocking legitimate users is also a cost.

📦 Use case: Debugging a latency spike

Burn-rate alert fires for checkout p99. The trace view shows 80% of time in a SELECT on the inventory DB; logs linked by trace_id show a new query plan after a deploy; the continuous profiler shows the same. Rollback via feature flag fixes it in minutes.

📦 Use case: B2B SaaS authorization

Users sign in through their company’s IdP (OIDC/SAML). The API gateway validates JWTs; services call OpenFGA to check “can user U edit document D” based on folder sharing relationships; Postgres row-level security ensures even a buggy query cannot read another tenant’s rows.

🔑 Takeaways

  • Instrument once with OpenTelemetry; correlate metrics, logs, and traces by trace ID.

  • Alert on SLO burn rate, not on every error.

  • Short-lived tokens, workload identity, and mTLS replace network trust.

  • Enforce tenant isolation in the data layer.
