👋 Intro

How LLM applications are built: tokens and context windows, prompt and context engineering, RAG pipelines, embeddings and vector search, agents and tool use (MCP, A2A), LLM gateways and model routing, guardrails and prompt-injection defense, evaluation, and cost control.

LLM Basics for System Designers

🌱 Beginner

A large language model is a very well-read autocomplete. Given some text, it predicts the next word piece (a token), adds it, and repeats. It only knows what it learned in training plus what you put in the prompt. It cannot look things up unless you give it tools, and it can sound confident while being wrong. Most GenAI system design is about feeding it the right information and checking what comes out.

🔧 Intermediate

Facts that shape architecture:

  • Tokens: about 4 characters or 0.75 English words each. Pricing, rate limits, and latency are all per token. Output tokens cost 3–5\(\times\) more than input and are generated one at a time.

  • Context window: the maximum tokens per request (input plus output), now commonly 128K to 1M+. Bigger contexts cost more, are slower, and models can miss details in the middle.

  • Stateless: the API remembers nothing between calls. Your system stores conversation history and re-sends what is relevant.

  • Non-deterministic: the same input can give different outputs. Systems need validation, retries, and evaluations instead of exact tests.

  • Latency: time-to-first-token (TTFT) plus output length \(\times\) time-per-output-token. Stream tokens to users.

  • Reasoning models spend extra “thinking” tokens before answering: better on hard problems, but slower and pricier. Many APIs let you set a thinking budget.

Prompt and Context Engineering

🔧 Intermediate

Prompt engineering is writing clear instructions: role, task, constraints, output format, and examples (few-shot). Context engineering is the broader systems problem: deciding which information goes into the limited context window on each call: system instructions, retrieved documents, conversation history (summarized when long), tool definitions, memory, and the user’s request.

Practical rules:

  • Put stable content first (system prompt, tool schemas, documents) so prompt caching applies; variable content last.

  • Ask for structured output (JSON Schema). Most providers and inference engines support constrained decoding that guarantees valid JSON.

  • Keep only what helps: irrelevant context lowers quality and raises cost.

  • Version prompts like code and gate changes with evals (Chapter (cicd)).

Retrieval-Augmented Generation (RAG)

🌱 Beginner

RAG is an open-book exam. Instead of hoping the model memorized your company handbook, you look up the relevant pages and hand them over with the question: “Answer using these pages.” Answers become current, specific, and citeable.

A production RAG pipeline: offline ingestion and online retrieval.

🔧 Intermediate

Ingestion: parse documents (layout-aware PDF parsing, tables, OCR), split into chunks of a few hundred tokens with overlap or along document structure (headings, sections), attach metadata (source, date, ACLs, tenant), embed each chunk, and store in a vector index alongside a keyword (BM25) index.

Retrieval: rewrite the user’s question (resolve “it” from conversation, expand acronyms), run hybrid search (vector plus BM25, merged with reciprocal rank fusion), filter by metadata and permissions, then rerank the top 50–100 with a cross-encoder to pick the best 5–10.

Generation: prompt the model to answer only from the provided context and cite sources; say “I don’t know” when the context is insufficient.

🧠 Expert

Where RAG fails and the fixes:

  • Bad chunks (a table split in half): structure-aware chunking; contextual retrieval (prepend an LLM-written summary of the parent document to each chunk before embedding); parent-document retrieval (match small chunks, return the larger section).

  • Vocabulary mismatch: hybrid search; HyDE (embed a hypothetical answer).

  • Multi-hop questions: agentic RAG, where the model issues several searches iteratively; GraphRAG, which extracts an entity graph for questions about relationships and global themes.

  • Stale or unauthorized results: incremental re-indexing via CDC; enforce document ACLs at query time, never only at ingestion.

  • Long context vs RAG: with 1M-token windows you can sometimes skip retrieval for small corpora, using prompt caching to keep it affordable. RAG still wins on cost, latency, freshness, and access control for large or changing corpora.

Measure retrieval separately from generation: recall@k and MRR for retrieval; faithfulness (is the answer supported by context?) and answer relevance for generation (RAGAS-style metrics).

Embeddings and Vector Search

🔧 Intermediate

An embedding model turns text (or images) into a vector, typically 256–3,072 dimensions, where similar meaning means nearby vectors (cosine similarity). Matryoshka embeddings can be truncated to fewer dimensions with small quality loss, saving storage. Index choices are covered in Chapter (data) (HNSW, IVF, DiskANN, quantization). Rule of thumb: 10M chunks \(\times\) 1,024 dims \(\times\) 4 bytes \(\approx\) 41 GB of raw vectors, before index overhead; binary or int8 quantization cuts this 4–32\(\times\), with a rescoring pass to recover accuracy.

📦 Use case: Enterprise knowledge assistant

Employees ask questions across Confluence, Google Drive, and Jira. Connectors sync changes hourly; chunks carry the source’s ACL group list; search filters by the asking user’s groups. Answers include links to sources. Hit rate and “thumbs down” rates are tracked per data source to find poor ingestion.

Agents and Tool Use

🌱 Beginner

A chatbot answers. An agent does. Give the model a set of tools (search the web, query a database, send an email) and let it decide, step by step, which tool to use until the task is done, like an intern with a to-do list and access to a few apps.

The agent loop (ReAct style): reason, act, observe, repeat.

🔧 Intermediate

Tool calling: you describe tools with JSON Schemas; the model returns a structured call; your code executes it and returns the result. The model never executes anything directly.

Protocols:

  • Model Context Protocol (MCP): an open standard (introduced by Anthropic, now broadly adopted across vendors and IDEs) for connecting models to tools, data sources, and prompts through MCP servers. Write a tool integration once, use it from any MCP-compatible client.

  • Agent-to-Agent (A2A): an open protocol (started by Google, now under the Linux Foundation) for agents built by different vendors to discover each other’s capabilities and delegate tasks.

Patterns, simplest first: prompt chaining (fixed steps), routing (classify then dispatch), parallelization (fan out and merge), orchestrator-workers (a lead agent spawns sub-agents), evaluator-optimizer (one model drafts, another critiques). Start with a fixed workflow and only add autonomy where the task actually needs it.

Memory: short-term (the conversation, summarized as it grows) and long-term (facts and preferences saved to a store and retrieved later).

🧠 Expert

Production agents are distributed systems with an unreliable planner:

  • Durability: run long tasks in a durable workflow engine (Chapter (dtx)) so crashes resume from the last step, not from scratch.

  • Idempotent tools: the model may call the same tool twice; tools with side effects need idempotency keys.

  • Budgets: cap steps, tokens, wall time, and dollars per task.

  • Least privilege: scoped, short-lived credentials per tool; read-only by default; human approval for irreversible actions (payments, deletes, external emails).

  • Sandboxing: code execution and browser use in isolated microVMs or containers with no access to internal networks or secrets.

  • Observability: trace every step (prompt, tool call, result, tokens) so you can replay and debug failed runs.

  • Context management: long runs overflow the window; compact history, store intermediate results in files or memory, and give sub-agents clean, focused contexts.

📦 Use case: Customer support agent

Tools: lookup_order, issue_refund (requires approval above $100), search_kb, escalate_to_human. Routing sends simple FAQ questions to a small fast model and complex cases to a larger one. Every conversation is traced and a sample is scored daily by an LLM judge for correctness and policy compliance.

📦 Use case: Coding agent

The agent reads the repository, edits files, and runs tests inside a sandboxed container per task. Its loop ends when tests pass or the step budget is spent. Output is a pull request reviewed by a human, never a direct push to main.

LLM Gateways and Model Routing

🔧 Intermediate

An LLM gateway is an API gateway specialized for models (LiteLLM, Portkey, Kong AI Gateway, Envoy AI Gateway, cloud offerings). It provides one API across providers, per-team keys and token budgets, provider failover, retries with backoff, response and semantic caching, PII redaction, request logging, and cost attribution.

Model routing sends each request to the cheapest model that can handle it: a classifier or rules decide small vs large model, or a cascade tries the small model first and escalates when confidence is low. Typical savings are large, because most traffic is easy.

Guardrails and Safety

Guardrails around the model.

🧠 Expert

Prompt injection is the top LLM security risk: instructions hidden in retrieved documents, web pages, emails, or tool results that the model obeys. There is no complete fix at the model level, so design as if the model can be hijacked:

  • Treat all retrieved and tool content as untrusted data, clearly delimited.

  • Apply least privilege: an agent that reads untrusted email should not also hold credentials to send money. Avoid combining (1) access to private data, (2) exposure to untrusted content, and (3) ability to send data out.

  • Require human confirmation for sensitive actions; validate tool arguments in code, not in the prompt.

  • Use classifier models (e.g. Llama Guard style safety models, injection detectors) as extra layers, not the only layer.

  • Block data exfiltration paths such as auto-rendered images and links to unknown domains.

Other risks from the OWASP Top 10 for LLM Applications: sensitive information disclosure, supply chain (untrusted model weights), excessive agency, system prompt leakage, vector store poisoning, misinformation, and unbounded consumption (cost attacks).

Evaluation and LLMOps

🔧 Intermediate

You cannot improve what you do not measure, and LLM output cannot be checked with assertEqual.

  • Offline evals: a golden dataset of inputs with expected outputs or rubrics. Score with code (exact match, JSON validity, unit tests), LLM-as-judge (calibrated against human labels), and human review.

  • Online evals: user feedback, task success, escalation rate, A/B tests, and sampled LLM-judge scores on live traffic.

  • Tracing: Langfuse, LangSmith, Arize Phoenix, Braintrust, or OpenTelemetry GenAI conventions.

Deep Dive: Building RAG That Works

🔧 Intermediate

Hybrid search with Reciprocal Rank Fusion. Vector search finds paraphrases; BM25 finds exact terms (error codes, product names, people). Merge their ranked lists with RRF, which needs no score normalization: \[\text{RRF}(d) = \sum_{r \in \text{rankers}} \frac{1}{k + \text{rank}_r(d)}, \quad k \approx 60\] A document ranked 1st by BM25 and 10th by vectors scores \(1/61 + 1/70\), beating one ranked 5th by only one list.

Chunk sizing. Too small and chunks lose context (“it increased by 20%” with no subject); too large and the embedding blurs several topics and wastes context. Start around 300–800 tokens following document structure, with 10–20% overlap, and tune on your eval set.

Context budget. With a 16K budget: system prompt 1K, conversation summary 1K, retrieved chunks 8 \(\times\) 600 = 4.8K, user question 0.2K, reserved output 2K. Stuffing 50 chunks rarely helps; models miss details in the middle of long contexts, and cost scales with every token.

def answer(question, user, history):
    q = rewrite_query(question, history)              # resolve "it", acronyms
    vec = vector_index.search(embed(q), k=50, filter={"acl": user.groups})
    kw  = bm25_index.search(q, k=50, filter={"acl": user.groups})
    candidates = rrf_merge(vec, kw)[:60]
    top = reranker.rank(q, candidates)[:8]            # cross-encoder
    if top[0].score < MIN_RELEVANCE:
        return "I couldn't find this in the knowledge base."
    prompt = build_prompt(SYSTEM, history_summary(history), top, question)
    resp = llm.generate(prompt, max_tokens=800, stream=True)
    log_trace(q, [c.id for c in top], resp)           # for evals and debugging
    return with_citations(resp, top)
🧠 Expert

Evaluation set design. Build 200–500 real questions from logs, each labeled with the documents that answer it. Measure retrieval recall@8 (is the right document in the context?) separately from answer faithfulness and correctness. Most quality problems show up as retrieval misses; fixing chunking and adding hybrid search usually beats changing the model. Re-run the set on every change to chunking, embeddings, prompts, or models (Chapter (cicd)).

Freshness. Use CDC or webhooks from sources to re-embed changed documents, keep a doc_version, and delete stale chunks. Re-embedding the whole corpus when changing embedding models is a large batch job; plan for dual indexes during the switch.

Deep Dive: An Agent Loop With Guardrails

def run_agent(task, tools, max_steps=15, max_cost=2.00):
    messages = [system_prompt(tools), user(task)]
    cost = 0.0
    for step in range(max_steps):
        resp = llm.chat(messages, tools=tool_schemas(tools))
        cost += resp.cost
        if cost > max_cost:
            return fail("budget exceeded")
        if not resp.tool_calls:
            return resp.text                          # final answer
        for call in resp.tool_calls:
            tool = tools[call.name]
            args = tool.validate(call.args)           # schema + business rules in code
            if tool.risky and not human_approves(call):
                result = "Action rejected by user."
            else:
                key = f"{task.id}:{step}:{call.name}" # idempotency key
                result = tool.run(args, idempotency_key=key, timeout=30)
            messages += [resp.as_message(), tool_result(call.id, truncate(result))]
    return fail("step limit reached")

Fine-Tuning vs RAG vs Prompting

Approach Best for Not for
Prompting Most tasks; fast iteration Large private knowledge
RAG Private, changing, citeable knowledge Teaching a new style or format
Fine-tuning (LoRA/QLoRA) Consistent format, tone, domain tasks; distilling a big model into a small one Adding fast-changing facts
Preference tuning (DPO, RL) Aligning behavior with feedback Small teams without eval infrastructure

Cost Engineering

🔧 Intermediate

Monthly cost \(\approx\) requests \(\times\) (input tokens \(\times\) input price \(+\) output tokens \(\times\) output price). Example: 1M requests/month, 3,000 input and 400 output tokens, at $3 and $15 per million tokens: \(1\text{M}\times(3{,}000\times 3 + 400\times 15)/10^6 = \$15{,}000\)/month. Levers: prompt caching (often the largest), shorter prompts, model routing, batch APIs (about 50% off for non-urgent work), output length limits, semantic caching, and self-hosting open-weight models at high, steady volume.

🔑 Takeaways

  • LLMs are stateless, probabilistic, and token-priced; design around those facts.

  • RAG quality is mostly retrieval quality: hybrid search plus reranking plus good chunks.

  • Agents need durability, budgets, least privilege, sandboxes, and tracing.

  • Assume prompt injection will happen; limit what a hijacked model can do.

  • Evals are the test suite of AI systems; gate every change on them.
