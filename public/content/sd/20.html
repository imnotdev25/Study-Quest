👋 Intro

Four end-to-end designs using the six-step framework from Chapter (foundations): a URL shortener (beginner), a real-time chat system (intermediate), a social news feed (intermediate), and a multi-tenant LLM platform with RAG (expert).

URL Shortener (Beginner)

Requirements.

Create short links, redirect fast, optional expiry and custom alias, click analytics. 100M new links/month, 10:1 read:write. Redirects must be fast and highly available.

Estimates.

Writes \(\approx 100\text{M}/(30\times10^5) \approx 40\)/s; reads \(\approx 400\)/s average, a few thousand at peak. 5 years \(\times\) 1.2B links \(\times\) 500 bytes \(\approx\) 3 TB. A 7-character base62 code gives \(62^7 \approx 3.5\times10^{12}\) combinations: plenty.

API.

POST /v1/links {url, alias?, expires_at?} \(\to\) {code}; GET /{code} \(\to\) 301/302 Location.

URL shortener architecture.

Deep dives.

  • Code generation: hashing the URL causes collisions; a counter encoded in base62 is collision-free. Each write server leases a block of 1,000 IDs from a coordinator (or a DB sequence), so there is no per-write coordination. Shuffle the bits if codes should not be guessable.

  • 301 vs 302: 301 is cached by browsers (less load, fewer analytics events); 302 sends every click through you.

  • Read path: cache-aside in Redis; hot links cached at the CDN. Analytics are async so redirects never wait on them.

  • Abuse: rate-limit creation per user/IP; scan destination URLs against malware lists.

Real-Time Chat (Intermediate)

Requirements.

1:1 and group chat (up to 500 members), online presence, delivery and read receipts, history sync across devices, push notifications. 50M DAU, 40 messages/user/day.

Estimates.

\(50\text{M}\times40/10^5 = 20\)K messages/s average, \(\sim\)60K peak. At 200 bytes, \(\sim\)400 GB/day of messages. 10–20M concurrent WebSocket connections; at 50K connections per gateway node, about 300–400 nodes.

Chat architecture: stateful gateways, stateless message service.

Deep dives.

  • Storage: partition by conversation_id, cluster by message ID (a time-sortable Snowflake-style ID), so loading a chat is one partition range scan.

  • Ordering and dedup: the client sends a client_msg_id (idempotency key); the server assigns a per-conversation sequence number. Clients sync by asking for messages after their last sequence number.

  • Delivery guarantees: at-least-once to devices with client-side dedup; receipts are just more messages.

  • Groups: fan-out on write to members’ gateways for small groups; very large channels fan-out on read.

  • Presence: heartbeats every 30 s with TTL keys; publish changes only to contacts currently online, batched, to avoid presence storms.

  • Gateway deploys: drain connections gradually; clients reconnect with jittered backoff and resync.

Social News Feed (Intermediate)

Requirements.

Users post; followers see a ranked feed; 300M DAU; average 200 follows; some accounts have 100M followers. Feed load p99 under 300 ms.

Hybrid fan-out: push for normal accounts, pull for celebrities.

Deep dives.

  • Fan-out on write (push to followers’ feed caches) makes reads fast but a 100M-follower post means 100M writes. Fan-out on read is cheap to write but slow to read. Use the hybrid: push for most users, pull and merge for accounts above a follower threshold.

  • Ranking: candidate generation (followed posts plus recommendations from embeddings) then a ranking model scoring engagement; keep feature lookups in a low-latency feature store.

  • Cache sizing: keep the latest 500 post IDs per active user (8 bytes each): 300M \(\times\) 4 KB \(\approx\) 1.2 TB across a Redis cluster.

  • Degradation: if ranking times out, serve chronological from cache.

Multi-Tenant LLM Platform with RAG (Expert)

Requirements.

An internal platform letting 200 product teams build AI features: chat over company documents, agents with tools, batch summarization. Must enforce document permissions, per-team budgets, provider failover, and audit logging. 5M requests/day, average 6K input / 500 output tokens; mix of hosted frontier models and self-hosted open models.

Estimates.

\(5\text{M}/10^5 = 50\) req/s average, \(\sim\)200 peak. Tokens/day: 30B input, 2.5B output. With 70% of input served from prompt or prefix cache and 60% of requests routed to a small model, cost falls by well over half versus sending everything uncached to the largest model. Concurrency by Little’s Law: 200 req/s \(\times\) 8 s average duration \(\approx\) 1,600 in-flight streams.

Multi-tenant LLM platform.

Deep dives.

  • Gateway: OpenAI-compatible API; per-team virtual keys; token budgets (ITPM/OTPM) enforced with a distributed token bucket; reserve max_tokens and refund after completion. Retries with full-jitter backoff, a circuit breaker per provider and model, and failover to an equivalent model. Every request carries a trace ID and team ID for cost attribution.

  • Routing: a lightweight classifier picks model tier; teams can pin models for reproducibility. Stable prompt prefixes are encouraged so provider prompt caching and self-hosted prefix caching hit.

  • Self-hosted serving: vLLM or SGLang behind KV-cache-aware routing (prefix affinity plus least-KV-usage); autoscale on waiting requests; FP8 weights and KV; chunked prefill for long RAG prompts; disaggregated prefill only if TTFT SLOs are missed at scale.

  • RAG with permissions: ingestion via connectors and CDC; every chunk stores tenant and ACL groups; retrieval filters by the caller’s identity at query time; hybrid search plus reranking; answers cite sources.

  • Agents: run in a durable workflow engine; tools exposed as MCP servers with scoped credentials; side-effecting tools require idempotency keys and human approval above thresholds; code execution in microVM sandboxes.

  • Safety: input and output guardrails (PII redaction, injection detection, policy classifiers); retrieved content treated as untrusted.

  • Quality: each team registers an eval set; prompt or model changes are gated in CI; online LLM-judge sampling and user feedback dashboards.

  • Failure modes: provider outage (failover, degrade to smaller model), GPU node loss (replicas across zones), vector DB slowness (timeout and answer without retrieval with a disclaimer, or fail clearly), runaway agent (step and spend caps).

🔑 Takeaways

  • Every design repeats the same moves: estimate, find the pressure, apply a building block.

  • Read-heavy systems lean on caching and CDNs; write-heavy ones on partitioning and queues.

  • Hybrid strategies (push plus pull, small plus large model) handle skewed real-world load.

  • AI platforms are classic distributed systems with new resources: tokens, KV cache, and GPUs.
