👋 Intro

Asynchronous communication: queues vs pub/sub, Kafka’s log model, delivery guarantees, ordering, dead-letter queues, event-driven architecture, event sourcing, CQRS, the outbox pattern, and change data capture.

Why Asynchronous?

🌱 Beginner

Calling someone on the phone is synchronous: both of you must be free at the same time. Sending a text is asynchronous: you send it, carry on, and they reply when ready. Message queues are text messages between services. If the receiver is busy or down, the message waits instead of being lost.

Benefits: decoupling (producer does not know the consumer), load leveling (absorb spikes), resilience (consumer outages do not fail the user’s request), and fan-out (many consumers react to one event).

Message Queues (Point-to-Point)

Competing consumers: each message goes to exactly one worker. Poison messages land in a dead-letter queue.

🔧 Intermediate

Key mechanics:

  • Acknowledgement: the consumer acks after processing. No ack within the visibility timeout means redelivery.

  • Dead-letter queue (DLQ): messages that fail \(N\) times are moved aside for inspection rather than blocking the queue.

  • Delivery guarantees: at-most-once (ack before processing, may lose), at-least-once (ack after, may duplicate; the common default), and effectively-once (at-least-once plus idempotent consumers).

  • Ordering: standard SQS is best-effort; SQS FIFO and Kafka partitions give order per group/key.

  • Backpressure: queue depth is the signal for autoscaling workers (KEDA in Kubernetes).

Products: RabbitMQ (rich routing, AMQP), Amazon SQS (fully managed), Azure Service Bus, NATS JetStream, Redis Streams, and job frameworks like Celery, Sidekiq, BullMQ.

📦 Use case: Image processing pipeline

User uploads a photo to S3; the API enqueues {photo_id} and returns 202 Accepted. Workers generate thumbnails, run moderation, extract EXIF, and update the DB. Upload latency stays at 100 ms regardless of processing time, and workers scale with queue depth.

Pub/Sub and Kafka

🌱 Beginner

A queue is a to-do list shared by workers: each task is done once. Pub/sub is a newspaper: every subscriber gets their own copy of each edition.

Kafka topic with three partitions. Every consumer group reads all messages; within a group each partition goes to one consumer.

🔧 Intermediate

Kafka’s model: a topic is split into partitions, each an ordered, append-only, replicated log. Producers choose a partition by key hash, so all events for one key stay in order. A consumer group divides partitions among its members; each group tracks its own offset, so groups are independent and can replay history. Messages are retained by time or size, not deleted on read. Parallelism within a group is capped by the partition count.

Comparable systems: Redpanda (Kafka API, C++, no JVM), Apache Pulsar (tiered storage, multi-tenancy), AWS Kinesis, Google Pub/Sub, Azure Event Hubs, NATS. Kafka 4.0 removed ZooKeeper in favor of built-in KRaft consensus, and Kafka-compatible “diskless” designs (WarpStream, Confluent Freight, AutoMQ, KIP-1150) write directly to object storage to cut cross-zone network cost.

🧠 Expert

Exactly-once in Kafka = idempotent producer (sequence numbers per partition dedupe retries) + transactions (atomic writes across partitions and offset commits). This gives exactly-once for Kafka-to-Kafka stream processing. Side effects outside Kafka (sending email, charging a card) still require idempotent consumers.

Partition sizing: target throughput / per-partition throughput, with headroom; increasing partitions later breaks key-to-partition mapping and ordering guarantees. Rebalancing pauses consumption; use cooperative sticky assignment and static membership. Consumer lag (latest offset minus committed offset) is the key health metric. Hot partitions from skewed keys: add a salt suffix for heavy keys and re-aggregate downstream.

Event-Driven Architecture

Producers publish facts; consumers subscribe. New consumers are added without changing the producer.

🔧 Intermediate

Events are immutable facts in past tense (OrderPlaced, PaymentFailed). Two styles:

  • Event notification: thin event (order_id); consumers call back for details.

  • Event-carried state transfer: fat event with full data; consumers keep local copies.

Use a schema registry (Avro, Protobuf, JSON Schema) and enforce backward compatibility so producers can evolve without breaking consumers. Standard envelopes like CloudEvents help across teams.

The Outbox Pattern and CDC

Transactional outbox: the event is written in the same transaction as the business data, then relayed.

🧠 Expert

The dual-write problem: writing to the DB and then publishing to Kafka can fail between the two steps, leaving them inconsistent. The transactional outbox writes the event to an outbox table in the same DB transaction; a relay (polling or CDC on the write-ahead log) publishes it. This guarantees at-least-once publication, so consumers must still be idempotent. Change data capture (Debezium, DynamoDB Streams, Postgres logical replication) also feeds caches, search indexes, and data warehouses from one source of truth.

Event sourcing stores the sequence of events as the source of truth; current state is a fold over events. Gains: full audit history, time travel, rebuildable projections. Costs: schema evolution of old events, snapshotting for long streams, and a steep learning curve. CQRS separates write models (normalized, validated) from read models (denormalized projections per query), often fed by events. Accept that read models are eventually consistent.

📦 Use case: E-commerce order flow

OrderPlaced is published via outbox. Inventory reserves stock, Payments charges the card, Notifications emails the customer, and Analytics streams to the warehouse, all independently. Adding a loyalty-points service later requires zero changes to the order service.

📦 Use case: Ride sharing location updates

Driver apps publish GPS pings every 4 seconds to a partitioned stream keyed by driver_id. A matching service consumes them to update a geospatial index; an ETA service and a surge-pricing service consume the same stream independently.

⚠️ Pitfall

  • Assuming exactly-once delivery; design every consumer to be idempotent.

  • Using a queue to hide a synchronous dependency the user is waiting on.

  • No DLQ or alerting on it, so failures pile up silently.

  • Event spaghetti: nobody can explain the full flow. Document flows and use tracing across async hops.

Deep Dive: Inside Kafka’s Durability Guarantees

A partition’s replicas. Offsets beyond the high watermark are not yet visible to consumers.

🔧 Intermediate

  • Each partition has one leader and several followers that copy its log. Followers caught up within replica.lag.time.max.ms form the in-sync replica set (ISR).

  • The high watermark is the highest offset copied to every ISR member. Consumers only see messages below it, so they never read data that could vanish on leader failover.

  • Producer acks: 0 (fire and forget), 1 (leader wrote it; lost if the leader dies before followers copy it), all (every ISR member has it).

  • min.insync.replicas=2 with acks=all and replication factor 3 is the standard durable setup: a write succeeds only if at least two replicas have it; you can lose one broker with no data loss and keep writing.

🧠 Expert

Unclean leader election. If every ISR member is down, Kafka can either wait (unavailable) or elect an out-of-sync replica (available, but loses the messages it never received). unclean.leader.election.enable=false chooses consistency, the CAP trade-off in a single config flag.

Ordering with retries. A producer sends batches 1 and 2; batch 1 fails and is retried after batch 2 lands, so order flips. The idempotent producer (default in modern clients) tags batches with a producer ID and sequence numbers, letting the broker reject duplicates and keep order with up to 5 in-flight requests.

Consumer commit semantics. Commit offsets after processing for at-least-once. If processing writes to a database, store the offset in the same database transaction as the result; on restart, resume from the stored offset, which gives effectively-once without Kafka transactions.

Sizing example. 200K events/s at 1 KB = 200 MB/s in. Replication factor 3 means 600 MB/s of disk writes across the cluster, plus each consumer group reads 200 MB/s. Three consumer groups read 600 MB/s. At roughly 10 MB/s comfortable per partition, you need at least 20 partitions for the producer side; choose 64 or more to allow consumer parallelism and growth. Seven days retention is \(200\,\text{MB/s}\times 604{,}800\times 3 \approx 363\) TB of disk, which is why tiered storage to S3 became standard.

Deep Dive: Work Queues, Schedulers, and Rule Engines

Delegation and Async Work

🔧 Intermediate

Move work off the request path when the user does not need to wait for it: sending email, generating thumbnails, recomputing recommendations, calling slow third parties. The request records the intent durably (a row, an outbox event, a queue message) and returns 202 Accepted with a status URL or later notification. Rule of thumb: if it can be retried, can take more than a few hundred milliseconds, or can fail independently, delegate it.

A Postgres SKIP LOCKED Work Queue

CREATE TABLE jobs (
  id          BIGSERIAL PRIMARY KEY,
  kind        TEXT NOT NULL,
  payload     JSONB NOT NULL,
  run_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  attempts    INT NOT NULL DEFAULT 0,
  status      TEXT NOT NULL DEFAULT 'queued',   -- queued | running | done | failed
  locked_until TIMESTAMPTZ
);
CREATE INDEX jobs_ready ON jobs (run_at) WHERE status = 'queued';

-- each worker claims a batch without blocking other workers
UPDATE jobs SET status = 'running', attempts = attempts + 1,
                locked_until = now() + interval '5 minutes'
WHERE id IN (
  SELECT id FROM jobs
  WHERE status = 'queued' AND run_at <= now()
  ORDER BY run_at
  LIMIT 10
  FOR UPDATE SKIP LOCKED
)
RETURNING id, kind, payload;
🔧 Intermediate

FOR UPDATE SKIP LOCKED lets many workers poll concurrently: each locks different rows and skips rows another worker already locked, without waiting. Advantages over a separate broker: jobs can be enqueued in the same transaction as the business change (no dual write, like an outbox), you get SQL for inspection and retries, and there is one less system to run. Workers mark jobs done or reschedule with exponential backoff (run_at = now() + 2^attempts seconds) and move them to failed after a limit; a reaper resets running jobs whose locked_until passed (crashed workers). Libraries: GoodJob and Solid Queue (Ruby), Oban (Elixir), pg-boss and Graphile Worker (Node), River (Go). Limits: thousands of jobs per second is fine; much more, or fan-out to many consumers, belongs in a dedicated queue or log.

A Distributed Task Scheduler

🔧 Intermediate

“Run this job at 9:00 every day” or “in 30 minutes” for millions of tasks. Design: store tasks with next_run_at in a database indexed on that column, partitioned (by task ID hash) across scheduler instances so each partition has one owner (leases or a leader per partition, Chapter (dtx)). Each owner repeatedly claims due tasks (next_run_at <= now()), enqueues them to a work queue for executors, and computes the next run time from the cron expression. Guarantees: at-least-once execution, so jobs must be idempotent (key by task ID plus scheduled time); handle missed runs after an outage with a policy (run once, run all, skip). For precise short delays, hierarchical timing wheels (used by Kafka and Netty) hold timers in buckets by expiry for \(O(1)\) insert. Workflow engines (Temporal, Airflow) add dependencies, retries, and history.

DAG Workflow Orchestration

🔧 Intermediate

Multi-step pipelines (ETL, ML training, media processing) are DAGs of tasks. An orchestrator (Airflow, Dagster, Prefect, Argo Workflows, Temporal) stores the DAG and each run’s state, starts tasks whose dependencies succeeded (topological order), retries failures, supports backfills over past dates, and records lineage. Design tasks to be idempotent and to write outputs atomically (to a temporary location, then rename) so a retried task cannot leave partial results.

Rule Engines and Trigger Frameworks

🔧 Intermediate

Many products let users or operators define “when X happens, if condition Y, do Z”: automation in Zapier or Slack workflows, fraud rules, alerting, marketing journeys. Architecture: events arrive on a stream; a matcher finds rules subscribed to that event type (index rules by event type and by the fields they test, so each event is checked against few rules); a condition evaluator runs a safe, sandboxed expression language (not arbitrary code) with timeouts; actions are enqueued as idempotent jobs. Concerns: rule loops (an action triggers the same rule; cap depth), per-tenant rate limits, versioning rules (evaluate events against the version active at event time), testing rules against historical events before enabling, and audit logs of every firing. Classic rule engines (Drools) use the Rete algorithm to share partial condition matches across many rules.

Deep Dive: Choosing Queue, Log, or Stream

Need Queue (SQS, RabbitMQ) Log (Kafka, Pulsar, Kinesis) Workflow engine (Temporal)
Per-message ack and redelivery native by offset only per activity
Replay history no yes workflow history
Many independent consumers needs fan-out (SNS) native no
Ordering FIFO variants per partition per workflow
Delays, timers, long waits limited poor native (days, months)
Best for background jobs event streams, CDC, analytics multi-step business processes
🔑 Takeaways

  • Queues distribute work; pub/sub broadcasts facts; Kafka does both with replay.

  • Order is guaranteed per partition key, not globally.

  • At-least-once plus idempotency is the practical “exactly once.”

  • Use the outbox pattern or CDC to avoid dual writes.
