👋 Intro

Continuous integration and delivery pipelines, deployment strategies (rolling, blue/green, canary, feature flags), GitOps, infrastructure as code, software supply-chain security, and CI/CD for ML and LLM applications.

🌱 Beginner

In a car factory, every part is checked as it is added, not at the end. Continuous Integration checks every code change automatically. Continuous Delivery means the car is always ready to drive off the line. Continuous Deployment means it drives off automatically once it passes inspection.

A typical CI/CD pipeline.

Continuous Integration

🔧 Intermediate

Everyone merges small changes to the main branch at least daily (trunk-based development). Each push runs: build, lint, unit tests, static analysis (SAST), dependency scanning (SCA), secret scanning, and container image build. Keep CI under 10 minutes using caching, test parallelization, and running only affected targets in monorepos (Bazel, Nx, Turborepo). Tools: GitHub Actions, GitLab CI, Jenkins, Buildkite, CircleCI.

Deployment Strategies

Canary release with automated analysis.

Strategy How Trade-off
Recreate Stop all v1, start v2 Downtime; simplest
Rolling Replace instances gradually No extra capacity; mixed versions during rollout
Blue/green Full v2 environment; switch traffic at once Instant rollback; double capacity
Canary Small percentage to v2, watch metrics, expand Limits blast radius; needs good metrics
Feature flags Ship code dark; enable per user/segment Decouples deploy from release; flag debt
Shadow Mirror traffic to v2, discard responses Zero user risk; side effects must be disabled

Deployment strategies

🧠 Expert

Database migrations are the hard part. Use expand/contract: (1) add the new column, (2) deploy code that writes both, (3) backfill, (4) switch reads, (5) stop writing old, (6) drop old. Every step is backward compatible so any deploy can be rolled back. Progressive delivery tools (Argo Rollouts, Flagger) automate canary analysis against Prometheus metrics. Feature-flag platforms (LaunchDarkly, Unleash, OpenFeature standard) also act as kill switches during incidents. Large companies deploy region by region with bake times between waves, so a bad change never reaches every region at once.

GitOps and Infrastructure as Code

GitOps: Git is the single source of truth; an agent in the cluster pulls and reconciles.

🔧 Intermediate

Infrastructure as Code (IaC) defines cloud resources in versioned files: Terraform / OpenTofu (HCL, multi-cloud), Pulumi (general-purpose languages), AWS CDK, Crossplane (Kubernetes-native). Run plan in CI on every PR, require review, and apply from the pipeline, not laptops. Store state remotely with locking. GitOps extends this: Argo CD or Flux pull from Git and continuously reconcile, so the cluster self-heals from manual drift and every change is auditable. Platform engineering teams package these into internal developer platforms (Backstage) with golden paths.

Supply-Chain Security

🧠 Expert

Attacks such as SolarWinds, Codecov, and the 2024 xz backdoor target the build pipeline itself. Defenses: pinned dependencies with lockfiles, pinned CI actions by commit SHA, short-lived OIDC credentials from CI to cloud (no stored keys), SBOM generation (Syft), artifact signing and verification at admission (Sigstore cosign plus Kyverno or policy controllers), and build provenance at SLSA level 3. Treat AI-generated code like any other contribution: review, test, and scan it.

CI/CD for ML and LLM Applications

🆕 New in 2026

LLM features change behavior through prompts, models, retrieval data, and tools, not only code. Treat all of them as versioned artifacts:

  • Eval gates in CI: run a golden dataset through the new prompt or model; block merge if quality scores (LLM-as-judge, exact match, groundedness) drop below threshold.

  • Prompt registry with versions and rollback.

  • Model rollout via canary or shadow traffic, comparing quality, latency, and cost per request.

  • Model registry (MLflow, cloud registries) for fine-tuned weights; weights are large artifacts pulled at startup, so pre-stage them on nodes or use streaming loaders to cut cold starts.

📦 Use case: SaaS team shipping 50 times a day

Trunk-based development, 8-minute CI, every merge auto-deploys to staging and then to a 5% canary. Argo Rollouts promotes after 10 minutes if error rate and p99 are within bounds. Risky features ship behind flags and are enabled for internal users first.

📦 Use case: Regulated bank

Same pipeline with added gates: change tickets created automatically, two-person review, signed artifacts, SBOMs archived for auditors, blue/green deploys during approved windows with instant switch-back.

📦 Use case: Updating a RAG chatbot prompt

A prompt change is a PR. CI runs 500 eval questions; groundedness drops 4%, so the merge is blocked. After a fix, the new prompt rolls out to 10% of conversations with thumbs-up rate and escalation rate monitored.

🔑 Takeaways

  • Small, frequent, automated changes are safer than large, rare ones.

  • Canary plus automatic rollback limits blast radius; flags decouple deploy from release.

  • Git as source of truth for apps and infrastructure gives audit and self-healing.

  • Secure the pipeline itself; for AI apps, add evals as merge gates.
