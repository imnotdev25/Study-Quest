👋 Intro

Where caches live, the five caching patterns, eviction policies, invalidation strategies, stampede and hot-key problems, and caching for AI (semantic, prompt, and KV caches).

🌱 Beginner

You keep a water bottle on your desk instead of walking to the kitchen every time you are thirsty. A cache is that bottle: a small, fast store of things you use often. When it is empty (a miss), you walk to the kitchen (the database) and refill it.

Where Caches Live

The cache hierarchy

Caching Patterns

Cache-aside (lazy loading): the application manages the cache.

Pattern How it works When to use
Cache-aside App reads cache, on miss reads DB and fills cache Default; read-heavy; tolerant of brief staleness
Read-through Cache library loads from DB on miss Same as above, cleaner code
Write-through Write cache and DB synchronously Data must be read immediately after write
Write-back (behind) Write cache; flush to DB asynchronously Write-heavy counters, metrics; risk of loss
Write-around Write DB only; cache filled on read Data written often but rarely read

Caching patterns

def get_product(pid):
    key = f"product:{pid}"
    val = redis.get(key)
    if val is not None:
        return deserialize(val)
    # Only one caller rebuilds; others briefly wait or serve stale
    if redis.set(f"lock:{key}", 1, nx=True, ex=5):
        try:
            row = db.query("SELECT * FROM products WHERE id = %s", (pid,))
            ttl = 300 + random.randint(0, 60)          # jitter avoids sync expiry
            redis.set(key, serialize(row), ex=ttl)
            return row
        finally:
            redis.delete(f"lock:{key}")
    time.sleep(0.05)
    return get_product(pid)

Eviction and Invalidation

🔧 Intermediate

Eviction (cache is full): LRU (least recently used, the default), LFU (least frequently used, better for stable popularity), TTL (time-based expiry), FIFO, and modern adaptive policies like W-TinyLFU (Caffeine) and S3-FIFO, which beat LRU on real workloads with one-hit wonders.

Invalidation (data changed):

  • TTL only: simple, bounded staleness.

  • Delete on write: after updating DB, delete the key (not update it).

  • Event-driven: CDC stream (Debezium) emits changes; consumers invalidate.

  • Versioned keys: user:42:v7; bump version to invalidate everything.

🧠 Expert

The race in cache-aside. Reader A misses, reads old value from DB. Writer B updates DB and deletes the key. A then writes the old value to cache, which stays stale until TTL. Fixes: short TTLs as a safety net, delayed double delete (delete again after a few hundred ms), or leases (Facebook’s memcache paper: the cache gives the missing reader a token, and a delete invalidates it so the stale set is rejected).

Stampede / thundering herd: a hot key expires and 10,000 requests hit the DB at once. Fixes: request coalescing (single-flight), locking, serving stale while one worker refreshes (stale-while-revalidate), and probabilistic early expiration (refresh with probability rising as TTL nears zero).

Hot keys: one key gets millions of QPS (a celebrity profile) and saturates one Redis shard. Fixes: local in-process cache in front of Redis, key replication (key#1..key#N read randomly), and client-side tracking (Redis 6+).

Cache penetration: requests for keys that do not exist bypass the cache every time. Cache negative results briefly, or put a Bloom filter in front.

Redis in Practice

🔧 Intermediate

Redis is a single-threaded (per shard) in-memory data-structure server: strings, hashes, lists, sets, sorted sets (leaderboards), streams, HyperLogLog (approximate counts), geospatial indexes, and vector search. Persistence via RDB snapshots and AOF logs. Scale with Redis Cluster (16,384 hash slots across shards). Valkey, the Linux Foundation fork created after Redis’s 2024 license change, is now widely used by cloud providers; Redis 8 later returned to an OSI license option (AGPL). Memcached is simpler, multi-threaded, and good for pure key-value caching. DragonflyDB and KeyDB are multi-threaded Redis-compatible alternatives.

Caching in AI Systems

🆕 New in 2026

  • Exact response cache: hash(model + prompt + params) \(\to\) response. Only useful at temperature 0 with repeated prompts.

  • Semantic cache: embed the query; if a past query is within a similarity threshold, return its answer. Big savings for FAQ-style traffic, but a threshold set too loose returns wrong answers.

  • Provider prompt caching: Anthropic, OpenAI, and Google cache the processed prefix of long prompts (system prompt, documents, tool definitions). Cached input tokens are billed at a fraction of normal price and cut time-to-first-token. Design prompts with stable content first and variable content last.

  • KV cache and prefix caching inside inference engines; see Chapter (inference).

📦 Use case: Social media profile pages

Profiles are read 1,000\(\times\) more than updated. Cache-aside in Redis with a 10-minute TTL and delete-on-write. Celebrity profiles also get a 5-second in-process cache on each app server to absorb hot-key traffic.

📦 Use case: Leaderboard for a mobile game

A Redis sorted set: ZINCRBY on score, ZREVRANGE 0 99 for the top 100, ZREVRANK for a player’s rank. All \(O(\log N)\). Snapshot to the DB every minute (write-back).

📦 Use case: Customer support chatbot

The 8,000-token system prompt and policy documents are placed first and cached by the provider, reducing input cost substantially and TTFT by hundreds of milliseconds. A semantic cache in front answers “how do I reset my password” variants without calling the model.

Deep Dive: Sizing and Reasoning About a Cache

🔧 Intermediate

Hit rate is everything. Database load \(=\) total reads \(\times\) (1 \(-\) hit rate). Going from 90% to 99% hit rate cuts DB reads by 10\(\times\). That is why the last few percent of hit rate are worth real engineering effort.

Sizing example. 100M users, 20M daily active, profile object 2 KB. Caching every active profile: \(20\text{M}\times 2\,\text{KB} = 40\) GB, plus about 30% overhead for keys and allocator fragmentation \(\approx\) 52 GB. Three Redis shards of 25 GB each with replicas gives room to grow. If access follows a Zipf distribution (a few items very popular), caching the top 20% of items often gives 80–90% hit rate, so you may not need all of it.

Average latency with a cache: \(\text{hit} \times t_{\text{cache}} + (1-\text{hit}) \times (t_{\text{cache}} + t_{\text{db}})\). With 0.5 ms cache, 10 ms DB, 95% hit: \(0.5 + 0.05\times10 = 1.0\) ms on average, but p99 is still the DB’s latency. Caches improve averages more than tails.

🧠 Expert

Cold cache after failure. If a cache cluster restarts empty, the hit rate drops to 0 and the database sees 10–100\(\times\) its normal load, which it was never sized for. Mitigations: replicate cache data (Netflix EVCache copies across zones), warm new nodes from peers before taking traffic, rate-limit misses to the DB, and consistent hashing so losing one node only empties \(1/N\) of the keyspace. Facebook’s gutter pool (Part (cases)) sends a failed node’s keys to spare servers instead of rehashing them onto healthy ones.

Consistency choice. Ask: what is the worst thing that happens if a user sees data that is \(T\) seconds old? A product description: nothing. A price in a checkout: a pricing complaint, so re-read from the source at checkout. An account balance or permission: a security or correctness bug, so do not cache, or invalidate synchronously.

⚠️ Pitfall

  • Caching without TTLs, then serving stale data forever after a missed invalidation.

  • All keys expiring at once after a deploy (add TTL jitter).

  • Treating the cache as the source of truth; a restart must not lose data.

  • Caching personalized or authorized responses under a shared key (data leak).

🔑 Takeaways

  • Cache-aside plus TTL plus delete-on-write is the default.

  • Plan for stampedes, hot keys, and penetration from day one.

  • Invalidation is the hard part: bound staleness with TTLs.

  • In AI systems, prompt and KV caching are among the largest cost levers.
