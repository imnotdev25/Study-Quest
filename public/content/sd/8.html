👋 Intro

How to keep a system up when its dependencies fail: timeouts and deadlines, retries with exponential backoff and jitter, circuit breakers, bulkheads, idempotency keys, graceful degradation, and chaos engineering.

🌱 Beginner

Everything fails eventually: networks drop packets, servers restart, third parties go down. Resilience patterns are the house rules for dealing with it: don’t wait forever (timeouts), try again politely (retries with backoff), stop calling someone who isn’t answering (circuit breaker), and make sure doing something twice is harmless (idempotency).

A typical resilience stack around an outbound call.

Timeouts

🔧 Intermediate

Every network call needs a timeout. Without one, a slow dependency ties up threads and connections until your service also stops responding.

  • Connect timeout: short (100 ms–1 s).

  • Request/read timeout: based on the dependency’s p99.9, plus margin.

  • Deadline propagation: pass the remaining time budget downstream (gRPC deadlines, a header like X-Request-Deadline), so a service does not start work the caller has already given up on.

🧠 Expert

Budgets must shrink down the call tree: if the edge timeout is 2 s, the gateway gives services 1.8 s, and so on. A common bug is an inner timeout larger than the outer one, which makes retries useless. For LLM calls use two timeouts: time-to-first-token (e.g. 10 s) and an inter-token idle timeout (e.g. 30 s), rather than one fixed total that would kill long but healthy generations.

Retries

🔧 Intermediate

Retry only transient failures: connection resets, timeouts, 429, 502/503/504. Never retry 400, 401, 403, 404, or validation errors. Only retry operations that are idempotent or protected by an idempotency key. Cap attempts (typically 3) and honor Retry-After.

🧠 Expert

Retry amplification: if each of 4 layers retries 3 times, one user request can become \(3^4 = 81\) requests at the bottom, turning a small blip into a full outage (a retry storm). Rules:

  • Retry at one layer only, usually closest to the failing call.

  • Use a retry budget: retries may add at most 10% extra load (Finagle, Envoy, gRPC support this).

  • Propagate a “do not retry” signal when overloaded.

  • Hedged requests for read latency: after the p95 time, send a second request to another replica and take the first response.

Exponential Backoff with Jitter

🌱 Beginner

If a shop is crowded, you do not walk back in every second. You wait one minute, then two, then four. And if everyone outside waited exactly the same amount, they would all rush in together, so each person adds a random few seconds.

Exponential backoff with a cap, and full jitter spreading clients apart.

RETRYABLE = {429, 500, 502, 503, 504}

def call_with_retry(fn, max_attempts=4, base=0.2, cap=10.0):
    for attempt in range(max_attempts):
        try:
            resp = fn()
            if resp.status not in RETRYABLE:
                return resp
            retry_after = resp.headers.get("Retry-After")
        except (ConnectionError, TimeoutError):
            retry_after = None
        if attempt == max_attempts - 1:
            raise RetryExhausted()
        delay = random.uniform(0, min(cap, base * 2 ** attempt))  # full jitter
        if retry_after:
            delay = max(delay, float(retry_after))
        time.sleep(delay)
🔧 Intermediate

Jitter variants (from the AWS Architecture Blog analysis): full jitter random(0, exp) gives the lowest total load; equal jitter exp/2 + random(0, exp/2) guarantees a minimum wait; decorrelated jitter min(cap, random(base, prev*3)) works well in practice.

Circuit Breakers

🌱 Beginner

An electrical circuit breaker cuts power when there is a fault, so the whole house does not burn. A software circuit breaker stops calling a failing service for a while, so your service fails fast instead of piling up waiting requests.

Circuit breaker state machine.

🔧 Intermediate

Configuration: a sliding window (last 100 calls or last 60 s), a minimum number of calls before evaluating, a failure-rate threshold (e.g. 50%), a slow-call threshold (calls over 2 s count as failures), an open duration (30 s), and the number of half-open trial calls. When open, return a fallback: cached data, a default, a degraded feature, or a clear error. Libraries: Resilience4j (Java), Polly (.NET), pybreaker, gobreaker; at the platform level Envoy/Istio outlier detection ejects bad hosts.

Bulkheads and Load Shedding

🔧 Intermediate

Bulkheads, named after ship compartments, isolate resources so one failing dependency cannot consume everything: separate thread or connection pools per dependency, separate queues per tenant, separate clusters for critical and batch traffic. Load shedding rejects excess requests early (cheap 503) when the server is saturated, keeping latency low for the requests it does accept. Prioritize: shed analytics before checkout.

Idempotency

🌱 Beginner

Pressing an elevator button five times does not summon five elevators. That button is idempotent: doing it again has no extra effect. Payment buttons must work the same way, or a double click charges you twice.

Idempotency keys make retries of non-idempotent operations safe.

🔧 Intermediate

HTTP semantics: GET, PUT, DELETE are idempotent by definition; POST and PATCH are not. Techniques:

  • Idempotency key: client sends a UUID per logical operation; the server stores key \(\to\) (request hash, status, response) for 24 h or more.

  • Natural keys and unique constraints: UNIQUE(order_id) turns a duplicate insert into a no-op.

  • Conditional writes: UPDATE ... WHERE version = 7 (optimistic concurrency), DynamoDB condition expressions.

  • Dedup tables for message consumers: record processed message IDs in the same transaction as the side effect.

🧠 Expert

Implementation details that matter: insert the key with status IN_PROGRESS atomically before doing work, so concurrent duplicates get a 409 rather than both executing; store a hash of the request body and reject the same key with a different body (422); persist the key in the same database transaction as the business change, or recover in-progress keys after crashes; never cache transient 5xx results as final. For downstream calls, pass a derived key (k1:charge) so the whole chain is idempotent end to end.

📦 Use case: Payment API on a flaky mobile network

The app generates Idempotency-Key when the user taps Pay and retries with the same key on timeout. The server charged the card on the first attempt but the response was lost; the retry returns the stored success response. One charge, a happy user. This is how Stripe’s API works.

📦 Use case: Third-party outage during peak

A recommendation service starts timing out. The circuit breaker opens within seconds; the product page falls back to “popular items” from cache. Checkout, which uses a separate connection pool (bulkhead), is unaffected. When the service recovers, half-open trials close the breaker automatically.

📦 Use case: LLM provider failover

Primary model returns 529/overloaded. The AI gateway retries once with jittered backoff, then fails over to a second provider or region with an equivalent model. A circuit breaker per provider avoids hammering an overloaded endpoint. The request carries an idempotency key so agent tool calls are not repeated.

Chaos Engineering

🔧 Intermediate

Test resilience on purpose: inject latency, kill instances, drop a zone, throttle a dependency, and verify the system meets its SLOs. Start in staging with a clear hypothesis and a small blast radius, then run game days in production. Tools: Chaos Monkey, Gremlin, AWS Fault Injection Service, Chaos Mesh, LitmusChaos.

Deep Dive: Why Systems Collapse Under Load

Queueing delay explodes as utilization approaches 100%.

🔧 Intermediate

In a simple queue, average time in system is service time divided by \((1-\rho)\). At 50% utilization latency is 2\(\times\) the service time; at 80% it is 5\(\times\); at 95%, 20\(\times\). This is why Shopify’s payment team targets well below full saturation (Part (cases)), and why autoscaling targets of 60–70% CPU are common.

🧠 Expert

Metastable failure. A system can be stable at normal load, get pushed over by a short trigger (a deploy, a cache flush, a brief network blip), and then stay broken after the trigger is gone. The mechanism is a feedback loop: latency rises \(\to\) clients time out and retry \(\to\) load rises \(\to\) latency rises further. Work done for requests whose callers have already given up is pure waste (“goodput” falls to zero even though servers are 100% busy). The AWS us-east-1 case (Part (cases)) is a textbook example: after DynamoDB recovered, the backlog of lease renewals kept timing out and retrying.

Defenses, in order of importance:

  1. Bound queues; reject early when full (fast failure is cheap).

  2. Drop requests whose deadline has already passed before doing any work.

  3. Retry budgets and jittered backoff so retries cannot multiply load.

  4. Prefer LIFO over FIFO under overload for interactive traffic: the newest requests are the ones whose users are still waiting.

  5. Admission control and priority: keep serving the most important traffic.

  6. A recovery playbook that throttles inbound work while backlogs drain.

Retry math. With failure probability \(p\) per attempt and up to \(n\) attempts, expected load multiplier is \(1 + p + p^2 + \dots + p^{n-1}\). At \(p=0.1\) and \(n=3\) that is 1.11 (fine). During an outage \(p\to 1\) and the multiplier is \(n\), at every layer that retries, so 3 layers \(\times\) 3 attempts gives 27\(\times\) load exactly when the system can least handle it.

⚠️ Pitfall

  • No timeout on HTTP clients (many libraries default to infinite).

  • Retrying without jitter, creating synchronized waves.

  • Retrying non-idempotent operations: duplicate orders and charges.

  • Circuit breaker thresholds tuned for normal traffic that never trip at low volume.

  • Fallbacks that are never tested and fail when finally needed.

🔑 Takeaways

  • Timeouts everywhere, with budgets shrinking down the call chain.

  • Retry transient errors at one layer, with capped exponential backoff and jitter.

  • Circuit breakers and bulkheads stop failures from spreading.

  • Idempotency is what makes retries and at-least-once delivery safe.
