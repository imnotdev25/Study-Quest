👋 Intro

The building blocks of social and location products: choosing between long polling, SSE, and WebSockets; modeling follows, likes, reactions, hashtags, and photo tags; unread indicators; live commentary; nearby search with geohashes and grids; Redis GEO; geofencing with point-in-polygon; filtering already-seen items; and an overview of matching and recommendation algorithms.

Long Polling vs SSE vs WebSockets

Long polling Server-Sent Events WebSocket
Direction server to client (simulated) server to client both
How request held open until data or timeout, then re-sent one HTTP response streamed forever upgraded TCP connection, framed messages
Infrastructure works everywhere plain HTTP; works through most proxies needs proxies and LBs that support upgrade and long connections
Reconnect by design built-in with Last-Event-ID you implement it
Overhead a request per message low lowest
Use fallback, notifications to old clients feeds, notifications, LLM tokens chat, games, collaboration, voice
🔧 Intermediate

Whichever you choose, the scaling problems are the same as in Chapter (networking) and the Slack and Netflix cases (Part (cases)): a registry of which gateway holds each user’s connection, pub/sub to reach the right gateway, jittered reconnects after deploys, autoscaling on connection count, and a resync protocol (client sends its last sequence number) because pushes are best effort.

Social Network Data Modeling

users     (user_id PK, handle UNIQUE, name, created_at, ...)
posts     (post_id PK /* time-sortable id */, author_id, body, created_at,
           like_count, comment_count)              -- denormalized counters
follows   (follower_id, followee_id, created_at,
           PRIMARY KEY (follower_id, followee_id)) -- "who do I follow"
followers (followee_id, follower_id, created_at,
           PRIMARY KEY (followee_id, follower_id)) -- reverse index, separate shard key
likes     (post_id, user_id, created_at, PRIMARY KEY (post_id, user_id))
user_likes(user_id, post_id, created_at, PRIMARY KEY (user_id, post_id))
🔧 Intermediate

Each edge is stored twice, once per direction, because the two questions (“whom does A follow?” and “who follows A?”) shard by different keys. Writes update both rows (a transaction if co-located, otherwise an outbox event that updates the reverse index). Counts (followers, likes) are denormalized onto the user or post row and updated asynchronously or with sharded counters (Chapter (analytics)); exact counts can be recomputed from edges.

The Social Graph: FlockDB and Friends

🔧 Intermediate

Twitter built FlockDB (open-sourced 2010) to store follow edges: adjacency lists in sharded MySQL (through its Gizzard sharding framework), optimized for the operations a social graph needs: add and remove edges idempotently, page through a node’s edges in time order, count edges, and set operations across adjacency lists (“people A follows who also follow B”: an intersection). It deliberately did not support multi-hop graph traversal; most product queries are one hop. Meta’s TAO (Part (cases)) is the same idea with a caching layer in front. Multi-hop queries (friends-of-friends suggestions) are computed offline in batch graph jobs.

Reactions

🔧 Intermediate

A reaction is a typed edge: reactions(target_id, user_id, type, created_at, PRIMARY KEY (target_id, user_id)). The primary key enforces one reaction per user per target; changing a reaction is an upsert, removing it a delete. Make the API idempotent (PUT /posts/42/reaction {type} rather than “toggle”, which double-taps break). Keep per-type counts on the post ({"like": 1203, "laugh": 87}), updated from the change stream with sharded counters for viral posts. “Did I react?” is a point lookup by (target_id, user_id), cached with the post for the viewer.

Hashtags and the Tag Store

🔧 Intermediate

Extract hashtags at write time with a Unicode-aware tokenizer (hashtags are not ASCII-only), normalize (case folding, Unicode NFKC normalization so visually identical tags match), and store in post_tags(tag, post_id) ordered by post_id (time-sortable) for “latest posts with #tag.” Popular tags produce huge, hot partitions: bucket by time ((tag, day) as the partition key) or route very hot tags to a dedicated store. Trending tags come from streaming counts compared to baselines (Chapter (analytics)). Tag pages are typically served from a search index, which handles ranking and filtering.

Photo Tagging Coordinates

🔧 Intermediate

Store a tag as (photo_id, tagged_user_id, x, y, w, h, status, tagged_by) with coordinates as fractions of image width and height (0.0–1.0), not pixels, so tags stay correct for every rendition size and after the client resizes the image. Handle EXIF orientation by normalizing images on upload. A status field supports approval flows (tags of you pending your approval) and privacy rules. Index by tagged_user_id for “photos of me.”

A Newly-Unread Indicator

🔧 Intermediate

The red dot or “3 new” badge must be cheap because it is shown on every screen.

  • Read pointer: store each user’s last_read_seq per conversation or inbox; each conversation has a latest_seq. Unread \(= \text{latest} - \text{last read}\) (or unread if they differ). Opening the conversation advances the pointer.

  • Counter on write: increment a per-user unread counter (Redis) during fan-out; reset on open. Fast reads, but counters drift with retries and multiple devices, so periodically recompute from pointers.

  • Multi-device: the read pointer is server state, so reading on the phone clears the badge on the laptop (push a “read up to” event to other devices).

  • Show “99+” instead of exact large numbers: it is cheaper and users do not need more.

Live Commentary

🔧 Intermediate

A live match with millions of readers and a few writers (official commentary) or many writers (live comments). Writes go through the normal API (auth, moderation, rate limits) into a log per event; a fan-out service publishes to WebSocket or SSE gateways subscribed to that event; clients fetch the recent history once from a cache and then receive updates. For a flood of user comments, sample or rank which comments each viewer sees (no one can read 5,000 comments per second), apply per-user rate limits and slow mode, and run automated moderation before broadcast. Order by server timestamp plus sequence number. Persist everything for replays and the final page.

Nearby Search

🌱 Beginner

To find coffee shops near you, you should not measure the distance to every coffee shop on Earth. Divide the map into a grid, look only in your square and the squares around it, then measure distances to the few shops found there.

Geohash Prefix Index

Querying a cell and its neighbors avoids missing points just across a boundary.

🔧 Intermediate

A geohash interleaves bits of latitude and longitude and encodes them in base 32: each extra character makes the cell about 32 times smaller in area. Precision 5 is about 4.9 km \(\times\) 4.9 km, precision 6 about 1.2 km \(\times\) 0.6 km, precision 7 about 150 m. Points that share a prefix are in the same cell, so a sorted index on the geohash string (a B-tree or a sorted key-value store) answers “points in this cell” with a prefix range scan. Query: choose a precision whose cells are about the search radius, compute the user’s cell and its 8 neighbors, range-scan each, then filter candidates by exact (haversine) distance and sort. The neighbors are necessary because two nearby points on opposite sides of a cell boundary can have different prefixes, and the Z-order curve has jumps where adjacent cells have very different hashes.

Grid Systems: Geohash, S2, H3

🔧 Intermediate

Geohash: simple strings, prefix queries on any sorted store, rectangular cells that distort near the poles. S2 (Google): the sphere projected onto a cube, cells ordered along a Hilbert curve (better locality than Z-order), 64-bit IDs, region coverings of any shape; used by Google Maps and many databases. H3 (Uber): hexagons with one neighbor distance, ideal for aggregation and smoothing (Part (cases)). Quadtrees adapt cell size to density (split a cell when it holds too many points), good for very uneven data like restaurants. PostGIS uses R-trees (GiST indexes) and supports ST_DWithin queries directly; for many applications that is enough.

Redis GEO for the Hot Path

🔧 Intermediate

For constantly moving entities (drivers, couriers), keep locations in memory. Redis GEO stores members in a sorted set whose score is a 52-bit geohash: GEOADD drivers:sf lon lat driver42 on every location update (every few seconds), and GEOSEARCH drivers:sf FROMLONLAT lon lat BYRADIUS 2 km ASC COUNT 20 to find the nearest. Shard keys by city or by coarse geohash cell to keep sets small; expire stale drivers by also tracking last-update times (a second sorted set by timestamp, trimmed periodically), because GEO members do not expire individually. The durable record of trips lives in a database; Redis holds only the current positions.

Geofencing: Point in Polygon

Ray casting: count how many polygon edges a ray from the point crosses.

🔧 Intermediate

Ray casting: from the point, cast a ray in one direction and count crossings with polygon edges; an odd count means inside. For each edge \((x_i, y_i) \to (x_j, y_j)\), it crosses a horizontal ray to the right of \((x, y)\) if \((y_i > y) \ne (y_j > y)\) and \(x < x_i + (y - y_i)(x_j - x_i)/(y_j - y_i)\). Handle points exactly on edges and vertices consistently. \(O(\text{vertices})\) per polygon.

At scale (millions of location updates against thousands of zones: delivery areas, surge zones, airport pickup zones): first filter by bounding box, then use a spatial index (an R-tree, or precompute each polygon’s covering H3 or S2 cells into a hash map from cell to candidate polygons) so each update is tested against only one or two polygons. Track the previous zone per entity to emit enter and exit events, with hysteresis or a minimum dwell time to avoid flapping at the boundary from GPS noise.

Seen Filtering: Bloom vs Exact Sets

🔧 Intermediate

Feeds and recommendation systems must not show the same item twice.

Exact set (Redis set, DB table) Bloom filter per user
Memory 8+ bytes per item per user, plus overhead about 10 bits per item for 1% false positives
Errors none false positives: an unseen item is sometimes skipped; never shows a seen item
Deletion / expiry easy not supported; rotate filters
Use small histories, must be exact (purchases, “don’t show again”) huge histories (every video impression)

For time-limited “seen in the last 30 days,” keep a ring of filters (one per few days), check all, and drop the oldest when rotating. A 1% false positive rate means hiding 1% of unseen candidates, usually invisible to users. Apply seen filtering at candidate generation, before expensive ranking.

Matching and Recommendation Algorithms

🔧 Intermediate

  • Content-based: recommend items similar to what the user liked (shared attributes or embedding similarity). Works for new items; can be narrow.

  • Collaborative filtering: item–item similarity from co-occurrence (“people who bought X bought Y”), matrix factorization, or two-tower neural models trained on interactions, served with approximate nearest neighbor search.

  • Graph-based: random walks on user–item graphs (Pinterest’s Pixie) or friends-of-friends for people suggestions.

  • Ranking: a multi-task model predicting click, watch, purchase, and negative feedback, combined into a score (the companion interview book covers the models).

  • Two-sided matching (ride hailing, delivery, dating, marketplaces): both sides have preferences or constraints. Batch the decision into short rounds and solve an assignment problem (Hungarian algorithm or min-cost flow) instead of greedy nearest matching; for mutual-preference markets, stable matching (Gale–Shapley) avoids pairs who would both rather be together. Dating apps also ration attention: popular profiles should not receive every like (fairness and quality for both sides).

  • Exploration: reserve some traffic for new items and uncertain candidates (bandits) so the system keeps learning.

📦 Use case: Design “nearby friends”

Friends opt in to sharing location. Each app sends a location every 30 seconds while active; the location service updates the user’s position in a geo-sharded in-memory store and publishes to a per-user channel. Each user’s session subscribes to their friends’ channels and computes distances itself (friend lists are small, so this is cheaper than a geo query). Inactive users’ locations expire after a few minutes. Privacy: precision is coarsened, sharing can be paused, history is not stored.

🔑 Takeaways

  • Pick long polling, SSE, or WebSockets by direction and infrastructure; the scaling patterns are the same.

  • Store social edges in both directions, keep counts denormalized, and make reaction APIs idempotent.

  • Unread state is a read pointer versus a latest sequence number.

  • Nearby search = grid cell + neighbors + exact distance filter; Redis GEO for moving entities.

  • Ray casting decides point in polygon; index polygons by cells for scale.

  • Bloom filters make “seen” filtering cheap when rare false positives are acceptable.
