👋 Intro

How a request travels from a browser to your server: DNS, TCP/UDP, TLS, HTTP/1.1–3, CDNs, and the API styles (REST, gRPC, GraphQL, WebSockets, SSE) you choose between.

The Life of a Request

DNS lookup, connection setup, edge cache, then origin.

DNS

🌱 Beginner

DNS is the internet’s phone book. You type shop.example.com; DNS returns a number like 203.0.113.7 that computers use to connect.

🔧 Intermediate

Resolution walks root \(\to\) TLD (.com) \(\to\) authoritative server, with caching at every layer governed by TTL. Record types: A/AAAA (IPv4/IPv6), CNAME (alias), MX (mail), TXT (verification), SRV (service location). DNS is also a load-balancing tool: GeoDNS returns the nearest region, weighted records split traffic, and health-checked records (Route 53) fail over.

🧠 Expert

Low TTLs (30–60 s) enable fast failover but raise resolver load, and many clients ignore TTLs anyway (JVM caches, OS stubs). For instant failover, prefer anycast (one IP announced from many locations via BGP) over DNS changes. DNS is a classic single point of failure: the 2016 Dyn outage took down many major sites. Use two DNS providers for critical domains.

Transport protocols compared

🔧 Intermediate

HTTP/1.1 sends one request at a time per connection, so browsers open six connections. HTTP/2 multiplexes many streams over one TCP connection with header compression, but a single lost packet stalls all streams (TCP head-of-line blocking). HTTP/3 runs over QUIC on UDP, fixing that and cutting handshake time. TLS 1.3 reduced the handshake to one round trip.

Content Delivery Networks

🌱 Beginner

A CDN is like having copies of a popular book in libraries in every city, so readers do not have to travel to the publisher.

🔧 Intermediate

Pull CDN: the edge fetches from origin on first miss and caches by TTL (most common). Push CDN: you upload content ahead of time (large, predictable files). Control caching with Cache-Control, ETag, and Vary. Use versioned filenames (app.3f9a.js) so you can cache forever and never need to purge. Modern CDNs also run code at the edge (Cloudflare Workers, Lambda@Edge, Fastly Compute) for auth, A/B routing, personalization, and even small AI inference.

📦 Use case: Video streaming platform

Videos are transcoded into segments at multiple bitrates (HLS/DASH). Segments are immutable and cached at edges near viewers; the player switches bitrate based on bandwidth. Netflix goes further with Open Connect appliances placed inside ISP networks, serving most traffic without crossing the internet backbone.

📦 Use case: E-commerce flash sale

Product images, JS, and CSS come from the CDN. The product page HTML is cached for 10 seconds at the edge (“micro-caching”), absorbing 99% of traffic while staying almost fresh. Only cart and checkout hit origin.

Choosing an API style

🧠 Expert

API design rules that age well: version in path or header (/v1/); cursor-based pagination (?after=opaque_cursor) rather than offsets for large tables; idempotency keys on mutating POSTs; consistent error envelopes (RFC 9457 Problem Details); explicit rate-limit headers. For streaming LLM output, SSE has become the de facto standard (OpenAI, Anthropic APIs), since it works through HTTP proxies and needs no upgrade handshake. WebSockets are used when the client must also stream (realtime voice).

📦 Use case: Real-time chat

Clients hold a WebSocket to a gateway fleet. A connection registry (Redis: user_id \(\to\) gateway node) lets any service find where a user is connected. Messages go through a pub/sub layer to the right gateway. With millions of connections, gateways are tuned for file descriptors and memory per connection (often 10–50 KB).

HTTP Request Types (Methods)

🌱 Beginner

An HTTP method is the verb of a request. GET means “give me this,” POST means “do something with this,” PUT means “store this here,” DELETE means “remove this.” Proxies, caches, browsers, and retry logic all make decisions based on the verb, so picking the right one is a correctness choice, not just style.

Method Meaning Safe Idempotent Cacheable Body
GET read a resource yes yes yes no (ignored)
HEAD GET without the body (check existence, size, ETag) yes yes yes no
OPTIONS ask what is allowed (CORS preflight) yes yes no optional
POST create a child resource or run an action no no rarely yes
PUT create or fully replace the resource at this URL no yes no yes
PATCH partially modify a resource no not guaranteed no yes
DELETE remove a resource no yes no optional
CONNECT open a tunnel (HTTPS through a proxy) no no no n/a
TRACE echo the request (diagnostics; usually disabled) yes yes no no

HTTP methods (RFC 9110).

🔧 Intermediate

  • Safe means the request should not change server state, so crawlers, prefetchers, and link previews can call it freely. Never let a GET delete or charge anything (GET /delete?id=5 gets triggered by a link-preview bot).

  • Idempotent means sending it twice has the same effect as once, so clients and proxies may retry it automatically after a timeout. PUT and DELETE are idempotent by design; POST is not, which is why payment and order creation need an Idempotency-Key header (Chapter (resilience)). PATCH is idempotent only if the patch is (“set name to X” is; “append item” is not).

  • PUT vs PATCH: PUT sends the full representation; fields left out are removed. PATCH sends changes, as JSON Merge Patch (RFC 7396: send only the fields to change, null deletes) or JSON Patch (RFC 6902: a list of operations).

  • POST vs PUT for creation: POST /orders when the server picks the ID; PUT /orders/{client-generated-id} when the client does, which makes creation naturally idempotent.

  • Search with a large filter: a GET with a long query string can exceed URL limits (often about 8 KB at proxies); options are POST /search (not cacheable, not idempotent by default) or the newer QUERY method draft (safe and idempotent with a body), not yet widely supported.

Headers That Carry Design Decisions

🔧 Intermediate

  • Conditional requests: the server returns an ETag (a version or hash). A client re-validates with If-None-Match (gets 304 if unchanged, saving bandwidth) and updates with If-Match (gets 412 if someone else changed it first). That is optimistic concurrency over HTTP: no lost updates without locks.

  • Caching: Cache-Control (max-age, no-store, private, immutable, stale-while-revalidate), Vary.

  • Content negotiation: Accept, Content-Type, Accept-Encoding (gzip, br, zstd).

  • Range: Range: bytes=1000000- resumes a download or seeks in a video.

  • CORS: browsers send an OPTIONS preflight before cross-origin requests with custom headers or non-simple methods; the server answers with Access-Control-Allow-*. Cache the preflight (Access-Control-Max-Age) to avoid an extra round trip per call.

  • Tracing and identity: traceparent, Authorization, Idempotency-Key, X-Request-Id.

Request Body Formats

🔧 Intermediate

JSON (application/json) for most APIs; application/x-www-form-urlencoded for simple HTML forms; multipart/form-data for file uploads from browsers (each part has its own headers), though large files should go directly to object storage (Chapter (media)); Protocol Buffers for gRPC; application/octet-stream for raw bytes; NDJSON (one JSON object per line) for streaming many records.

HTTP Versions Under the Hood

🔧 Intermediate

HTTP/1.1: one request at a time per connection (pipelining is unused in practice); keep-alive reuses connections; browsers open about six per host. Chunked transfer encoding lets a server stream a response of unknown length, which is what SSE and streamed JSON ride on. HTTP/2: binary frames, many concurrent streams on one TCP connection, header compression (HPACK), per-stream flow control; one lost packet still stalls every stream (TCP head-of-line blocking). HTTP/3: the same model over QUIC (UDP), with independent streams, 1-RTT (or 0-RTT) setup including TLS 1.3, and connection migration across networks. All three expose the same methods, headers, and status codes.

Long Polling in Detail

🔧 Intermediate

The client sends GET /updates?cursor=123. If new data exists, the server answers at once; otherwise it holds the request (say up to 30 seconds), answering as soon as data arrives or with an empty response at the timeout. The client immediately sends the next request with the new cursor. The cursor is what makes it reliable: nothing is lost between requests. Server side, a held request must not hold a thread (use async I/O), and timeouts at every proxy must exceed the hold time. Dropbox used long polling for change notifications.

Server-Sent Events in Detail

retry: 3000

id: 41
event: token
data: {"text": "Hello"}

id: 42
event: token
data: {"text": " world"}

: comment lines keep the connection alive through idle proxies
🔧 Intermediate

Each event is a few field: value lines ending with a blank line. On disconnect, the browser’s EventSource reconnects after retry milliseconds and sends Last-Event-ID: 42, so the server can resume from the right place. Limitations: server to client only (send client messages with normal POSTs), UTF-8 text only, and EventSource cannot set custom headers (so LLM APIs are usually consumed with fetch and a streamed body instead). Under HTTP/1.1, each SSE connection uses one of the browser’s six per-host connections; HTTP/2 removes that limit. Disable proxy buffering for streams (Chapter (lb)).

WebSockets in Detail

🔧 Intermediate

The client sends an HTTP GET with Upgrade: websocket and a random key; the server replies 101 Switching Protocols, and the TCP connection becomes a bidirectional stream of small frames (text, binary, ping, pong, close). There is no built-in request/response matching, acknowledgement, or resume, so applications add message IDs, acks, sequence numbers for resync, heartbeats (ping every 20–30 s to detect dead connections and keep NATs open), and authentication at connect time (a short-lived token, since browsers cannot set custom headers on the upgrade request). Scaling needs sticky routing of a connection to one gateway, a registry of which gateway holds each user, and pub/sub between gateways (Slack and Netflix cases, Part (cases)).

gRPC Streaming Modes

🔧 Intermediate

  • Unary: one request, one response (like REST).

  • Server streaming: one request, a stream of responses (subscribe to price updates, stream LLM tokens between services).

  • Client streaming: a stream of requests, one response (upload sensor readings, then get a summary).

  • Bidirectional streaming: both sides stream independently (chat, Uber’s push platform, interactive agents).

Each RPC carries a deadline that propagates to downstream calls; flow control comes from HTTP/2. Browsers need gRPC-Web or Connect through a proxy.

Webhooks in Detail

🔧 Intermediate

The provider sends POST requests to a URL you registered when events happen. Design rules for both sides:

  • Verify every request: an HMAC signature of the body with a shared secret (Stripe’s Stripe-Signature, GitHub’s X-Hub-Signature-256) and a timestamp to reject replays.

  • Acknowledge fast (2xx within a few seconds) and process asynchronously; providers retry on timeouts or non-2xx with exponential backoff for hours or days.

  • Deduplicate by event ID, since delivery is at least once and order is not guaranteed; fetch the latest state from the provider’s API when ordering matters.

  • Providers should offer a replay UI, a list-events API for recovery, per-endpoint circuit breaking, and signing-secret rotation.

🎤 Interview

Choosing a mechanism in an interview:

  • Ordinary reads and writes: request–response over HTTP/2 or HTTP/3.

  • Updates every few minutes, few clients: short polling.

  • Server pushes to browsers, one direction (notifications, feeds, LLM output): SSE.

  • Both directions, high frequency (chat, games, collaborative editing): WebSocket.

  • Between your own services with streams: gRPC streaming.

  • Real-time audio and video: WebRTC.

  • Notifying another company’s server: webhooks.

  • Battery- and bandwidth-constrained devices: MQTT.

Whatever the transport, design for disconnects: a cursor or sequence number so the client can resume, idempotent handlers, and a fallback to plain HTTP fetching.

Service-to-Service Communication in Practice

Batching

🔧 Intermediate

Each network call has fixed overhead (round trip, headers, serialization, syscalls). Batching amortizes it: one MGET of 100 keys instead of 100 GETs, a multi_get(ids) API, Kafka producer batches (linger.ms waits a few milliseconds to fill a batch), bulk inserts, GPU inference batches. The trade-off is latency: an item waits until the batch fills or a timeout fires. Bound batch size (memory, request limits) and wait time, and fail individual items, not the whole batch, when one is bad. The N+1 query problem (loading a list, then one query per item) is the most common missed batching opportunity; GraphQL servers fix it with a DataLoader that batches lookups within one request.

Backpressure

🔧 Intermediate

When a consumer is slower than its producer, work piles up somewhere. Without backpressure, queues grow without bound until memory runs out or latency becomes useless. Mechanisms:

  • Bounded queues that block or reject when full.

  • Flow control in the protocol: TCP windows, HTTP/2 and gRPC stream flow control, Reactive Streams’ request(n).

  • Pull-based consumers (Kafka): consumers fetch at their own pace and lag becomes the visible signal.

  • Signals upstream: 429/503 with Retry-After, so callers slow down.

Choose deliberately what happens at the limit: block the producer, drop the newest, drop the oldest, or sample. For metrics and logs, dropping is acceptable; for payments, it is not.

Tail Latency

🔧 Intermediate

The slowest 1% of requests matter more than averages suggest, because a user action fans out to many services (Chapter (foundations)). Sources of tail latency: GC pauses, queueing behind slow requests, noisy neighbors, cold caches, background compaction, retries, and network retransmits. Techniques from Google’s “The Tail at Scale” (Dean and Barroso, 2013):

  • Hedged requests: after the p95 time, send a duplicate to another replica and use the first response (adds about 5% load).

  • Tied requests: send to two replicas, each told about the other, and the first to start cancels the other.

  • Micro-partitioning: many small partitions per machine so load can be moved quickly.

  • Selective replication of hot items, and latency-aware load balancing (least outstanding requests).

  • Return good-enough partial results when a few shards are slow.

🔑 Takeaways

  • DNS and anycast are your first layer of load balancing and failover.

  • HTTP/3 over QUIC removes head-of-line blocking and speeds up mobile.

  • Cache static assets forever with versioned names; micro-cache dynamic pages.

  • REST outside, gRPC inside, SSE for streaming tokens, WebSocket for duplex.
