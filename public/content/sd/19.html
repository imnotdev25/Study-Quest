👋 Intro

What happens inside an LLM server: prefill and decode, why decode is memory-bound, KV cache math, continuous batching, PagedAttention, prefix caching, chunked prefill, disaggregated serving, quantization, speculative decoding, parallelism strategies, serving engines, metrics, and autoscaling.

How Generation Works

🌱 Beginner

Reading the question is fast: the model reads all words of your prompt at once, in parallel. Writing the answer is slow: it must write one token, then reread its notes to write the next, and so on. To avoid rereading everything each time, it keeps a notebook of what it has already processed. That notebook is the KV cache, and managing it is most of inference engineering.

The two phases of LLM inference.

🔧 Intermediate

  • Prefill: process the whole prompt in one forward pass, producing the first token and filling the KV cache. Large matrix multiplies, so it is compute-bound. Determines time-to-first-token (TTFT).

  • Decode: generate one token per forward pass, reading all model weights and the KV cache each step. Very little compute per byte read, so it is memory-bandwidth-bound. Determines time per output token (TPOT), also called inter-token latency (ITL).

End-to-end latency \(\approx\) TTFT \(+\) TPOT \(\times\) (output tokens \(-1\)).

The Roofline: Why Batching Matters

Roofline for an H100-class GPU (approximate figures). Decode at batch 1 uses a tiny fraction of the GPU’s compute.

🧠 Expert

During decode, each weight (2 bytes in BF16) is used for about 2 FLOPs per sequence in the batch, so intensity \(\approx\) batch size (FLOPs per byte). The GPU only becomes compute-bound when intensity exceeds peak FLOPs / bandwidth \(\approx 989 / 3.35 \approx 295\). So:

  • At batch size 1, a 70B BF16 model across 4 GPUs reads 140 GB of weights per token at \(4\times3.35\) TB/s \(\approx\) 10 ms per token, about 95 tokens/s, with the compute units mostly idle.

  • At batch 64, almost the same 10 ms step yields 64 tokens: about 64\(\times\) the throughput for a small latency increase.

Batching is the single biggest throughput lever. The constraint that stops you is memory for the KV cache, which grows with batch size \(\times\) sequence length.

KV Cache Math

🔧 Intermediate

Per token, the KV cache stores a key and a value vector for every layer: \[\text{KV bytes/token} = 2 \times n_{\text{layers}} \times n_{\text{kv\_heads}} \times d_{\text{head}} \times \text{bytes per element}\] Example (Llama-3-70B-class): 80 layers, 8 KV heads (grouped-query attention), head dim 128, FP16: \(2\times80\times8\times128\times2 = 327{,}680\) bytes \(\approx\) 320 KB per token.

  • One 8K-token conversation \(\approx\) 2.6 GB.

  • 64 concurrent 8K conversations \(\approx\) 168 GB, more than the weights themselves.

Without GQA (64 KV heads) it would be 8\(\times\) larger. This is why model architectures use GQA, multi-query attention, or multi-head latent attention (MLA), as in DeepSeek models, which compresses KV into a small latent vector.

70B weights in FP8 70 GB

Remaining for KV cache \(\sim\)530 GB \(\to\) \(\sim\)1.6M tokens of context in FP16 KV

Capacity planning: KV cache space decides how many users fit.

Batching and Memory Management

Continuous (in-flight) batching admits new requests at every decode step.

🔧 Intermediate

  • Continuous batching: the scheduler adds and removes sequences at every iteration instead of waiting for a whole batch to finish. Standard in every modern engine; often 5–20\(\times\) throughput over static batching.

  • PagedAttention: stores the KV cache in fixed-size blocks (like OS virtual memory pages) instead of one contiguous buffer per request, so memory is not wasted on reserved-but-unused space. Introduced by vLLM.

  • Prefix caching: requests that share a prefix (system prompt, documents, earlier turns) reuse the KV blocks already computed for it, skipping that part of prefill. SGLang’s RadixAttention keeps a radix tree of cached prefixes. This is the server-side version of provider prompt caching.

  • Chunked prefill: split long prompts into chunks and mix them with decode steps, so one 100K-token prompt does not stall everyone else’s tokens.

  • Preemption: when KV memory runs out, pause low-priority sequences and swap their KV to CPU memory or recompute it later.

  • KV offloading / tiering: keep cold KV blocks in CPU RAM, local SSD, or a shared cache across servers (LMCache, NVIDIA Dynamo KV manager), so long multi-turn conversations do not need full recomputation.

Disaggregated Prefill and Decode

Disaggregated serving: prefill and decode run on separate GPU pools.

🧠 Expert

Prefill and decode compete on the same GPU: a burst of long prompts spikes everyone’s TPOT. Disaggregation runs them on separate pools that scale independently and can use different parallelism or even different hardware; the KV cache is shipped from prefill to decode over fast interconnect (NIXL-style transfer libraries over NVLink or RDMA). It improves goodput under strict TTFT and TPOT SLOs, at the cost of KV transfer bandwidth and system complexity. Open-source stacks include NVIDIA Dynamo, llm-d (Kubernetes-native, built on vLLM), and the disaggregation modes of vLLM and SGLang. It pays off mostly at large scale and with long prompts; small deployments often do better with chunked prefill on unified servers.

Quantization formats

🔧 Intermediate

Quantization reduces the bytes read per token, which directly speeds up memory-bound decode and frees memory for KV cache. Always evaluate on your own task: math, code, and long-context quality degrade first.

Speculative Decoding

Speculative decoding: cheap guesses verified in parallel.

🔧 Intermediate

A small draft model (or extra prediction heads such as Medusa or EAGLE, or the model’s own multi-token-prediction layers, or n-gram lookup from the prompt) guesses several tokens; the large model checks them in a single forward pass and keeps the longest correct prefix. The output distribution is mathematically identical to normal decoding. Speedups of 2–3\(\times\) are common at low batch sizes, where the GPU has spare compute; gains shrink at high batch.

Kernel and Architecture Optimizations

🔧 Intermediate

FlashAttention (now in its third and fourth generations) computes attention in on-chip memory tiles, avoiding writes of the huge attention matrix. CUDA graphs remove CPU launch overhead in decode. Kernel fusion and compilers (torch.compile, TensorRT) combine operations. Mixture of Experts (MoE) models (DeepSeek-V3, Qwen3-MoE, Llama 4, many frontier models) activate only a few experts per token, so compute per token is small but all experts must sit in memory.

Parallelism Strategies

Strategy Splits Use when
Data parallel (replicas) Whole model copied; requests split Model fits on one GPU or node; scale throughput
Tensor parallel (TP) Each layer’s matrices across GPUs Model too big for one GPU; needs NVLink; reduces latency
Pipeline parallel (PP) Layers across GPUs/nodes Model too big for one node; adds pipeline bubbles
Expert parallel (EP) MoE experts across GPUs Large MoE models; all-to-all communication
Context / sequence parallel Long sequence across GPUs Very long contexts (prefill of 1M tokens)

Parallelism for inference

🧠 Expert

Rule of thumb: tensor parallel within a node (NVLink domain), pipeline or expert parallel across nodes, data parallel for scale. Large MoE serving (DeepSeek-style) combines wide expert parallelism for decode across many GPUs with smaller tensor-parallel groups for attention, plus disaggregated prefill. Rack-scale systems with a single large NVLink domain (GB200/GB300 NVL72) make wide tensor and expert parallelism practical across 72 GPUs.

The inference software landscape

Metrics and Service Levels

🔧 Intermediate

  • TTFT: perceived responsiveness. Chat target is typically under 1 s.

  • TPOT / ITL: streaming smoothness. Humans read about 5–10 tokens/s; 20–50+ tokens/s feels fast. Agents and code generation want much faster.

  • Throughput: total output tokens/s per GPU; drives cost.

  • Goodput: requests per second that meet both TTFT and TPOT SLOs. The right metric to optimize.

  • Cost per million tokens: GPU $/hour \(\div\) (tokens/hour \(/ 10^6\)).

Throughput and latency trade against each other through batch size. Benchmark with realistic input/output length distributions, not a single fixed shape.

🧠 Expert

Cost example. A GPU at $2.50/hour sustaining 2,500 output tokens/s yields \(9\text{M}\) tokens/hour, so about $0.28 per million output tokens at 100% utilization. At 30% average utilization, cost more than triples. Utilization is what makes self-hosting win or lose against API pricing.

Autoscaling LLM servers on CPU utilization does not work. Scale on queue depth, KV cache utilization, and running/waiting request counts. Cold starts are minutes (pulling tens of GB of weights, loading to GPU, compiling graphs); mitigate with pre-warmed pools, weights cached on local NVMe, streaming model loaders, and snapshot/restore of initialized processes.

Routing: use load- and cache-aware routing (least KV usage, prefix affinity via consistent hashing on the prompt prefix) rather than round robin; the Kubernetes Gateway API Inference Extension standardizes this pattern.

Multi-LoRA serving: one base model in memory with hundreds of small LoRA adapters loaded on demand (S-LoRA, vLLM/SGLang multi-LoRA), so many fine-tuned variants share GPUs.

📦 Use case: Self-hosted chat assistant at 2,000 concurrent users

A 70B FP8 model on 8\(\times\)H100 nodes with vLLM, tensor parallel 4 (two replicas per node). Prefix caching on the shared 3K-token system prompt cuts TTFT and prefill compute. Chunked prefill keeps TPOT stable when users paste long documents. Autoscaling triggers on waiting requests \(>\) 20 per replica.

📦 Use case: Bulk document processing overnight

Latency does not matter; throughput does. Run maximum batch sizes, INT4 or FP8 weights, no speculative decoding (high batch already uses compute), on spot GPUs. Or use a provider batch API at a discount.

📦 Use case: Low-latency coding autocomplete

A small (1–8B) model, speculative decoding with n-gram or draft heads (code repeats a lot), prefix caching keyed by file, and regional deployment close to users. Target TTFT under 150 ms.

Deep Dive: Capacity Planning an LLM Deployment

🔧 Intermediate

Goal: serve a 70B-class model (GQA, 320 KB/token KV in FP16) to a chat product with 400 requests/s at peak, average 2,000 input tokens (60% prefix-cached) and 300 output tokens, SLO: TTFT p95 \(<\) 1 s, TPOT p95 \(<\) 50 ms.

Step 1: concurrency (Little’s Law). Average request duration \(\approx\) 0.6 s TTFT \(+\) \(300\times 0.04\) s \(\approx\) 12.6 s. In-flight requests \(= 400 \times 12.6 \approx 5{,}000\).

Step 2: KV memory. Average context during generation \(\approx 2{,}000 + 150 = 2{,}150\) tokens. With FP8 KV (160 KB/token): \(5{,}000 \times 2{,}150 \times 160\,\text{KB} \approx 1.7\) TB of KV cache.

Step 3: per-replica capacity. One replica on 4 GPUs with 80 GB each (320 GB): weights in FP8 70 GB, overhead 30 GB, leaving about 220 GB of KV, enough for roughly \(220\text{\,GB}/(2{,}150\times160\text{\,KB}) \approx 640\) concurrent sequences. Benchmarking would confirm whether TPOT stays under 50 ms at that batch size; assume a safe operating point of 400 sequences per replica.

Step 4: replicas. \(5{,}000 / 400 \approx 13\) replicas, plus 30% headroom and one replica per zone for failure: about 18 replicas = 72 GPUs = 9 nodes.

Step 5: prefill check. Uncached input \(= 400 \times 2{,}000 \times 0.4 = 320\)K tokens/s. If one replica prefills about 30K tokens/s while still meeting TPOT (with chunked prefill), 13 replicas give 390K tokens/s, so prefill fits, but barely. Long-prompt bursts are the risk; that is the signal to consider disaggregated prefill or more aggressive prefix caching.

Step 6: cost. 72 GPUs at $2.50/h = $180/h. Output tokens/h \(= 400\times 300\times 3{,}600 = 432\)M at peak, so roughly $0.42 per million output tokens at peak; averaged over a day at 40% mean load, about $1 per million. Compare with API pricing for the same model class before deciding to self-host.

🧠 Expert

Things the simple model misses: output length variance (a few 4K-token answers hold KV far longer, so plan on p95 length, not mean), preemption under memory pressure (which wastes prefill work), tensor-parallel communication overhead, and diurnal load (autoscale replicas but keep a warm minimum because cold start is minutes). Always validate with a load test that replays a real distribution of prompt and output lengths, measuring goodput at your SLO, not peak tokens/s.

⚠️ Pitfall

  • Sizing for weights only and running out of KV cache memory at real concurrency.

  • Benchmarking with short prompts while production has 20K-token RAG prompts.

  • Round-robin load balancing across inference replicas.

  • Autoscaling on CPU or GPU utilization percentage (it reads near 100% even when idle-ish).

  • Quantizing without task-specific evals.

🔑 Takeaways

  • Prefill is compute-bound (TTFT); decode is memory-bound (TPOT).

  • Batching fills idle compute; KV cache memory limits the batch.

  • PagedAttention, prefix caching, and chunked prefill are standard; disaggregation is for scale.

  • Quantization and speculative decoding cut bytes and steps per token.

  • Optimize goodput and cost per million tokens; route by cache and load, not round robin.
