👋 Intro

How traffic is spread across servers: L4 vs L7, balancing algorithms, health checks, global load balancing, consistent hashing, and the reverse proxy that sits in front of nearly every production system.

Load Balancing

🌱 Beginner

A load balancer is the host at a busy restaurant who seats each new group at the table with the free waiter. If a waiter calls in sick, the host stops sending guests to that section. Nobody waits in a long line while other tables sit empty.

A load balancer exposes one virtual IP and removes failed servers from rotation.

L4 vs L7

Layer 4 (Transport) Layer 7 (Application)
Sees IP, port, TCP/UDP HTTP path, headers, cookies, gRPC method
Speed Very fast, millions of connections Slower; parses each request
Features Pass-through, TLS passthrough Path routing, TLS termination, retries, auth, compression
Examples AWS NLB, Maglev, IPVS, Katran AWS ALB, Nginx, Envoy, HAProxy, Traefik

L4 vs L7 load balancing

🔧 Intermediate

Algorithms:

  • Round robin: next server in turn. Good when requests are uniform.

  • Weighted round robin: bigger machines get more traffic.

  • Least connections / least outstanding requests: send to the least busy server. Best when request costs vary (and for LLM backends).

  • IP hash / consistent hash: same client or key goes to the same server. Needed for cache affinity and sticky sessions.

  • Power of two choices: pick two random servers, send to the less loaded. Nearly as good as global least-loaded with no shared state.

Health checks can be active (LB pings /healthz every few seconds) or passive (outlier detection: eject a host after 5 consecutive 5xx). Distinguish liveness (process alive) from readiness (able to take traffic, e.g. warm cache, DB connected).

Consistent Hashing

Consistent hash ring with virtual nodes (A’, B’, C’). Adding or removing a node only moves about \(1/N\) of keys.

🧠 Expert

With naive hash(key) mod N, changing \(N\) remaps nearly every key, destroying cache hit rates. Consistent hashing maps both nodes and keys onto a ring; each key belongs to the next node clockwise. Virtual nodes (100–200 per physical node) smooth out uneven distribution. Alternatives: rendezvous (HRW) hashing (score every node, pick the max: simple, no ring), jump consistent hash (no memory, but only supports appending buckets), and Google’s Maglev hashing (lookup-table based, used in L4 LBs). Bounded-load consistent hashing caps any node at \((1+\epsilon)\times\) average load, which matters for hot keys.

🔧 Intermediate

Worked example: how much moves? 10 cache nodes, 100M keys.

  • hash(key) mod N, going from 10 to 11 nodes: a key stays put only if h mod 10 = h mod 11, which is true for about 1 in 11 keys. About 91% of keys move, so the hit rate collapses.

  • Consistent hashing, going from 10 to 11 nodes: only keys in the new node’s ranges move, about \(1/11 \approx 9\%\).

  • Without virtual nodes, the largest node’s share can easily be 2–3\(\times\) the average because random points on a ring leave uneven gaps. With 100–200 virtual nodes per server, the spread typically falls to within a few percent.

import bisect, hashlib

def h(s): return int(hashlib.md5(s.encode()).hexdigest()[:16], 16)

class Ring:
    def __init__(self, nodes, vnodes=150):
        self.ring = sorted((h(f"{n}#{i}"), n) for n in nodes for i in range(vnodes))
        self.points = [p for p, _ in self.ring]

    def node_for(self, key):
        i = bisect.bisect(self.points, h(key)) % len(self.points)  # next clockwise
        return self.ring[i][1]
📦 Use case: Seen in production

Discord routes every request for a channel to the same data-service instance by consistent hashing so duplicate reads can be coalesced; Slack assigns channels to channel servers on a hash ring managed by CHARMs; Uber’s Ringpop shards geographic cells across dispatch servers. See Part (cases).

Global Load Balancing

🔧 Intermediate

Multi-region systems route users to the nearest healthy region using GeoDNS, anycast IPs (Cloudflare, Google Cloud global LB), or latency-based routing. Inside a region a second tier of L4/L7 balancers distributes to services.

📦 Use case: Multi-region SaaS failover

Anycast routes EU users to Frankfurt and US users to Virginia. Frankfurt’s health checks fail; BGP withdraws the route and users land in Virginia within seconds. The application must tolerate higher latency and be able to serve EU users’ data from the US (or fail gracefully if data residency forbids it).

📦 Use case: LLM inference fleet

Round robin works poorly for LLMs: one request may be 50 tokens, another 50,000. Inference gateways route by queue depth and KV-cache usage, and prefer the replica that already has the prompt prefix cached (prefix-aware routing). See Chapter (inference).

Reverse Proxies

🌱 Beginner

A reverse proxy is a receptionist for a building. Visitors talk only to the receptionist, who forwards them to the right office. Visitors never learn the internal room numbers.

Reverse proxies act on behalf of servers; forward proxies act on behalf of clients.

🔧 Intermediate

Responsibilities: TLS termination, HTTP/2 and HTTP/3 to clients, compression (gzip/Brotli/Zstd), response caching, request buffering (protects slow servers from slow clients), path and host routing, header rewriting, WAF rules, and connection pooling to backends. Popular choices: Nginx (mature, config-file driven), Envoy (dynamic config via xDS APIs, the base of most service meshes and AI gateways), HAProxy (high-performance L4/L7), Caddy (automatic HTTPS), Traefik (auto-discovers containers).

🧠 Expert

Things that bite in production: proxies buffer responses by default, which breaks streaming (set proxy_buffering off or X-Accel-Buffering: no for SSE); idle timeouts shorter than a long LLM generation will cut streams; proxies must forward real client IPs via X-Forwarded-For or PROXY protocol, and you must only trust these headers from known hops. Connection reuse to backends (keep-alive) often matters more for latency than any other knob.

📦 Use case: Monolith to microservices migration

Nginx sits in front of the monolith. New services are added behind it and paths are moved one at a time (/payments now routes to the new payments service). This is the strangler fig pattern: the old system shrinks until it can be removed, and users never notice.

⚠️ Pitfall

  • Load balancer itself as a single point of failure; run it in an HA pair or use a managed LB.

  • Health checks that only test “process up,” sending traffic to servers that cannot reach the DB.

  • Sticky sessions that pin heavy users and defeat balancing; prefer stateless services.

  • Health check endpoints that call dependencies, causing cascading ejection of every server when the DB blips.

🔑 Takeaways

  • L4 for raw speed, L7 for smart routing.

  • Least-outstanding-requests beats round robin when request cost varies.

  • Consistent hashing keeps caches warm as nodes change.

  • Reverse proxies centralize TLS, compression, routing, and protection.
