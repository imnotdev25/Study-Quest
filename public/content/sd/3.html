👋 Intro

The front door of a microservice system: what API gateways do, BFFs, the four main rate-limiting algorithms, distributed rate limiting with Redis, and how AI gateways limit by tokens instead of requests.

API Gateways

🌱 Beginner

An API gateway is an airport security checkpoint. Every passenger passes through one place where tickets are checked (authentication), bags are scanned (validation), crowds are metered (rate limiting), and people are pointed to their gate (routing).

API gateway handles cross-cutting concerns so services can focus on business logic.

🔧 Intermediate

Gateway responsibilities: authentication (API keys, OAuth2 JWT validation, mTLS), authorization hooks, rate limiting and quotas, request routing and canary splits, protocol translation (REST to gRPC), request/response transformation, response aggregation, caching, CORS, and observability.

Backend for Frontend (BFF): instead of one gateway for all clients, run one per client type. The mobile BFF returns compact payloads that combine three services into one call; the web BFF returns richer data.

Products: Kong, AWS API Gateway, Apigee, Azure API Management, Tyk, Envoy Gateway, and Kubernetes Gateway API implementations (the successor to Ingress, now the standard way to configure L7 routing in Kubernetes).

🧠 Expert

Keep gateways thin. Business logic in the gateway creates a distributed monolith that every team must deploy through. Put domain aggregation in BFFs or GraphQL federation (a supergraph composed from per-team subgraphs). Gateways are in every request’s path, so latency budget matters: JWT validation with cached JWKS keys is microseconds; calling an auth service per request is milliseconds and a new failure dependency. Run gateways in multiple zones and treat their config as code with staged rollouts. A bad gateway config push is a global outage.

📦 Use case: Public developer platform

A payments company exposes api.example.com. The gateway validates API keys, applies per-plan quotas (free: 100 req/min, enterprise: 10,000), enforces idempotency keys on POST, records usage for billing, and routes /v1 and /v2 to different service versions.

Rate Limiting

🌱 Beginner

A nightclub bouncer lets in a fixed number of people per minute. Arrive too fast and you are asked to wait. This protects everyone inside: the club never gets dangerously packed, and one big group cannot take every spot.

Rate limiting protects against abuse and overload, enforces fairness and business tiers, and controls cost (critical for LLM APIs, where each request burns GPU time).

Algorithms

Token bucket allows bursts up to \(b\); leaky bucket smooths output to a constant rate.

Algorithm How it works Pros / Cons Used by
Token bucket Bucket of \(b\) tokens refilled at \(r\)/s; each request spends one Allows bursts, \(O(1)\) memory AWS, Stripe
Leaky bucket Queue drained at fixed rate Smooth output; adds queueing delay Nginx limit_req
Fixed window Counter per minute Simple; 2\(\times\) burst at window edges Basic quotas
Sliding log Store every timestamp Exact; memory heavy Low volume, strict
Sliding window counter Weighted mix of current and previous window Accurate, cheap Cloudflare

Rate-limiting algorithms

🔧 Intermediate

Sliding window counter estimate: \[\text{count} \approx \text{curr} + \text{prev}\times\frac{\text{window} - \text{elapsed}}{\text{window}}\] With a 60 s window, 40 requests in the previous window, 20 so far, and 15 s elapsed: \(20 + 40\times 45/60 = 50\).

Respond with 429 Too Many Requests and headers: Retry-After, RateLimit-Limit, RateLimit-Remaining, RateLimit-Reset. Limit keys can be user ID, API key, IP, tenant, or endpoint, and you usually layer several (per-IP at the edge, per-tenant at the gateway, per-dependency inside services).

Distributed Rate Limiting

A shared counter store makes limits global across gateway instances.

-- KEYS[1]=bucket key  ARGV: rate, capacity, now_ms, cost
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local rate, cap, now, cost = tonumber(ARGV[1]), tonumber(ARGV[2]),
                             tonumber(ARGV[3]), tonumber(ARGV[4])
local tokens = tonumber(b[1]) or cap
local ts     = tonumber(b[2]) or now
tokens = math.min(cap, tokens + (now - ts) / 1000 * rate)   -- refill
local allowed = tokens >= cost
if allowed then tokens = tokens - cost end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate * 1000))
return { allowed and 1 or 0, tokens }
🧠 Expert

A central Redis adds a network hop per request and becomes a hot spot. Options at scale: (1) local token buckets with periodic sync: each node gets a share of the global limit and reconciles every few hundred ms (slightly inaccurate, very fast); (2) sharded counters by key; (3) fail-open vs fail-closed decision when Redis is down: fail open for user-facing traffic (accept a short overrun), fail closed for cost-sensitive or security limits (login attempts). Envoy’s global rate limit service and Cloudflare’s edge limiter use these hybrids.

Load shedding differs from rate limiting: it drops work based on server health (CPU, queue depth, latency) rather than a client quota, and should drop lowest-priority traffic first. Adaptive concurrency limits (Netflix’s concurrency-limits, based on TCP Vegas-style latency gradients) find the right concurrency automatically.

📦 Use case: Login brute-force protection

Limit by IP (20 attempts/min) and by username (5 failures/15 min, then exponential lockout). Fail closed if the limiter store is unreachable.

📦 Use case: LLM API token-based limits

Request counts are meaningless when one request is 10 tokens and another is 100K. LLM providers limit requests per minute (RPM), input tokens per minute (ITPM), and output tokens per minute (OTPM). The gateway estimates input tokens before forwarding, reserves max_tokens of output budget, and refunds the unused part after the response completes. Tenants also get monthly spend caps.

⚠️ Pitfall

  • Limiting only by IP: NATs and mobile carriers put thousands of users behind one IP.

  • Not returning Retry-After, so clients retry immediately and make overload worse.

  • Rate-limiting check that is slower than the work it protects.

🔑 Takeaways

  • Gateways centralize auth, limits, routing, and telemetry; keep them free of business logic.

  • Token bucket is the default algorithm; sliding window counter for accurate quotas.

  • Distributed limits need a shared store or approximate local shares.

  • AI systems limit by tokens and cost, not just requests.
