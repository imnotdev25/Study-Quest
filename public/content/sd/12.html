👋 Intro

Moving large bytes efficiently and safely: direct-to-object-storage uploads with signed URLs, image CDNs and on-the-fly resizing, an avatar service, multipart and resumable video uploads, the transcoding pipeline, adaptive bitrate and CDN selection, content protection (signed URLs, DRM, watermarking), live streaming and WebRTC, and file sync with content-defined chunking and versioned block lists.

Direct-to-Object-Storage Upload

🌱 Beginner

If you send a parcel to a warehouse, you do not hand it to the receptionist to carry across the building. The receptionist gives you a slip that lets you drop it at the loading dock yourself. App servers should not carry gigabytes of video either: they hand the client a signed permission slip and the client uploads straight to storage.

The client uploads directly; the app server only authorizes.

🔧 Intermediate

  1. The client asks the API to upload (file name, size, content type). The API checks authorization and quotas, creates a metadata row with status PENDING, and returns a presigned URL: a URL with an expiry time and a signature that grants permission to PUT exactly one object key, optionally with a required content type, maximum size, and checksum (presigned POST policies can enforce size limits).

  2. The client uploads to the object store directly.

  3. The object store emits an event (S3 Event Notifications) or the client calls complete; a worker validates the file (real type by magic bytes, size, malware scan, content moderation), then marks the row READY.

App servers never touch the bytes, so they need no large buffers or long-lived connections. Generate keys server-side (random or content hash), never from the user’s file name.

Image CDN and Resizing

🔧 Intermediate

Clients need many sizes and formats (thumbnail, feed, full screen; WebP or AVIF for browsers that support them, JPEG otherwise). Two approaches:

  • Pre-generate a fixed set of renditions at upload: predictable cost and latency, wasted storage for sizes never requested.

  • Resize on the fly at the edge: the URL encodes the transform (/img/abc123?w=400&fmt=auto); the CDN caches each variant; on a miss an image service fetches the original (through an origin shield, a mid-tier cache that protects storage from many edges missing at once), resizes, and returns it. Restrict allowed sizes to a whitelist so attackers cannot generate unlimited variants (a cache and compute exhaustion attack).

Use Vary: Accept or format-specific URLs for format negotiation, strip EXIF metadata (GPS location) from public images, and set long cache lifetimes because image URLs are immutable.

An Avatar Service

🔧 Intermediate

Avatars are read on almost every page and change rarely. Store each upload as an immutable, content-addressed object (key = hash of the processed image) and store the current avatar’s hash on the user row. The URL embeds the hash (/avatars/{hash}/96.webp), so it can be cached forever; changing your avatar changes the URL, which is instant cache invalidation without purging. Serve a default avatar (or generated initials) when none exists. Moderate uploads asynchronously and keep the previous avatar until the new one passes.

Video Upload: Multipart and Resumable

🔧 Intermediate

Large files must survive flaky networks. S3 multipart upload: initiate an upload (get an upload ID), upload parts in parallel (each part 5 MB to 5 GB except the last; up to 10,000 parts; objects up to 5 TB), each with its own presigned URL and checksum, then complete with the list of part numbers and ETags. Failed parts are retried individually; a lifecycle rule aborts incomplete uploads after a few days so orphaned parts do not accumulate cost. Resumable uploads (the tus protocol, Google’s resumable upload API) let the client ask the server “how many bytes do you have?” after a disconnect and continue from there.

Video Transcoding Pipeline

A transcoding DAG: segments encode in parallel.

🔧 Intermediate

The pipeline is a DAG of jobs in a workflow engine: probe the input (codec, resolution, duration), split into segments at keyframes (GOP boundaries) so segments can be encoded independently and in parallel, encode each segment into every rung of the bitrate ladder (several resolution/bitrate pairs; per-title encoding tunes the ladder to each video’s complexity), then concatenate and package into HLS and/or DASH: short segments (2–6 seconds) plus manifests listing the variants. Generate thumbnails, run content ID and moderation, extract captions. Each step is idempotent (output keyed by input hash and parameters) so retries and spot-instance interruptions are cheap. The YouTube case study (Part (cases)) describes a production version.

Adaptive Bitrate and the CDN Decider

🔧 Intermediate

The player chooses which rung to fetch for each segment: throughput-based algorithms estimate bandwidth from recent downloads; buffer-based algorithms (BOLA) choose by how many seconds are buffered; hybrids are common. Start low for a fast first frame, ramp up, and drop before the buffer empties to avoid stalls.

A CDN decider (steering service) runs at playback start and picks which CDN or edge cluster serves this session, based on real-time quality of experience data (startup time, rebuffering, throughput by ISP and region), cost commitments, capacity, and health. It returns ordered URLs so the player can fail over mid-stream. Netflix’s playback service does this for its own Open Connect appliances; multi-CDN companies do it across vendors.

Signed URLs, DRM, and Video Security

🔧 Intermediate

  • Signed URLs or cookies (CloudFront, Cloud CDN) restrict access to paid content for a short time; a signed cookie covers all segments of one stream. They stop link sharing, not screen recording or downloading by the viewer.

  • DRM: segments are encrypted (Common Encryption, AES-128 CTR or CBCS mode, so one set of files works for several DRM systems); the player obtains a decryption key from a license server after the app proves the user is entitled. Widevine (Android, Chrome), FairPlay (Apple), and PlayReady (Windows, many TVs) keep keys inside protected hardware or software modules, and enforce output rules (HD only on secure hardware, no screen capture).

  • Forensic watermarking embeds an invisible per-session identifier in the video, so leaked copies can be traced (A/B watermarking switches between two pre-watermarked variants per segment at the CDN).

  • Key rotation for live streams limits the damage of a leaked key.

Low-latency HLS / DASH partial segments, chunked transfer 2–5 s millions via CDN
WebRTC real-time media over UDP (SRTP) \(<\) 0.5 s needs SFU fan-out; costly at huge scale
🔧 Intermediate

Live pipeline: the broadcaster sends RTMP, SRT, or WebRTC (WHIP) to an ingest server; a live transcoder produces the ladder in real time; a packager writes segments and updates manifests every few seconds; the CDN serves them. Choose by interactivity: sports and concerts accept a few seconds; auctions, betting, and live shopping want sub-second; video calls require WebRTC.

WebRTC connects peers with ICE: try direct connections, use STUN to learn the public address behind NAT, and fall back to a TURN relay when direct connection fails (often 10–20% of sessions, and TURN bandwidth is a real cost). For group calls, mesh (everyone sends to everyone) works for 3–4 people; an SFU (selective forwarding unit) receives each participant’s stream once and forwards it to others, often with simulcast (each sender uploads several qualities and the SFU forwards the right one per receiver); an MCU mixes streams into one, costly in CPU. Large webinars combine an SFU for speakers with HLS for the audience.

Remote File Sync

File sync: separate metadata (small, transactional) from blocks (large, immutable).

Chunking and Content Addressing

🔧 Intermediate

Split each file into blocks and identify each block by a cryptographic hash (SHA-256): content addressing. Identical blocks (in different versions or different users’ copies of the same file) are stored once; an upload sends only blocks the server does not already have.

  • Fixed-size blocks (Dropbox used 4 MB): simple; but inserting one byte at the start shifts every boundary, so every block’s hash changes.

  • Content-defined chunking (Rabin fingerprints, FastCDC): place boundaries where a rolling hash of the last few bytes matches a pattern, so boundaries move with the content; an insertion changes only nearby chunks. Average chunk size is controlled by the pattern’s probability, with min and max limits.

  • rsync’s rolling weak checksum plus strong hash finds matching blocks at any offset when syncing two versions over a network.

Note the privacy trade-off: cross-user deduplication can reveal that someone else already uploaded a given file (the upload is suspiciously fast); many services deduplicate only within one user’s or team’s namespace, or use convergent encryption with care.

Block-List Versioned File Metadata

🔧 Intermediate

A file version is metadata: (namespace, path, version, size, mtime, block_list = [h1, h2, h3]). Each namespace (a user’s root or a shared folder) has an append-only journal of changes with a monotonically increasing sequence number. Upload: chunk and hash locally; ask the metadata service to commit the new block list; it replies with the hashes it lacks; upload those to the block service; retry the commit, which succeeds once all blocks exist. Download: the client keeps a cursor (last journal position seen), asks for changes since the cursor (woken by a long-poll or push notification), and fetches only missing blocks. Conflicts: a commit includes the version it was based on; if the server has a newer version, the client saves its copy as “file (conflicted copy)” rather than overwriting. Deleted versions and blocks are retained for a recovery window, then garbage-collected by reference counting or mark-and-sweep.

📦 Use case: Design Dropbox in an interview

Separate the metadata service (sharded by namespace, strongly consistent, transactional commits) from the block store (content-addressed, immutable, object storage). Clients chunk, hash, and upload only missing blocks; sync via cursors over a per-namespace journal; notifications by long polling; conflicts become conflicted copies. 🔑 Takeaways

  • Upload bytes directly to object storage with short-lived presigned URLs; process asynchronously.

  • Content-addressed, immutable media URLs can be cached forever; changing content changes the URL.

  • Transcode segments in parallel into a bitrate ladder; let players adapt and a steering service pick CDNs.

  • Choose HLS, low-latency HLS, or WebRTC by required interactivity.

  • File sync = chunking + hashing + block lists in a versioned journal + upload only what is missing.
