👋 Intro

Eight systems that move messages to millions of connected clients or between thousands of services: Slack, WhatsApp, Discord, Netflix, LinkedIn, Facebook Live, McDonald’s, and Uber.

The common thread.

Real-time systems split into a stateful edge that holds connections and a stateless or sharded core that decides where messages go. Almost every case below has a connection layer, a routing layer based on consistent hashing, and a fan-out step. The hard problems are reconnect storms, hot channels, and knowing where each user is connected.

Case: Slack: The Journey of a Message

📋 Case facts

Domain: Workplace chat
Scale: Tens of millions of channels per host; about 500 ms global delivery
Concepts: WebSockets, consistent hashing, stateful services, regional edges, presence
Source: Slack engineering blog, “Real-time Messaging” (2023)

Slack’s real-time path: send via HTTP, fan out via WebSockets.

The components.

  • Channel Servers (CS) are stateful, in-memory Java services holding recent history for channels. Each CS owns a set of channels via consistent hashing; at peak a host serves about 16 million channels. “Channel” is abstract: a user, a team, a file, a huddle, or a regular channel.

  • CHARMs (consistent hash ring managers) keep the ring healthy and replace a failed CS in under 20 seconds. Ring configuration lives in Consul.

  • Gateway Servers (GS) hold each user’s WebSocket and its channel subscriptions. They are the only part deployed in many regions, so users connect nearby. A region can be drained by moving users to the next healthy one.

  • Admin Servers (AS) are stateless and connect the main web application to channel servers.

  • Presence Servers track online status; clients only subscribe to presence for users visible on screen.

Following one message.

The client sends the message by an ordinary HTTP API call to Webapp, which persists it and hands it to an Admin Server. The AS looks up the owning Channel Server on the hash ring. The CS sends it to every Gateway Server subscribed to that channel worldwide, and each GS pushes it to its connected clients. Ephemeral events like “typing…” skip persistence and go client \(\to\) GS \(\to\) CS \(\to\) GSs directly.

Why sending uses HTTP, not the socket.

Writes need authentication, validation, persistence, and idempotency, which the regular web stack already does well. WebSockets are used where they are strong: low-latency push. This split also means a WebSocket outage does not lose messages; clients can still send and fetch over HTTP.

📚 Lesson

  • Separate the write path (HTTP, durable) from the push path (WebSocket, best-effort plus resync).

  • Consistent hashing of channels to stateful servers keeps state in memory without a shared bottleneck.

  • Only push what the user can see (presence for visible users) to cut fan-out.

Case: WhatsApp: Millions of Connections per Server with Erlang

📋 Case facts

Domain: Messaging
Scale: About 2M TCP connections per server (2012); 900M users with about 50 engineers (2015)
Concepts: Lightweight processes, vertical scaling, store-and-forward, simplicity
Source: WhatsApp engineering blog (2012); Rick Reed, Erlang Factory talks (2012, 2014)

The design philosophy.

WhatsApp is the strongest counterexample to “you need hundreds of microservices.” The backend was written in Erlang on FreeBSD, running on relatively few large machines.

  • Erlang processes are extremely light (a few hundred bytes of initial memory, scheduled by the BEAM VM, not the OS). One process per connection is natural, and a crash in one process cannot corrupt another. Supervisors restart failed processes automatically: “let it crash.”

  • Kernel and VM tuning (file descriptor limits, network buffers, BEAM scheduler settings, lock contention fixes) took a single server to about 2 million concurrent TCP connections in 2012.

  • Store and forward. The server keeps a message only until the recipient’s device acknowledges it, then deletes it. Messages are stored on devices, not servers. This keeps server storage small and, later, made end-to-end encryption (Signal Protocol, 2016) a natural fit.

  • Mnesia, Erlang’s built-in distributed database, held routing and offline-message data, partitioned across nodes.

Delivery receipts.

The single tick means the server stored it; two ticks mean the recipient’s device received it; blue ticks mean it was read. Each is just a small acknowledgement message flowing back, which is how the at-least-once delivery pipeline is made visible to users.

📚 Lesson

  • The right runtime (Erlang/BEAM, Elixir) can replace a lot of distributed infrastructure.

  • Not storing data you do not need (store and forward) removes whole classes of scaling problems.

  • Small teams scale when the architecture stays simple.

Case: Discord: Fan-Out with Elixir

📋 Case facts

Domain: Chat and voice
Scale: Millions of concurrent users; servers with hundreds of thousands of members
Concepts: Actor model, fan-out, batching, back-pressure
Source: Discord engineering blog, “How Discord Scaled Elixir to 5,000,000 Concurrent Users” (2017)

The design.

Each Discord server (“guild”) is an Elixir GenServer process holding its state. Each connected user has a session process. When someone posts, the guild process sends the event to the session processes of every online member. For a guild with 100,000 online members, one event becomes 100,000 messages, often across many machines.

Problems and fixes.

  • Cross-node fan-out cost. Sending to many remote processes one by one is slow. Discord built Manifold, which groups recipients by node, sends one batch per node, and lets a process on that node fan out locally. This divides network traffic and CPU on the sender.

  • Hot reads of shared data. A lookup table read by every process became a bottleneck; FastGlobal compiles rarely changing data into a module so reads are constant time with no copying.

  • Overload protection. A semaphore library limits how many concurrent requests reach a service, rejecting excess rather than queueing without bound.

  • Big guilds: relays and passive sessions (users who are not actively looking do not get every event) cut work further.

📚 Lesson

  • Batch fan-out per destination node instead of per recipient.

  • Send fewer events to inactive users; fan-out cost is the product of rate and audience.

  • Bounded concurrency (semaphores) is a simple, strong overload defense.

Case: Netflix: Zuul Push

📋 Case facts

Domain: Streaming
Scale: Millions of always-on connections
Concepts: WebSockets/SSE, push registry, reconnect storms, autoscaling on connections
Source: Netflix TechBlog, “Zuul Push Messaging Service” (2018)

Why push?

Netflix’s apps used to poll the backend for things like updated recommendations. Push lets servers notify devices directly (“a new row is ready, refresh it”), reducing wasted requests and making the UI feel live.

Netflix Zuul Push.

The design.

Push servers are built on Netty (non-blocking I/O) and hold WebSocket or SSE connections. When a device connects and authenticates, the server records user_id \(\to\) server in a push registry (a low-latency store with TTLs). Backend services publish a message through a push library to Kafka; a message processor looks up which server holds the user’s connection and forwards it there.

Operational lessons reported.

  • Reconnect storms. If a push server dies or is deployed, all its clients reconnect at once. Connections are given a maximum lifetime with randomized jitter, so reconnects are spread out, and clients back off.

  • Scale on connections, not CPU. Push servers are mostly idle CPU holding many connections; autoscale on open connection count.

  • Prefer many smaller instances, so losing one causes a smaller storm.

  • Load balancers must support long-lived connections (and WebSocket upgrade), with idle timeouts set accordingly.

📚 Lesson

  • A connection registry (user to server) is the core of any push system.

  • Plan for thundering-herd reconnects: jittered lifetimes and client backoff.

  • Autoscale stateful connection servers on connections, not CPU.

Case: LinkedIn: The Birth of Kafka

📋 Case facts

Domain: Professional network
Scale: Trillions of messages per day across LinkedIn’s Kafka clusters (later years)
Concepts: Log abstraction, pub/sub, data integration, stream processing
Source: Jay Kreps, “The Log: What every software engineer should know…” (2013); Kafka paper (NetDB 2011)

The problem.

By around 2010 LinkedIn had many data sources (databases, user activity events, metrics) and many destinations (Hadoop, search indexes, the social graph, monitoring). Connecting each source to each destination created an \(N\times M\) web of custom pipelines that were fragile and slow.

From \(N\times M\) pipelines to \(N+M\) connections through one log.

The design.

Kafka was built around one idea: an append-only, partitioned, replicated log. Producers append; consumers read at their own pace by offset. Messages are retained by time, so slow or new consumers can replay. Performance came from simple, mechanical choices: sequential disk writes, relying on the OS page cache instead of an in-process cache, batching, and zero-copy transfer from file to network socket (sendfile).

The bigger idea.

Kreps argued that a log is the backbone of data integration: every database is internally a log plus a materialized view, so exposing the log lets any system build its own view. That idea underlies change data capture, event sourcing, stream processing (Kafka Streams, Flink), and the “turning the database inside out” approach.

📚 Lesson

  • A central log turns \(N\times M\) integrations into \(N+M\).

  • Simple storage design (sequential I/O, page cache, batching) can beat complex in-memory brokers.

  • Retention and replay make new consumers and reprocessing cheap.

Case: Facebook Live: Surviving the Thundering Herd

📋 Case facts

Domain: Live video
Scale: Popular streams watched by millions at once
Concepts: Edge caching, request coalescing, origin protection
Source: Facebook engineering, “Under the hood: Broadcasting live video to millions” (2015)

The problem.

Live video is cut into short segments. When a celebrity goes live, a huge number of viewers request the same newest segment at the same moment, and that segment is not cached yet because it was just created. Every edge cache misses at once and forwards to the origin.

The design.

Viewers fetch segments from edge cache servers (points of presence), which fetch from origin servers, which fetch from the encoding servers. At each layer, request coalescing holds concurrent requests for the same segment: the first request goes upstream, the rest wait and receive the same response. In the reported design this cut the load reaching the origin to a small fraction (the post describes most requests being absorbed at the edge). Broadcasters’ streams were also consistently hashed to specific encoding servers.

📚 Lesson

  • Coalescing is the main defense when many clients want the same new object.

  • Every caching tier should coalesce, not just the last one.

  • Live content behaves very differently from on-demand content: there is no warm cache to rely on.

Case: McDonald’s: Event-Driven Architecture

📋 Case facts

Domain: Global restaurant chain / mobile ordering
Scale: Spiky regional traffic around promotions and meal times
Concepts: Managed Kafka, schema registry, outbox, dead-letter queues
Source: McDonald’s Technical Blog, “Behind the scenes: event-driven architecture at McDonald’s” (2022)

The design.

McDonald’s built a shared event platform so teams (mobile ordering, loyalty, deals, operations) could publish and consume events reliably:

  • Amazon MSK (managed Kafka) as the event backbone.

  • A schema registry that every event must be validated against before publishing, so a producer cannot break consumers with malformed data.

  • An SDK for producers and consumers that handles serialization, validation, retries, and error handling consistently.

  • When Kafka is unavailable, events are written to an outbox (a DynamoDB table) and published later, so producers do not lose events.

  • Dead-letter topics for events that fail processing, with tooling to inspect and replay them.

  • Custom domain-based sharding of events and autoscaling of consumers.

📚 Lesson

  • A shared event platform needs governance: schemas, SDKs, and standard error handling.

  • Plan for the broker being down (outbox fallback).

  • Dead letters need tooling to replay, not just a place to rot.

Case: Uber: Real-Time Push to Riders and Drivers

📋 Case facts

Domain: Mobility
Scale: Millions of connected apps; constant state changes per trip
Concepts: Server push, streaming RPC, at-least-once delivery, sequence numbers
Source: Uber engineering blog posts on RAMEN and its gRPC migration (2020–2022)

The problem.

During a trip, the rider and driver apps need a stream of updates: driver location, ETA, trip status, pricing, messages. Polling every few seconds wastes battery and data and adds latency.

The design.

Uber built a push platform (RAMEN, “Realtime Asynchronous MEssaging Network”) that keeps a persistent connection per app. Backend services send messages with metadata (priority, time-to-live). The platform sequences messages per user, and the client acknowledges what it has received; after a reconnect the client reports its last sequence number and the server replays what is missing. Uber later moved the transport from SSE to gRPC bidirectional streaming over HTTP/2 (and investigated QUIC), which gave a standard protocol for acknowledgements and better behavior on poor mobile networks.

📚 Lesson

  • Sequence numbers plus client acks turn an unreliable connection into reliable delivery.

  • Prioritize and expire messages: a stale location update is worthless.

  • Mobile networks are hostile; choose transports that survive network changes.
