👋 Intro

What system design is, how to measure a system (latency, throughput, availability), how systems scale, the CAP and PACELC theorems, consistency models, and back-of-the-envelope estimation.

What Is System Design?

🌱 Beginner

Imagine opening a small restaurant. On day one, one cook takes orders, cooks, and serves. When 500 people show up, you need more cooks (scaling), a waiter to hand out orders (load balancer), pre-made sauces (cache), a ticket rail for orders (queue), and a backup generator (redundancy). System design is planning the restaurant before the crowd arrives.

Every design starts from two kinds of requirements:

  • Functional requirements: what the system does (“users can post a photo”).

  • Non-functional requirements: how well it does it: latency, availability, durability, consistency, cost, security, compliance.

Non-functional requirements drive almost every architectural decision.

Measuring a System

🔧 Intermediate

  • Latency: time for one request. Always report percentiles (p50, p95, p99, p99.9), never just averages.

  • Throughput: work per unit time (QPS, tokens/s, MB/s).

  • Availability: fraction of time the system serves correctly.

  • Durability: probability data is never lost (S3: 11 nines).

  • SLI / SLO / SLA: the indicator you measure (p99 latency), the internal objective (p99 \(<\) 200 ms for 99.9% of minutes), and the external agreement with penalties.

🧠 Expert

Availability composes. Components in series multiply: two 99.9% services in a chain give \(0.999^2 \approx 99.8\%\). Redundant components in parallel give \(1-(1-a)^n\): two 99% replicas give 99.99%. This is why every critical dependency needs redundancy, and why deep call chains quietly erode your SLO.

Tail latency amplifies with fan-out. If one backend has a 1% chance of being slow and a request fans out to 100 backends, the chance at least one is slow is \(1-0.99^{100}\approx 63\%\). Mitigations: hedged requests (send a duplicate after the p95 deadline), tied requests, and reducing fan-out.

Little’s Law: \(L = \lambda W\). Concurrency equals arrival rate times latency. 2,000 QPS at 250 ms needs \(\approx 500\) requests in flight, which sizes thread pools, connection pools, and GPU batch slots.

Scaling: Vertical vs Horizontal

🌱 Beginner

Vertical scaling is buying a bigger oven. Horizontal scaling is buying more ovens. Bigger ovens are simple but have a size limit and are a single point of failure. More ovens scale further but need coordination.

Classic horizontally scaled web tier. State lives in the cache and database, so app servers are interchangeable.

🔧 Intermediate

The key to horizontal scaling is statelessness: any server can handle any request because session state lives in a shared store (Redis, DB, or a signed token). Then the scaling playbook is:

  1. Separate app and database; add a load balancer and multiple app servers.

  2. Add caching (CDN for static, Redis for hot data).

  3. Add read replicas for read-heavy workloads.

  4. Move slow work to async queues.

  5. Shard (partition) the database when writes outgrow one node.

  6. Split into services along team and domain boundaries when needed.

  7. Go multi-region for latency and disaster recovery.

📦 Use case: Startup growth from 1K to 10M users

1K users: one VM running app plus Postgres. 100K: managed Postgres, two app instances behind a load balancer, CDN for images. 1M: Redis cache, read replicas, background workers on a queue. 10M: sharded data or a distributed SQL database, separate services for search and notifications, multi-region read paths. Each step is taken only when measurements show the current bottleneck.

CAP, PACELC, and Consistency

🌱 Beginner

Two bank branches share one ledger over a phone line. The line goes dead. A customer wants to withdraw money. Either branch can (a) refuse until the line is back (consistent, not available), or (b) allow it and reconcile later (available, maybe inconsistent). You cannot have both while the line is cut. That is CAP.

CAP theorem. In a distributed system partitions will happen, so the real choice is C or A during a partition.

🔧 Intermediate

PACELC extends CAP: if Partition, choose Availability or Consistency; Else, choose Latency or Consistency. Even with no failures, strong consistency costs latency because replicas must coordinate.

Consistency models from strongest to weakest:

  • Linearizable: every read sees the latest write, as if one copy.

  • Sequential: all nodes see operations in the same order.

  • Causal: cause-effect order preserved (reply after comment).

  • Read-your-writes: you always see your own updates.

  • Eventual: replicas converge if writes stop.

🧠 Expert

Quorum systems tune the trade-off per request. With \(N\) replicas, write quorum \(W\) and read quorum \(R\), choosing \(R+W>N\) guarantees read and write sets overlap. \(N{=}3,W{=}2,R{=}2\) is the classic balance. \(W{=}1,R{=}1\) is fast and eventually consistent. Note that quorum overlap alone is not linearizability: sloppy quorums, hinted handoff, and concurrent writes with last-write-wins can still produce anomalies. Real systems add vector clocks, CRDTs, or consensus (Raft/Paxos) where correctness matters. Spanner achieves external consistency using TrueTime (GPS plus atomic clocks) with bounded clock uncertainty and commit-wait.

📦 Use case: Choosing CP vs AP

Bank balance / inventory count (CP): better to reject a purchase than sell the same seat twice. Use a strongly consistent DB or consensus. Social media like count (AP): showing 1,203 instead of 1,204 for a second is fine; availability matters more. Shopping cart (AP with merge): Amazon’s Dynamo paper let carts accept writes during partitions and merge them later, accepting a resurrected item over a lost sale.

Back-of-the-Envelope Estimation

🔧 Intermediate

Useful constants: 1 day \(\approx 10^5\) seconds (86,400). 1M requests/day \(\approx\) 12 QPS. Peak is typically 2–5\(\times\) average.

Example: a photo app with 100M daily active users.

  • Each user views 50 photos and uploads 0.1 per day.

  • Read QPS \(= 100\text{M}\times 50 / 10^5 = 50{,}000\) avg, \(\sim\)150K peak.

  • Write QPS \(= 100\text{M}\times 0.1 / 10^5 = 100\) avg.

  • Storage \(= 10\text{M photos/day} \times 2\text{ MB} = 20\) TB/day, \(\approx 7.3\) PB/year before replication.

  • Read:write ratio of 500:1 means caching and a CDN dominate the design.

How a Server Handles Many Requests

🌱 Beginner

A restaurant can hire one waiter per table (simple, but expensive when there are thousands of tables), or a few waiters who never stand still: they take an order, move on while the kitchen cooks, and come back when the food is ready. Servers make the same choice.

🔧 Intermediate

  • Process or thread per request (classic Apache, many Java servlet containers): simple blocking code; each thread costs memory (often 0.5–1 MB of stack) and context switches, so thousands of slow connections exhaust the server.

  • Thread pool + queue: a fixed number of workers take requests from a bounded queue. Little’s Law sizes the pool: concurrency = throughput \(\times\) latency. When the queue is full, reject quickly (Chapter (resilience)).

  • Event loop + non-blocking I/O (Nginx, Node.js, Netty, Python asyncio): one thread per core waits on many sockets with epoll/kqueue and runs a callback when one is ready. Handles tens of thousands of mostly idle connections (the “C10K problem”). One slow CPU-bound handler blocks everyone, so CPU work goes to a separate pool.

  • Lightweight threads / coroutines (Go goroutines, Java virtual threads, Erlang processes): blocking-style code scheduled by the runtime onto a few OS threads, combining simple code with event-loop efficiency.

Where the time goes in a typical request: accepting the connection (keep-alive avoids repeating TCP and TLS handshakes), parsing, waiting on the database and other services (usually the largest part), serialization. Most servers are I/O-bound, which is why connection pools to databases and downstream services matter so much: opening a new database connection per request can cost more than the query.

Architecture Hygiene

The Repository Pattern

🔧 Intermediate

Put all data access for an entity behind one interface (OrderRepository.get(id), .save(order), .find_by_customer(c, cursor)). Business logic never writes SQL or cache calls directly. Benefits: one place to add caching, sharding, read-replica routing, or a migration to a new store; tests use an in-memory fake; queries are visible and reviewable. Discord’s data services and Figma’s DBProxy (Part (cases)) are this idea at infrastructure scale. Avoid making the interface a leaky copy of the ORM; expose the queries the domain needs.

Extensible Data Modeling

🔧 Intermediate

Requirements change, so design schemas that can grow without painful migrations:

  • Stable, opaque IDs (never meaningful values like emails) as primary keys.

  • Enumerations stored as strings or lookup tables, not hard-coded integers whose meaning lives in code.

  • A JSON column (jsonb) for genuinely variable attributes (product attributes per category), with indexes on the few fields you query.

  • created_at, updated_at, and a version column on every table: they cost little and enable incremental sync, auditing, and optimistic locking.

  • Model relationships explicitly (join tables) even when they are one-to-one today.

  • Plan for multi-tenancy and soft delete early (Chapter (data)).

Avoid the opposite failure: a fully generic “entity–attribute–value” schema for everything, which makes every query slow and every constraint impossible to enforce.

Cost-Aware Architecture

🔧 Intermediate

Cost is a non-functional requirement. Estimate it in the design, just like QPS:

  • Know the big lines: compute (instances, GPUs), storage (per GB-month and per request), and data transfer (egress to the internet and cross-zone or cross-region traffic, often a surprise; DoorDash and Kafka “diskless” designs were driven partly by cross-zone transfer costs).

  • Match the pricing model to the load: reserved or committed capacity for steady load, autoscaling and spot instances for variable or interruptible work, serverless for spiky low-volume work (and its per-request costs at high volume; see the Prime Video case in Part (cases)).

  • Storage tiers: hot data on SSD or in memory, warm data in object storage, cold data in archive classes; lifecycle rules move it automatically.

  • Cost per unit (per request, per user, per 1M tokens) is the number to track; it shows whether growth makes the business better or worse.

When Not to Add Infrastructure

🔧 Intermediate

Every new component (a cache, a queue, a second database, a service) adds latency paths, failure modes, monitoring, upgrades, and on-call load. Add one only when a measured limit requires it. Questions to ask first: Is the current component actually the bottleneck (profile it)? Can an index, a query fix, a bigger instance, or a read replica solve it? Will the team operate it well at 3 a.m.? Stack Overflow and WhatsApp (Part (cases)) served enormous traffic with very few components. In an interview, it is a strong signal to say “we don’t need X yet; we would add it when Y.”

A Framework for Any Design

A six-step framework used throughout this book.

What Interviewers Probe Now

🔧 Intermediate

Patterns from public 2025–2026 interview guides and candidate reports (summarized without names):

  • Internals, not just boxes: interviewers follow up on why you chose a component, for example how consistent hashing rebalances or why a B-tree index rather than an LSM tree (Chapters (lb), (data), (storage)).

  • A timed shape: about 5 minutes on requirements, 5 on estimates, 5 on the API, then 15 or more on two or three deep dives, with estimates used to justify choices.

  • Two families of prompts: product designs (social networks, ride sharing, e-commerce, ticketing) and infrastructure designs (caches, key-value stores, crawlers, rate limiters, schedulers).

  • Newer prompts: “design ChatGPT” (GPU scheduling, KV cache, streaming tokens, where conversation state lives: Chapters (genai) and (inference)), live chat for a streaming site (hierarchical fan-out, deliberately lossy delivery: Chapter (socialgeo)), and serverless functions (container pools, pre-warming).

  • Common failure: adding a queue or cache because it “feels right” and then being unable to defend it. Name the requirement each component serves.

🎤 Interview

Spend the first five minutes on requirements and estimates. Interviewers judge whether you ask about scale, read/write ratio, and consistency needs before you draw boxes. Always say the trade-off out loud: “I’m choosing X, which costs Y, because requirement Z matters more.”

🔑 Takeaways

  • Non-functional requirements drive architecture.

  • Use percentiles. Tail latency and availability compound across dependencies.

  • Stateless services scale horizontally; state is the hard part.

  • During a partition you choose consistency or availability. Otherwise, latency or consistency.

  • Estimate before designing; ratios tell you where the pressure is.
