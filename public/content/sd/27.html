👋 Intro

Eight famous failures and what they teach: AWS us-east-1 (2025), Cloudflare (2025), CrowdStrike (2024), Facebook (2021), Roblox (2021), OpenAI (2024), GitLab (2017), and Knight Capital (2012). Postmortems are the most honest system design documents there are: they show where real architectures break.

The common thread.

Very few big outages start with hardware. Most start with a change (config, deploy, automation) that propagated too fast, and become large because of a hidden dependency (DNS, a control plane, a monitoring system) and a recovery path that was never tested at full scale. Read each case asking three questions: what changed, what amplified it, and what slowed recovery.

Case: AWS us-east-1: A DNS Race Condition in DynamoDB (October 2025)

📋 Case facts

Domain: Cloud provider
Scale: About 14.5 hours of impact across many AWS services and thousands of customers
Concepts: Race conditions in automation, DNS, control-plane dependencies, congestive collapse, recovery at scale
Source: AWS, “Summary of the Amazon DynamoDB Service Disruption in the Northern Virginia (US-EAST-1) Region” (October 2025)

What changed.

DynamoDB manages its DNS records with automation in two parts: a Planner that produces DNS plans (which load balancers, with what weights) and an Enactor, running independently in three Availability Zones, that applies plans to Route 53. Each Enactor checked that its plan was newer than the one in place only once, at the start.

The race.

One Enactor was hit by unusually long delays. Meanwhile the Planner kept producing new plans and a second Enactor applied a newer one, then ran cleanup to delete old plans. At that moment the delayed Enactor finished writing its stale plan to the regional endpoint. The cleanup then deleted that plan, which was now the active one. The result was an empty DNS record for dynamodb.us-east-1.amazonaws.com, and the system was left in a state that blocked further automatic updates.

How one empty DNS record cascaded.

What amplified it.

DynamoDB’s API was down from about 11:48 PM to 2:40 AM PDT. But other systems depended on it. EC2’s DropletWorkflow Manager (DWFM), which maintains leases on physical hosts, uses DynamoDB; leases timed out. When DynamoDB came back, the backlog of re-lease work was so large it kept timing out: congestive collapse, where the system is busy retrying work that never completes. Engineers had to throttle incoming work and restart hosts. New instances then launched without network connectivity because network state propagation was backlogged, and Network Load Balancer health checks against these instances flapped, triggering automatic AZ failover that removed healthy capacity. Engineers disabled the automatic failover until things stabilized. Full EC2 recovery took until about 1:50 PM.

Fixes announced.

The DNS automation was disabled worldwide until the race was fixed; NLB got a velocity control limiting how much capacity health checks can remove; EC2 added at-scale tests of the DWFM recovery workflow and queue-based rate limiting in data propagation.

📚 Lesson

  • Check-then-act with a long gap is a race; re-validate at the point of action or use versioned conditional writes.

  • Automation that can delete must refuse to delete the active state.

  • Recovery has its own capacity limits: design for backlog after an outage (throttling, admission control).

  • Automated failover needs a velocity limit, or it can make a partial failure total.

Case: Cloudflare: An Oversized Feature File (November 2025)

📋 Case facts

Domain: CDN and security edge
Scale: About six hours of widespread HTTP 5xx errors for sites behind Cloudflare
Concepts: Config propagation, input validation, hard limits, panics in critical paths, kill switches
Source: Cloudflare blog, “Cloudflare outage on November 18, 2025”

What changed.

A permissions change in a ClickHouse database cluster made previously implicit access to underlying tables explicit. A query used to generate the Bot Management feature file read column metadata without filtering by database name, so it began returning duplicate rows. The generated file roughly doubled in size.

What broke.

The file is regenerated every five minutes and pushed to every server on the network. The bot-scoring module in the new proxy (FL2, written in Rust) preallocates memory for a fixed maximum of 200 features (normal use was about 60). The oversized file exceeded the limit, the code returned an error, and an unwrap() on that error caused a panic, and the proxy returned 5xx errors. On the older proxy (FL) there were no errors, but every request got a bot score of zero, which broke customers’ bot rules.

Why it was confusing.

The database cluster was being updated gradually, so each five-minute run produced either a good or bad file. The network kept failing and recovering, which looked like a DDoS attack at first.

Fixes.

Stop generating the bad file, push a known-good file, restart proxies. Follow-ups: treat internally generated configuration with the same validation as user input, add global kill switches for features, and stop core dumps and error reporting from consuming resources during failures.

📚 Lesson

  • Config is code: generated files need validation, staged rollout, and size checks before global push.

  • When a hard limit is exceeded, fail safe (keep the last good config), do not crash the request path.

  • Flapping symptoms often mean a periodic job is alternating between good and bad output.

Case: CrowdStrike: A Content Update Crashes 8.5 Million Windows Machines (July 2024)

📋 Case facts

Domain: Endpoint security
Scale: About 8.5 million Windows devices crashed; airlines, hospitals, banks affected
Concepts: Kernel-mode code, staged rollout, input validation, manual recovery
Source: CrowdStrike Preliminary Post Incident Review and Root Cause Analysis (July–August 2024)

What changed.

CrowdStrike’s Falcon sensor runs a driver in the Windows kernel. Besides code updates (rolled out in stages), it receives frequent content updates: configuration that tells the sensor what behavior to detect. On July 19, 2024 a content update (“Channel File 291”) was pushed to all online Windows hosts at once.

What broke.

The new template defined 21 input fields, but the sensor code supplied only 20 values. Reading the 21st value was an out-of-bounds memory read in kernel mode, which crashes the whole operating system (the “blue screen”). Machines crashed again on every reboot because the bad file loaded at startup. The content validator had a bug that let the file pass, and content updates were not deployed in stages the way code was.

Why recovery was slow.

The fix was simple (delete the file), but it had to be done on each machine, often by hand in safe mode, and BitLocker disk encryption meant many machines needed recovery keys first. Remote recovery was impossible for machines that could not boot.

📚 Lesson

  • Treat configuration and content updates with the same staged rollout as code.

  • Code in the most privileged place (kernel, boot path) must validate all inputs and fail safe.

  • Plan for recovery when the broken component prevents remote access.

Case: Facebook: The BGP Withdrawal (October 2021)

📋 Case facts

Domain: Social network
Scale: About six hours of complete outage of Facebook, Instagram, WhatsApp
Concepts: BGP, DNS, backbone, out-of-band access, safety checks
Source: Meta engineering, “More details about the October 4 outage” (2021)

What changed.

During routine maintenance, a command intended to assess the capacity of Facebook’s global backbone accidentally disconnected all backbone connections between its data centers. An audit tool meant to block such commands had a bug and did not stop it.

What amplified it.

Facebook’s DNS servers are designed to withdraw their BGP route announcements if they cannot reach the data centers (a sensible health check: do not answer if you are cut off). With the backbone down, all of them did. The internet lost the routes to Facebook’s DNS servers, so facebook.com could not be resolved anywhere.

Why recovery was slow.

The same network outage took down internal tools, remote access, and even badge systems used to enter buildings. Engineers had to physically go to data centers, and getting through the heightened physical security took time. When the backbone came back, traffic had to be restored gradually to avoid power surges and cache stampedes.

📚 Lesson

  • Health checks that make a node withdraw itself can make every node withdraw at once.

  • Keep out-of-band access (separate network, separate auth) for when production is unreachable.

  • Bring a huge system back slowly; a sudden full load after an outage is its own incident.

Case: Roblox: A 73-Hour Outage Inside Consul (October 2021)

📋 Case facts

Domain: Gaming platform
Scale: About 73 hours offline for tens of millions of daily users
Concepts: Service discovery as a single point of failure, streaming features, BoltDB internals, circular dependencies
Source: Roblox engineering, “Roblox Return to Service 10/28-10/31 2021” (with HashiCorp)

What happened.

Roblox ran its own infrastructure, with HashiCorp Consul as the backbone for service discovery, health checks, and key-value config, used by Nomad and Vault as well. Consul became extremely slow and the whole platform went down.

The root causes

(found after days of investigation):

  • A recently enabled Consul streaming feature, under very high read and write load, caused contention on a small number of Go channels.

  • Consul’s storage engine BoltDB has a known pathology: its freelist of unused pages grew huge, and every write had to scan it, making writes progressively slower.

Disabling streaming and fixing the BoltDB freelist issue restored performance.

Why it took so long.

The monitoring and observability systems themselves depended on Consul, so the team was partly blind. Restarting services caused large, synchronized load on Consul (cold caches everywhere), and the cluster had to be brought back in stages.

📚 Lesson

  • A single shared control-plane system (service discovery, config) is a single point of failure; partition it into cells.

  • Your monitoring must not depend on the system it monitors.

  • Understand the storage engine under your critical infrastructure.

Case: OpenAI: A Telemetry Service Overloads Kubernetes (December 2024)

📋 Case facts

Domain: AI services
Scale: Several hours of outage for ChatGPT, the API, and Sora
Concepts: Kubernetes control plane, DNS caching, hidden dependencies, deploy safety
Source: OpenAI status page incident report, December 11, 2024

What changed.

OpenAI deployed a new telemetry service across its Kubernetes clusters. Its configuration caused every node to perform expensive Kubernetes API operations, and the cost grew with cluster size. In the largest clusters the API servers were overwhelmed.

The hidden dependency.

The data plane (running pods) can mostly work without the control plane, but in-cluster DNS-based service discovery needs the API server to know about endpoints. DNS caching hid the problem at first, so the change looked safe in staged rollout; when caches expired over the following minutes, services could not find each other.

Why recovery was slow.

Fixing it required the Kubernetes API, which was the thing that was overloaded. Engineers reduced cluster size, blocked network access to the API servers from the offending components, and scaled up API servers to get control back.

📚 Lesson

  • Caches can hide a failure during rollout; watch metrics past the longest cache TTL before proceeding.

  • Protect the control plane: rate limits and priority for system traffic (API Priority and Fairness).

  • Keep a break-glass path to the control plane that does not depend on the data plane being healthy.

Case: GitLab: Deleting the Production Database (January 2017)

📋 Case facts

Domain: Developer platform
Scale: About 6 hours of database data lost (issues, merge requests, comments); about 18 hours outage
Concepts: Backups, restore testing, replication, human error, operator safety
Source: GitLab, “Postmortem of database outage of January 31” (2017)

What happened.

Under load from spam and with replication lagging, an engineer working late tried to restart replication by wiping the data directory on the secondary database. The command was run in a terminal connected to the primary. About 300 GB of production data was deleted before it was stopped.

Why it was worse than it should have been.

GitLab had five backup or replication mechanisms. When they went to restore, they found that most were not working: regular backups had been failing silently (a version mismatch) and the failure notification emails were being rejected; disk snapshots were not enabled for the database servers. They restored from a staging copy taken about six hours earlier, live-streaming the recovery publicly.

📚 Lesson

  • A backup you have not restored is not a backup; test restores regularly and automatically.

  • Alerts on backup failure must be monitored, and their delivery must be monitored too.

  • Make the production shell look different (colored prompt) and prefer tools over manual destructive commands.

Case: Knight Capital: $440 Million in 45 Minutes (August 2012)

📋 Case facts

Domain: Algorithmic trading
Scale: About $440M loss in 45 minutes; the firm had to be rescued
Concepts: Deployment consistency, dead code, feature flags, kill switches
Source: U.S. SEC administrative proceeding against Knight Capital Americas (2013)

What happened.

Knight deployed new trading code to support a new NYSE program. The deployment was done manually to eight servers, and the technician missed one. The new code reused an old feature flag that, on the eighth server, activated “Power Peg”, test code that had been unused for years. Power Peg sent child orders continuously without tracking whether the parent order was filled. In 45 minutes it executed millions of trades in about 150 stocks.

Why it was not stopped.

There was no automated check that all servers ran the same version, no kill switch for the trading system, and automated emails about errors went unread before market open. During the incident, staff rolled back the new code on the seven good servers, which made them also run the old flag behavior and made things worse.

📚 Lesson

  • Automate deployments and verify every node runs the same version.

  • Delete dead code; never repurpose an old feature flag.

  • Have a kill switch, and know what a rollback will actually do.
