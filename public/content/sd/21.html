URL Shortener on One Machine

Requirements.

Same features as the URL shortener in Chapter (design), but for a company-internal tool or an early startup: 10,000 new links a day, 1 million redirects a day.

Estimates.

1M redirects/day is about 12 per second on average, perhaps 100 at peak. 10K links/day \(\times\) 5 years \(\times\) 500 bytes \(\approx\) 9 GB. All of it fits on one server’s disk and most of it in memory.

Design.

One application server and one Postgres (or SQLite) database: links(code PK, url, owner_id, created_at, expires_at). Codes come from the database sequence encoded in base62. An in-process LRU cache holds hot redirects. Nightly backups to object storage with tested restores; a standby replica if downtime matters.

Why this is the right answer.

Every component added beyond this (Redis, Kafka, a CDN, sharding) adds cost, failure modes, and on-call load without solving a problem the system has. A single modern server handles thousands of simple requests per second. Say what would trigger scaling (sustained CPU above 60%, data beyond memory, an availability target above what one region provides) and which step comes first.

Rate Limiting and Abuse Prevention for the URL Shortener

🔧 Intermediate

Public shorteners attract spam and phishing because a short link hides its destination.

  • Creation limits: per API key, per account, and per IP (token buckets, Chapter (gateway)); stricter for anonymous users; CAPTCHA or proof of work after suspicious bursts.

  • Destination checks at creation and periodically after: Safe Browsing style blocklists, domain reputation, newly registered domains, redirect chains (a short link to another shortener).

  • Interstitial warning page for links flagged as risky; disable links reported for abuse (with an appeals path).

  • Redirect limits per IP to stop scraping of the code space, and non-sequential codes (Chapter (design)) so codes cannot be enumerated.

  • Analytics privacy: aggregate click data; do not expose visitors’ IPs to link owners.

A Product Listing Page

Requirements.

An e-commerce product page and category listings: title, images, price, stock, reviews summary, recommendations. 50M page views a day, 99.9% of traffic is reads, price and stock must be accurate at checkout.

Design.

  • Catalog service owns product data in a relational database (products, variants, attributes with a JSON column for category-specific attributes); images in object storage behind an image CDN (Chapter (media)).

  • Read path: the page is assembled from cached fragments with different freshness: product content (cached minutes, invalidated on edit via CDC), price and stock (short TTL or read from a fast inventory cache), reviews summary (cached hours), recommendations (precomputed per product). Edge micro-caching absorbs spikes.

  • Category listings and filters come from a search index (Chapter (search)), synced by CDC, with facet counts computed by the engine.

  • Pagination: keyset pagination for stable, fast deep pages (Chapter (data)).

  • Correctness: the page may show a slightly stale price, but the cart and checkout re-read the authoritative price and stock.

An Object Store (S3)

Requirements.

PUT/GET/DELETE objects in buckets, list by prefix, versioning, multipart upload, 11 nines durability, high availability, petabytes to exabytes.

Design

(details in Chapter (storage)):

  • Stateless front ends (auth, request routing, rate limits per bucket).

  • A metadata index range-partitioned by (bucket, key) so listing is a range scan, managed by a partition manager that splits hot ranges.

  • A data layer of append-only extents: new writes replicated three ways across zones, sealed extents erasure-coded (e.g. 6+3) in the background.

  • PUT = write bytes, then commit metadata (atomic visibility); orphaned bytes are garbage-collected.

  • End-to-end checksums, background scrubbing, and automatic repair.

  • Multipart: parts stored independently and stitched by metadata on completion.

Deep dive questions.

How listing stays strongly consistent (metadata is the source of truth, read from the partition leader); hot prefixes; repair bandwidth after a rack failure; lifecycle rules moving data to colder, cheaper tiers.

A Kafka-Style Log

Requirements.

Durable, ordered, replayable streams; topics with partitions; many producers and consumer groups; millions of messages per second; configurable retention.

A partition is a sequence of segment files.

  • Storage: each partition is a directory of segment files. Appends go to the active segment; a sparse index maps offsets to file positions (binary search, then a short scan); a time index maps timestamps to offsets. Retention deletes whole old segments (cheap). Log compaction (optional per topic) keeps only the latest value per key, for changelogs.

  • Performance: sequential appends, the OS page cache instead of an application cache, batching and compression per batch, zero-copy sends to consumers.

  • Replication: leader per partition, followers fetch; in-sync replica set, high watermark, acks=all with min.insync.replicas=2 (Chapter (messaging)).

  • Metadata: controller with a Raft quorum stores topics, partition assignments, and leaders (KRaft).

  • Consumers: group coordinator assigns partitions to members and stores committed offsets in an internal compacted topic.

  • Tiered storage: old segments move to object storage, keeping broker disks small.

A Notifications System

Requirements.

Send push, email, SMS, and in-app notifications triggered by product events or campaigns; respect user preferences and quiet hours; no duplicates; track delivery; 1 billion notifications a day with campaign spikes.

Notifications: decide once, deliver per channel.

  • Decide: the notification service receives an event, resolves recipients, checks preferences (opt-outs per type and channel), quiet hours and time zone, frequency caps (per user per day), and deduplicates by (user, notification key) within a window. It renders a localized template.

  • Deliver: one queue per channel and priority (a password reset must not wait behind a marketing campaign). Workers call providers (APNs, FCM, an email service, an SMS gateway) with retries, backoff, and per-provider rate limits; failures go to a DLQ.

  • Idempotency: each notification has an ID passed to providers where supported, so retries do not double-send.

  • Tracking: store status per notification (queued, sent, delivered, opened, failed); process provider feedback (invalid device tokens are deleted, email bounces suppress the address).

  • Scheduling: campaigns are expanded in batches by a scheduler and spread over time to avoid traffic spikes against the app when users tap.

  • In-app inbox: a per-user list in a key-value store plus an unread count (Chapter (socialgeo)).

A Payment System

Requirements.

Accept card payments for an online marketplace, pay out sellers, refunds; never lose or double-count money; integrate with an external payment service provider (PSP); reconcile daily.

  • Payment state machine: CREATED \(\to\) AUTHORIZED \(\to\) CAPTURED \(\to\) SETTLED, with FAILED, REFUNDED, DISPUTED; transitions are persisted, never skipped, and every external call is keyed by an idempotency key derived from the payment ID and step (Stripe case, Part (cases)).

  • Double-entry ledger: every money movement is a transaction with entries that sum to zero (debit the buyer’s receivable, credit the seller’s payable and the platform’s fee account). Ledger rows are immutable and append-only; corrections are new entries. Balances are derived (and cached), never edited directly.

  • PSP integration: card details go directly from the client to the PSP (hosted fields or SDK) so the platform never touches raw card numbers (reducing PCI scope); the platform stores a token. Webhooks from the PSP are verified (signatures), deduplicated by event ID, and processed idempotently; the system also polls for payments whose outcome is unknown after a timeout.

  • Exactly-once effects: at-least-once messaging plus idempotent handlers and unique constraints; the outbox pattern for publishing payment events.

  • Reconciliation: daily, match internal ledger entries with the PSP’s settlement reports and bank statements; mismatches become tickets and automatic fixes.

  • Payouts: batched to sellers on a schedule, after risk holds; a saga with compensation if a bank transfer fails.

  • Data: a strongly consistent relational database; money as integers in minor units with a currency code, never floating point.

A Search Service

Requirements.

Full-text and filtered search over 100M documents for an app, under 200 ms p99, updates visible within seconds, per-tenant permissions.

Design

(Chapter (search)): CDC from the source database into an indexing pipeline (enrich, embed, write with external versions); a document-partitioned index with replicas; query service doing query understanding, BM25 plus vector retrieval, permission filters, and a re-ranker; autocomplete from query logs; offline judged sets plus online interleaving for quality. Reindex via a new index and alias swap.

Failure modes.

Indexing lag (alert on consumer lag; show results anyway); a shard down (serve partial results from replicas, mark them partial); a bad ranker (feature flag back to the previous model).

A Recommendation System

Requirements.

“Recommended for you” on a marketplace home page, 100M users, 10M items, 50 ms budget, measured by purchases and long-term retention.

Design.

Candidate generation from several sources (a two-tower model with ANN search, item-to-item co-purchase lists, recent views, trending in the user’s region, fresh items for exploration) yields about 1,000 candidates; seen and purchased filtering (Bloom filters, Chapter (socialgeo)); a ranking model scores them with features from a feature store; re-ranking adds diversity, business rules, and an exploration slot. Batch training daily, near-real-time features (last few clicks) from a stream. Evaluate offline with recall@k and NDCG on time-split data, online with A/B tests on purchases and guardrails. Cold start: popular-by-segment for new users, content embeddings and exploration boosts for new items. The companion interview book covers the models in depth.

Nearby Search (Yelp-Style)

Requirements.

Find businesses near a location, filtered by category and rating; 200M businesses; 10K queries per second; business data changes rarely.

Design.

Business data in a relational database; a read-optimized geo index built from it: geohash (precision chosen per search radius) or S2 cell IDs as an indexed column, or a search engine with geo-point fields (Elasticsearch geo_distance). Query the user’s cell and its neighbors, filter by exact distance, then rank by distance, rating, and relevance. Because data changes rarely, the index is rebuilt or updated hourly and the whole thing replicates well across read replicas or regions. Dense cities need smaller cells than rural areas: quadtrees adapt automatically (Chapter (socialgeo)).

A File Sync Service

Design

(Chapter (media)): clients chunk files (content-defined), hash chunks, upload only missing ones to a content-addressed block store; a metadata service sharded by namespace commits block lists to a per-namespace journal; clients sync with cursors and are woken by notifications; conflicts produce conflicted copies; retention windows allow undelete. Estimate: 500M users \(\times\) 10 GB average \(=\) 5 EB raw, much less after deduplication, which is why storage design and cost dominate (Dropbox’s Magic Pocket, Part (cases)).

Observability and SLOs for a Service

Prompt.

“Design the monitoring for a checkout service.”

  • SLIs: availability (fraction of checkout requests returning a non-5xx response) and latency (fraction under 800 ms), measured at the load balancer, plus a business SLI (successful orders per minute vs forecast).

  • SLOs: 99.9% availability over 28 days; alert on multi-window burn rates (Chapter (obs)).

  • Instrumentation: OpenTelemetry traces through checkout, payments, and inventory; RED metrics per endpoint; structured logs with trace IDs; dependency dashboards.

  • Pipeline: agents and collectors to a metrics store, log store, and trace store, with sampling that keeps all errors and slow traces.

  • Runbooks and ownership linked from every alert.

A Database Migration

Prompt.

“Move the orders table from a monolith’s MySQL database to a new orders service with its own Postgres, without downtime.”

Migrating data out of a monolith in reversible steps.

  1. Backfill: copy existing rows to the new store (versioned writes so backfill and live changes can interleave safely, as in Notion’s migration, Part (cases)).

  2. Keep in sync: CDC from the old database (preferred over application dual writes, which can diverge on partial failure), with the old database still the source of truth.

  3. Shadow (parallel) reads: for a sample of requests, read from both, return the old result, log mismatches; fix until mismatches are zero.

  4. Parallel monolith read drain: route an increasing percentage of reads to the new service behind a feature flag (1%, 10%, 50%, 100%), watching errors and latency; roll back instantly by flipping the flag. The monolith’s reads drain away while writes still go to the old path.

  5. Switch writes: make the new service the writer and source of truth, with reverse sync to the old table for a while as a rollback path.

  6. Retire: stop reverse sync, remove old code paths, archive and drop the table.

Each step is reversible on its own; that is the point. Schema changes inside one database follow expand/contract (Chapter (cicd)).

A Photo-Sharing App (Instagram-Style Interview)

Requirements.

Upload photos with captions, follow users, a home feed, likes and comments, profile grids; 500M daily active users; 100M photos uploaded a day.

Estimates.

100M uploads/day \(\approx\) 1,200/s average. At about 2 MB of renditions per photo, 200 TB/day of new storage, roughly 70 PB/year. Feed reads: 500M users \(\times\) 10 feed loads \(\approx\) 60K/s average.

Design.

  • Upload: presigned direct upload, then async processing: renditions, EXIF stripping, moderation (Chapter (media)); photo metadata in a sharded database keyed by time-sortable IDs that embed the shard (Instagram case, Part (cases)).

  • Serving: immutable image URLs through a CDN.

  • Social graph and feed: follow edges in both directions; hybrid fan-out with feed lists of post IDs in Redis; ranking (Chapter (design)).

  • Likes and comments: edges plus sharded counters; “liked by you” point lookups (Chapter (socialgeo)).

  • Profile grid: posts by author ordered by ID (one partition range scan).

  • Search: users and hashtags in a search index.

Deep dives.

Celebrity fan-out, hot photos, storage tiering of old photos to colder storage classes, and deletion (remove from CDN, feeds, search, and backups within a retention policy, Chapter (obs)).

A Ticket Booking System

Requirements.

Users browse events, pick seats, pay within 10 minutes; no seat is ever sold twice; a popular on-sale has 2 million users at once for 50,000 seats.

  • Inventory: a seats table with event_id, seat_id, status, hold_id, hold_expires_at, and order_id, partitioned by event.

  • Hold: an atomic conditional update,
    UPDATE seats SET status='HELD', hold_id=?, hold_expires_at=now()+10min
    WHERE event_id=? AND seat_id IN (...) AND status='AVAILABLE',
    succeeding only if every requested seat was available (check the row count, within one transaction). Expired holds are released by a sweeper or treated as available by queries.

  • Payment: a saga: hold \(\to\) charge \(\to\) confirm (SOLD); release the hold if payment fails; idempotency keys throughout.

  • On-sale surge: a virtual waiting room admits users at the rate the inventory service can handle; bot defense at the edge; seat maps served from a cache with availability updated every few seconds (Ticketmaster case, Part (cases)).

  • General admission (no seat numbers): a counter per ticket type with an atomic decrement guarded by remaining > 0, or pre-split the inventory into buckets to avoid one hot row.

🔑 Takeaways

  • Start from the simplest design that meets the numbers, and name the trigger for each scaling step.

  • Money and inventory need state machines, conditional writes, idempotency, and reconciliation.

  • Notification, search, and recommendation systems are pipelines with clear decide and deliver stages.

  • Migrations succeed as a series of individually reversible steps verified by shadow reads.
