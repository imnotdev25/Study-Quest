Which Building Block?

Problem Reach for
Too many reads on DB Cache (cache-aside), read replicas, CDN
Too many writes on DB Sharding, LSM-based store, write batching via queue
Slow user-facing request Move work async (queue), cache, parallelize calls
Traffic spikes Queue for load leveling, autoscaling, rate limiting, load shedding
Abuse / noisy tenant Rate limits per key/tenant, quotas, bulkheads
Flaky dependency Timeouts, retries with jittered backoff, circuit breaker, fallback
Duplicate side effects Idempotency keys, unique constraints, dedup tables
Cross-service consistency Saga (orchestrated with durable execution), outbox
DB and event bus out of sync Transactional outbox or CDC
Services finding each other Service discovery (K8s DNS, Consul), mesh
Global users GeoDNS/anycast, CDN, multi-region replicas
Search by text Inverted index (Elasticsearch/OpenSearch)
Search by meaning Embeddings + vector index, hybrid with BM25
LLM answers from private data RAG with ACL filtering and reranking
LLM cost too high Prompt caching, model routing, batch API, shorter context
LLM latency too high Streaming, smaller model, prefix caching, speculative decoding
GPU throughput too low Larger batches, continuous batching, quantization, more KV memory

Numbers to Remember

  • 1 day \(\approx 10^5\) s; 1M/day \(\approx\) 12/s; peak \(\approx\) 2–5\(\times\) average.

  • Memory 100 ns; SSD 20–100 \(\mu\)s; same-DC RTT 0.5 ms; cross-continent 80–150 ms.

  • 99.9% = 8.8 h/year downtime; 99.99% = 53 min/year.

  • One Redis shard: \(\sim\)100K+ simple ops/s. One Postgres primary: thousands to tens of thousands of writes/s depending on workload.

  • One Kafka partition: roughly 10 MB/s comfortable sustained throughput.

  • 1 token \(\approx\) 4 characters \(\approx\) 0.75 words.

  • KV cache (70B-class with GQA, FP16): \(\sim\)320 KB/token.

  • Weights: params \(\times\) bytes (70B: 140 GB BF16, 70 GB FP8, 35 GB INT4).

  • Decode time per token at batch 1 \(\approx\) weight bytes / memory bandwidth.

Interview Checklist

  1. Clarify: users, features in scope, scale, read/write ratio, latency, consistency, durability.

  2. Estimate QPS (avg and peak), storage, bandwidth, memory/cache size.

  3. Define the API and the core data model, including keys and indexes.

  4. Draw the high-level design: clients, edge, LB/gateway, services, data stores, async.

  5. Deep dive on the two hardest parts the interviewer cares about.

  6. Discuss failures: what happens when each box dies or slows down.

  7. Cover operations: monitoring, SLOs, deployment, security, cost.

  8. State trade-offs and what you would do differently at 10\(\times\) scale.
