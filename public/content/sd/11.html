👋 Intro

Counting things at scale: view and impression counters, raw events vs derived aggregates, bucketed time windows, and probabilistic sketches (HyperLogLog, count-min, top-\(k\) heavy hitters, reservoir sampling, t-digest) that are small, fast, and mergeable. Ends with high-throughput live reactions.

Why Counting Is Hard

🌱 Beginner

Counting seems trivial: add one. At a billion events a day, “add one” runs into three problems: a single counter becomes a hot spot that many servers fight over, retries make you count the same event twice, and some questions (“how many different people?”) need memory for everyone you have seen.

🔧 Intermediate

Decide first what kind of number you need:

Need Example Approach
Exact, money-relevant ad impressions billed to customers deduplicated events, idempotent aggregation, reconciliation
Approximately right, fast video view count, likes sharded counters, batched updates, eventual consistency
Distinct counts unique viewers, daily active users HyperLogLog
Frequency of each item trending hashtags, hot keys count-min sketch + top-\(k\)
Distribution p50/p99 latency, watch-time percentiles t-digest / KLL / DDSketch

View Counting at Scale

View counting: aggregate in the stream, write increments in batches.

🔧 Intermediate

Naive: UPDATE videos SET views = views + 1 per view. A viral video receives thousands of views per second on one row, and every update takes the same row lock: a hot key.

  • Aggregate before writing: a stream processor sums views per video per window (e.g. 10 seconds) and writes one +n per window. Thousands of writes become one.

  • Sharded counters: split a hot counter into \(N\) sub-counters (views:{id}:{0..N-1}), increment a random one, sum on read (cache the sum).

  • Validation: views are filtered for bots and abuse (minimum watch time, rate per user/IP, known bad actors), which is why public counts can lag or be revised.

  • Deduplication: client retries carry an event ID; the aggregator keeps a short-lived set of seen IDs (or a Bloom filter) per window.

  • Read path: the displayed count comes from a cache; slight staleness is acceptable.

Reddit has described counting post views with HyperLogLog: events flow through Kafka, one consumer decides whether each event should count, another updates a per-post HLL in Redis, and HLLs are periodically persisted to Cassandra. Counting unique viewers that way takes about 12 KB per post regardless of audience size.

Impression Counting for Billing

🔧 Intermediate

Ad impressions are money, so the bar is higher: each impression has a unique ID issued when the ad is served; the impression beacon carries it; ingestion is at-least-once and the aggregator deduplicates by ID within a window long enough to cover retries; aggregation writes are idempotent (keyed by window and campaign, not blind increments); the raw event log is kept so that billing totals can be recomputed and reconciled in a daily batch job, which is the version invoices use. Real-time numbers power pacing and dashboards; batch numbers are authoritative.

Raw Events vs Derived Analytics

🔧 Intermediate

Keep the immutable raw events (in object storage, partitioned by date, in Parquet) as the source of truth, and treat every counter, rollup, and dashboard as a derived view that can be rebuilt. Benefits: fix a bug and recompute, add a new metric over history, audit numbers. Costs: storage (mitigated by compression and retention tiers) and recompute time.

  • Lambda architecture: a fast streaming path for fresh approximate numbers and a batch path for corrected numbers, merged at read time. Two code paths to keep consistent.

  • Kappa architecture: one streaming path; to recompute, replay the log through a new version of the job. Simpler when the stream system retains enough history.

OLAP databases (ClickHouse, Druid, Pinot, BigQuery) often make pre-aggregation unnecessary for dashboards by scanning raw or lightly rolled-up columnar data quickly.

Bucketed Time Windows

Per-minute buckets; any window is a sum of buckets.

🔧 Intermediate

Store counts per entity per time bucket: key metric:entity:bucketStart, with TTL equal to the longest window you serve. “Last hour” = sum of 60 one-minute buckets; “last 30 days” = 30 daily buckets (roll up minutes into hours and days). An approximate sliding window weights the oldest bucket by the fraction still inside the window (the same trick as the sliding-window rate limiter, Chapter (gateway)). In memory, a ring buffer of \(W\) buckets gives \(O(1)\) updates and \(O(W)\) or \(O(1)\) (with a running total) queries.

Window types: tumbling (fixed, non-overlapping), hopping/sliding (overlapping), session (gap-based, per user). Event time vs processing time: bucket by when the event happened, not when it arrived; stream processors (Flink, Beam, Kafka Streams) use watermarks to decide when a window is complete and how long to wait for late events, and allow late updates to correct closed windows.

Mergeable Sketches

🌱 Beginner

A sketch is a tiny summary of a huge stream that answers one kind of question approximately. The key property for systems is that two sketches can be merged: combine the sketch from server A with server B, or Monday with Tuesday, and get the sketch of the combined data.

Sketch Answers Size Merge
HyperLogLog number of distinct items (\(\approx\)1–2% error) \(\sim\)12 KB bucket-wise max
Count-min frequency of any item (overestimate only) \(d\times w\) counters cell-wise sum
Top-\(k\) (Space-Saving / heavy hitters) most frequent items \(O(k)\) combine and re-trim
Bloom filter “seen before?” (false positives only) \(\sim\)10 bits/item for 1% bitwise OR
t-digest / KLL / DDSketch quantiles (p50, p99) a few KB merge centroids / buckets
Reservoir sample uniform random sample \(k\) items keep \(k\) smallest random keys
🔧 Intermediate

Store sketches per time bucket (one HLL per post per day), and answer any range by merging the buckets: unique visitors over the last 7 days is the merge of 7 daily HLLs, which you cannot get by adding daily unique counts (that double-counts people who came on several days). Redis implements HLL natively (PFADD, PFCOUNT, PFMERGE); BigQuery, Druid, and ClickHouse expose HLL and quantile sketches as column types. The algorithms themselves are covered in the companion interview book.

Top-\(k\) Heavy Hitters

🔧 Intermediate

“Top 10 trending hashtags in the last hour”: each stream partition keeps a count-min sketch plus a min-heap of its current top candidates (or the Space-Saving algorithm, which keeps \(k\) counters and replaces the minimum when a new item arrives). Every minute, partitions send their candidates to an aggregator that merges counts and computes the global top \(k\). Pitfall: merging per-partition top-\(k\) lists can miss an item that is moderately frequent everywhere but top-\(k\) nowhere; partitions should send more candidates than \(k\) (e.g. \(10k\)), or partition by item (hash the hashtag) so each item’s full count lives in one partition. “Trending” usually means growth, not volume: compare the current window with a baseline (e.g. a ratio against the same hour last week, with smoothing).

Sampling and Percentiles

🔧 Intermediate

Reservoir sampling keeps a uniform sample of a stream of unknown length in fixed memory, used for sampling logs, traces, and examples for labeling. Percentiles: you cannot average per-server p99s to get a global p99. Each server keeps a t-digest (or an HDR histogram, or DDSketch) per time bucket and ships it; the aggregator merges them and reads off the quantile. This is how monitoring systems compute fleet-wide latency percentiles (Prometheus histograms do a coarser version with fixed buckets).

Live Reactions at High Throughput

Aggregate up, broadcast down.

🔧 Intermediate

A live stream with 2 million viewers tapping hearts can produce hundreds of thousands of events per second. Do not fan out every reaction to every viewer (that is \(O(n^2)\)). Instead: gateways count reactions locally per short window and forward counts, regional aggregators sum them, and a global aggregator broadcasts a single update (totals per reaction type, perhaps a sample of individual reactions to animate) about once per second. Viewers see an accurate trend and a lively animation, generated client-side from the counts. Persist only the aggregate per time bucket. The same pattern applies to live polls and viewer counts.

📦 Use case: Daily active users across products

Each service emits a (user_id, product, date) event. A daily job builds one HLL per product per day; dashboards show DAU (one HLL), WAU and MAU (merge 7 or 30 HLLs), and cross-product unique users (merge across products). Exact counts are computed weekly from raw events to validate the approximations.

🔑 Takeaways

  • Decide between exact, approximate, distinct, frequency, and distribution questions first.

  • Aggregate before writing; shard hot counters; deduplicate by event ID.

  • Keep raw events immutable; derive and rebuild aggregates.

  • Store mergeable sketches per time bucket and merge to answer any range.

  • For live reactions, aggregate upward and broadcast summaries downward.
