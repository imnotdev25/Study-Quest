Retrieval in One Picture

🌱 Beginner

A RAG system answers a question in two moves: find a few relevant passages from a large collection, then ask a language model to answer using only those passages. The model is only as good as what you hand it, so most RAG engineering is really retrieval engineering.

The retrieval stack used by most production RAG systems.

🔧 Intermediate

Two broad families of retrievers:

  • Sparse (lexical): represent text as weights over vocabulary terms (most weights zero) and match on shared words. TF-IDF, BM25, SPLADE. Strong on exact terms, names, codes, rare words; weak on paraphrase.

  • Dense (semantic): represent text as a vector of a few hundred to a few thousand floats from a neural encoder and match by vector similarity. Strong on meaning and paraphrase; weak on exact identifiers and out-of-domain vocabulary.

Combining them (hybrid retrieval) and then re-ranking is the default because their errors are largely different.

Lexical Scoring: TF-IDF

🌱 Beginner

A word tells you more about a document if the document uses it a lot (term frequency) and few other documents use it at all (inverse document frequency). “The” appears everywhere and says nothing; “mitochondria” appears in few documents and says a lot.

🔧 Intermediate

For a term \(t\), document \(d\), and a collection of \(N\) documents where \(t\) appears in \(df(t)\) of them: \[\text{tf-idf}(t, d) = tf(t, d)\cdot\log\frac{N}{df(t)},\qquad \text{score}(q, d) = \sum_{t\in q}\text{tf-idf}(t, d).\] Common variants: log-scaled term frequency \(1 + \log tf\) (dampens repetition), smoothed IDF \(\log\frac{N+1}{df+1} + 1\) (scikit-learn’s default, avoids division by zero), and representing documents and queries as L2-normalized TF-IDF vectors scored by cosine similarity, which removes the bias toward long documents.

Lexical Scoring: BM25

🔧 Intermediate

TF-IDF has two flaws: score grows linearly with repetition (a page saying “cat” 50 times is not 50 times more relevant), and long documents win simply by containing more words. BM25 (Okapi BM25, Robertson et al.) fixes both: \[\text{BM25}(q, d) = \sum_{t\in q}\text{idf}(t)\cdot \frac{tf(t,d)\,(k_1 + 1)}{tf(t,d) + k_1\left(1 - b + b\,\frac{|d|}{\text{avgdl}}\right)}, \qquad \text{idf}(t) = \ln\!\left(\frac{N - df(t) + 0.5}{df(t) + 0.5} + 1\right)\] (the IDF form used by Lucene, Elasticsearch, and OpenSearch).

  • \(k_1\) (typically 1.2–2.0) controls saturation: the term-frequency part approaches but never exceeds \(k_1 + 1\), however often the term repeats.

  • \(b\) (typically 0.75) controls length normalization: \(b = 0\) ignores length, \(b = 1\) fully normalizes by \(|d|/\text{avgdl}\).

Worked Example

Doc Text (after lowercasing) Length
D1 cat sat on the mat 5
D2 the dog sat 3
D3 cat cat cat runs 4
🔧 Intermediate

Query: “cat mat”. \(N = 3\), \(df(\text{cat}) = 2\), \(df(\text{mat}) = 1\), \(\text{avgdl} = 4\), \(k_1 = 1.2\), \(b = 0.75\).

TF-IDF (raw \(tf\), natural log): \(\text{idf(cat)} = \ln(3/2) = 0.405\), \(\text{idf(mat)} = \ln 3 = 1.099\). D1 \(= 1(0.405) + 1(1.099) = \mathbf{1.504}\); D2 \(= 0\); D3 \(= 3(0.405) = \mathbf{1.216}\).

BM25: \(\text{idf(cat)} = \ln(1.5/2.5 + 1) = \ln 1.6 = 0.470\); \(\text{idf(mat)} = \ln(2.5/1.5 + 1) = \ln 2.667 = 0.981\).

  • D1 (\(|d| = 5\)): length factor \(k_1(1 - b + b\cdot 5/4) = 1.2 \times 1.1875 = 1.425\). Each term has \(tf = 1\): \(\frac{1 \times 2.2}{1 + 1.425} = 0.907\). Score \(= 0.470(0.907) + 0.981(0.907) = 0.426 + 0.890 = \mathbf{1.316}\).

  • D3 (\(|d| = 4\)): length factor \(1.2 \times 1.0 = 1.2\). For cat, \(tf = 3\): \(\frac{3 \times 2.2}{3 + 1.2} = 1.571\). Score \(= 0.470 \times 1.571 = \mathbf{0.739}\).

Both rank D1 first, because “mat” is rare and D1 contains it. Note the saturation: in D3, three occurrences of “cat” score 1.571, only 1.57\(\times\) what a single occurrence would score in a document of the same length (1.0), not 3\(\times\).

Variants

🔧 Intermediate

  • BM25F scores several fields (title, body, anchor text) with per-field weights and length normalization, combining term frequencies before saturation.

  • BM25+ adds a small constant so long documents containing a term never score below short documents lacking it.

  • Phrase and proximity boosts: extra score when query terms appear close together (requires positions in the index).

Learned Sparse Retrieval

🔧 Intermediate

Models such as SPLADE use a transformer to produce a sparse weight vector over the vocabulary for each document and query, including expansion terms that do not appear in the text (a passage about “automobiles” gets weight on “car”). The result is still served from an inverted index with exact term matching and good efficiency, but with much better recall than BM25 on paraphrases. Doc2query is an older trick: generate likely questions for each document with a model and append them before BM25 indexing.

Dense Embeddings

🌱 Beginner

An embedding model turns a sentence into a list of numbers, a point in space, arranged so that sentences with similar meaning land close together. Searching becomes “find the points nearest to my question’s point.”

🔧 Intermediate

Bi-encoders (dual encoders) embed queries and documents independently, so document vectors are computed once at indexing time and a query needs one encoder call plus a nearest-neighbor search. They are trained with contrastive losses (InfoNCE with in-batch and hard negatives) on (query, relevant passage) pairs. Many models expect different prefixes or instructions for queries and documents; using the wrong one silently lowers quality. Typical dimensions are 384–3,072. Matryoshka models can be truncated to fewer dimensions with modest loss, trading quality for memory.

Similarity Metrics

Metric Formula Notes
Cosine similarity \(\frac{a\cdot b}{\lVert a\rVert\,\lVert b\rVert}\) ignores length; the usual default for text
Dot product (inner product) \(a\cdot b\) equals cosine if vectors are L2-normalized; some models are trained for raw dot product
Euclidean (L2) distance \(\lVert a - b\rVert\) for normalized vectors \(\lVert a-b\rVert^2 = 2 - 2\cos(a,b)\), so it ranks identically to cosine
🔧 Intermediate

Use the metric the embedding model was trained with. Normalizing at write time lets the database use the cheapest operation (dot product) while keeping cosine semantics. Never mix embeddings from different models (or versions) in one index: their spaces are unrelated, so changing models means re-embedding the corpus.

How Vector Databases Work

🔧 Intermediate

Exact nearest-neighbor search compares the query to every vector: \(O(Nd)\) per query, fine up to perhaps a million vectors on a GPU or with SIMD, too slow beyond that. Vector databases use approximate nearest neighbor (ANN) indexes that find most of the true neighbors (measured as recall@k) while examining a small fraction of the data. Every index exposes a knob that trades recall for latency.

Index Idea Strengths / weaknesses Knobs
Flat (brute force) compare to all vectors exact; slow at scale none
IVF k-means into \(n_{list}\) cells; search the nprobe closest cells fast build, low memory; recall drops at cell borders nlist, nprobe
HNSW multi-layer proximity graph; greedy descent then best-first search high recall at low latency; memory-hungry; slower builds and deletes M, efConstruction, efSearch
PQ / IVF-PQ split vectors into \(m\) sub-vectors, store 1-byte codebook IDs 10–50\(\times\) compression; lossy, re-rank with exact vectors \(m\), bits per code
Scalar quantization float32 \(\to\) int8 per dimension 4\(\times\) smaller, small recall loss range calibration
Binary quantization keep only the sign bit 32\(\times\) smaller, Hamming distance; needs re-scoring oversampling factor
DiskANN (Vamana) graph on SSD, compressed vectors in RAM billions of vectors per node graph degree, beam width

ANN index families. The companion interview book’s Chapter 18 explains HNSW and PQ step by step.

🧠 Expert

Memory math for 10M chunks with 768-dimension embeddings:

  • float32 vectors: \(10^7 \times 768 \times 4\,\text{B} \approx 30.7\) GB.

  • HNSW graph with \(M = 16\): about \(2M\) neighbor IDs of 4 bytes at layer 0, roughly 128 B per vector, plus upper layers: about 1.3–1.5 GB.

  • int8 scalar quantization: about 7.7 GB; binary: about 0.96 GB; PQ with \(m = 96\): about 0.96 GB, plus codebooks.

A common production recipe: keep compressed vectors (int8, binary, or PQ) in memory for the candidate search, retrieve 3–10\(\times\) more candidates than needed (oversampling), then re-score them with full-precision vectors loaded from disk. That recovers most of the recall at a fraction of the memory. Deletes are usually tombstones cleaned up by periodic rebuilds or compaction, which is why heavy update workloads degrade HNSW recall over time.

Filtering

🔧 Intermediate

Real queries carry filters: tenant, permissions, language, date, product category.

  • Post-filtering: run ANN for top \(k\), then drop non-matching results. Simple, but a selective filter (1% of documents) leaves you with almost nothing; you must over-fetch heavily.

  • Pre-filtering: compute the matching set first, then search only within it (brute force if the set is small). Exact, but expensive for broad filters on a graph index.

  • In-index (filtered) search: the ANN traversal skips non-matching nodes while still using them for navigation (Qdrant, Weaviate, and others implement variants). Usually the best general option.

  • Partitioning: a separate index (namespace, collection, partition) per tenant when tenants are large and never searched together; it is also the strongest isolation.

Access-control filters must be applied at query time from the user’s current permissions, never only at ingestion.

Choosing a Vector Store

Option When it fits
pgvector (Postgres) you already run Postgres; up to tens of millions of vectors; want transactions, joins, and metadata filters in SQL
Elasticsearch / OpenSearch / Vespa you need strong BM25, hybrid ranking, facets, and vectors in one engine
Dedicated vector DBs (Qdrant, Weaviate, Milvus, Pinecone, and others) large scale, heavy filtering, multi-tenancy features, managed operations
Libraries (FAISS, hnswlib, ScaNN) embedded in your own service or batch jobs; you handle persistence and updates
Object-storage-backed engines (LanceDB, turbopuffer, S3 Vectors) very large, cost-sensitive corpora where some latency is acceptable
🔧 Intermediate

Decision questions: How many vectors now and in two years? Update rate? Required p99 latency and QPS? How selective are filters? Do you need hybrid lexical search? Multi-tenancy and data residency? Who operates it? A frequent mistake is adopting a new database for a corpus of 200,000 chunks that a Postgres table with an HNSW index serves easily.

Fusion and Re-ranking

🔧 Intermediate

Reciprocal rank fusion (RRF) merges ranked lists without needing comparable scores: \(\text{RRF}(d) = \sum_{r}\frac{1}{k + \text{rank}_r(d)}\) with \(k \approx 60\). Weighted score fusion normalizes each retriever’s scores (min–max or z-score per query) and takes \(\alpha\cdot s_{\text{dense}} + (1-\alpha)\cdot s_{\text{sparse}}\), tuning \(\alpha\) on an eval set.

Cross-encoder re-rankers read the query and one candidate together through a transformer and output a relevance score. They are far more accurate than bi-encoders because every query token can attend to every document token, but they cost one model call per candidate, so they run only on the top 50–200 fused candidates. LLM-based re-rankers (listwise ranking with a prompt) are stronger still and slower.

Late interaction (ColBERT) sits between the two: store one vector per token of each document; score a query by summing, for each query token, its maximum similarity to any document token (“MaxSim”). Nearly cross-encoder quality with precomputed document representations, at the cost of much larger indexes (mitigated by compression in ColBERTv2 and PLAID).

Model type Document encoding Query cost Quality
Bi-encoder one vector, precomputed 1 encode + ANN good
Late interaction (ColBERT) one vector per token, precomputed 1 encode + token-level scoring better
Cross-encoder none (query and doc read together) 1 model call per candidate best (for re-ranking)

Chunking

🔧 Intermediate
Strategy How Use when
Fixed size with overlap e.g. 512 tokens, 10–20% overlap baseline; uniform text
Recursive / structural split on headings, then paragraphs, then sentences documents with structure (docs, wikis, Markdown, HTML)
Semantic split where embedding similarity between adjacent sentences drops long unstructured text with topic shifts
Document-specific keep tables, code blocks, list items, Q&A pairs intact PDFs with tables, code, FAQs
Parent–child (small-to-big) index small chunks, return their larger parent section precise matching with enough context
Contextual chunk headers prepend title, section path, or an LLM-written summary of the document chunks that make no sense alone

Always store metadata with each chunk: source, URL, section path, timestamps, ACL groups, tenant, and a document version, so you can filter, cite, and update.

Types of RAG

🌱 Beginner

“RAG” is a family, not one recipe. The simplest version retrieves once and answers. More advanced versions rewrite the question, search several ways, check whether what they found is good enough, search again if it is not, or walk a knowledge graph. Each step adds quality and cost.

A rough progression of RAG designs.

Type How it works Best for / trade-off
Naive (vanilla) RAG embed query, top-\(k\) chunks, stuff into prompt, generate prototypes; fails on vocabulary mismatch and multi-part questions
Advanced RAG pre-retrieval (query rewriting, expansion), hybrid search, re-ranking, context compression the production default; more components to tune
Modular RAG retrieval, routing, memory, and generation as swappable modules wired per use case platforms serving many teams
Hybrid RAG sparse + dense retrieval fused (RRF) mixed queries with names, codes, and paraphrases
Multi-query / RAG-Fusion LLM generates several rephrasings; retrieve for each; fuse ambiguous or short queries; several retrieval calls
HyDE LLM writes a hypothetical answer; embed and search with it sparse questions vs long documents; risk of steering toward a wrong guess
Query decomposition split a complex question into sub-questions, answer each, combine comparisons and multi-part questions
Routing RAG classify the query, send it to the right index, tool, or no retrieval at all many sources; saves cost on questions needing no retrieval
Parent–child / small-to-big match small chunks, return parent sections precise matching plus full context
Contextual retrieval prepend an LLM-generated context sentence to each chunk before embedding and BM25 indexing chunks that lose meaning out of context; one-time indexing cost
Corrective RAG (CRAG) a grader scores retrieved documents; if weak, rewrite the query or fall back to another source (e.g. web search) reducing answers built on irrelevant context
Self-RAG / reflective RAG the model decides when to retrieve and critiques whether its answer is supported, then revises factuality; more calls, needs a capable model or a trained critic
Agentic RAG an agent plans, issues several searches, reads results, and decides when it has enough (often with tools beyond search) multi-hop research questions; least predictable latency and cost
GraphRAG extract entities and relations into a knowledge graph; summarize communities; retrieve via graph neighborhoods or community summaries “global” questions (themes across a corpus) and relationship questions; expensive indexing
Conversational RAG rewrite each turn into a standalone query using chat history before retrieval chat assistants (“what about its price?”)
Multimodal RAG index images, tables, slides, or audio (via captions, OCR, or multimodal embeddings) and pass them to a multimodal model PDFs with figures, slides, product images
Structured / text-to-SQL RAG generate a query against a database or API instead of searching text numbers and aggregates that text search cannot compute
Cache-augmented generation (CAG) skip retrieval: preload a small, stable corpus into the context and reuse its KV cache small corpora with long-context models; limited by context size

RAG variants. Names come from papers and practitioner write-ups; many systems combine several.

🧠 Expert

How to pick: start with advanced hybrid RAG and a re-ranker, measure retrieval recall on an eval set, and add complexity only where the failures are. If answers fail because the right chunk was never retrieved, improve chunking, hybrid search, query rewriting, or contextual retrieval. If the right chunk was retrieved but the question needs several pieces (multi-hop), add decomposition or an agentic loop. If questions are about the whole corpus (“what are the main complaints across all tickets?”), top-\(k\) retrieval cannot answer them; use GraphRAG-style summaries or a map-reduce over many documents. If the corpus is small and stable, consider long-context or cache-augmented generation and skip retrieval.

Evaluating RAG

🔧 Intermediate

Evaluate the two halves separately, then end to end:

  • Retrieval: recall@\(k\) (is a relevant chunk in the top \(k\)?), precision@\(k\), MRR, NDCG@\(k\) on a labeled set of questions with known relevant documents.

  • Generation: faithfulness / groundedness (every claim supported by the retrieved context), answer relevance (answers the question asked), and correctness against a reference answer. These three plus context relevance are often called the “RAG triad”; tools such as RAGAS, TruLens, and DeepEval automate LLM-judged versions.

  • Operational: latency per stage, tokens per answer, cost per query, citation accuracy, and “I don’t know” rate.

Build the eval set from real user questions; a few hundred labeled examples sliced by question type catch most regressions. Re-run it on every change to chunking, embeddings, index parameters, re-ranker, or prompt.

⚠️ Pitfall

  • Dense-only retrieval for queries full of product codes, error messages, or names.

  • Changing the embedding model without re-embedding the whole corpus.

  • Post-filtering with selective permission filters, returning too few (or unauthorized) results.

  • Tuning HNSW or IVF parameters without measuring recall against exact search.

  • Stuffing 50 chunks into the prompt instead of re-ranking to the best 5–10.

  • Choosing an agentic or graph design before measuring where simple RAG fails.

🎤 Interview

“Explain BM25 vs TF-IDF” in 30 seconds: both weight terms by frequency in the document and rarity across the collection; BM25 saturates term frequency (controlled by \(k_1\)) and normalizes by document length relative to the average (controlled by \(b\)), which fixes TF-IDF’s bias toward repetition and long documents. “When would dense retrieval lose to BM25?”: exact identifiers, rare domain terms, new vocabulary the encoder never saw, and very short keyword queries; the fix is hybrid retrieval. “Design RAG over 50M documents with per-user permissions”: chunk with metadata and ACLs, hybrid index with in-index filtering by the user’s groups, RRF, cross-encoder re-ranking, citations, and an eval set measuring recall and faithfulness (Chapter (genai)).

🔑 Takeaways

  • TF-IDF weights frequency by rarity; BM25 adds saturation (\(k_1\)) and length normalization (\(b\)).

  • Dense bi-encoders capture meaning; sparse methods capture exact terms; hybrid plus re-ranking is the default.

  • Vector databases trade recall for speed with IVF, HNSW, and quantization; measure recall against exact search.

  • Filtering strategy and per-query permissions are first-class design decisions.

  • RAG types range from naive to agentic and GraphRAG; add complexity only where measured failures demand it.
