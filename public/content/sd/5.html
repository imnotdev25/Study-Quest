Choosing a database, how indexes work, replication topologies, sharding and rebalancing, distributed SQL, object storage, search, and vector databases.

Choosing a Database

🌱 Beginner

A database is a filing cabinet. Relational (SQL) databases are cabinets with strict labeled folders and cross-references; they keep everything tidy and correct. NoSQL databases are cabinets built for a specific job: very fast lookups by label, huge write volumes, or flexible documents.

Database families

🔧 Intermediate

Start with PostgreSQL unless you have a specific reason not to. With extensions it covers relational, JSON documents (jsonb), full-text search, geospatial (PostGIS), time series (Timescale), and vectors (pgvector). Move to a specialized store when measurement shows Postgres is the bottleneck or the access pattern clearly fits something else.

Indexes and Storage Engines

🔧 Intermediate

An index is a sorted structure that turns a full table scan (\(O(n)\)) into a lookup (\(O(\log n)\)). Two dominant storage engines:

  • B-tree / B+tree (Postgres, MySQL InnoDB): in-place updates, fast reads, good range scans.

  • LSM tree (RocksDB, Cassandra, ScyllaDB): writes go to an in-memory memtable and are flushed to immutable sorted files (SSTables), merged by compaction. Very fast writes; reads may check several files, helped by Bloom filters.

Composite index order matters: an index on (tenant_id, created_at) serves WHERE tenant_id=? ORDER BY created_at but not a query on created_at alone.

Replication

Leader-follower replication

🔧 Intermediate

  • Leader-follower: one writer, many readers. Simple; reads from followers may be stale (replication lag).

  • Multi-leader: writers in several regions; needs conflict resolution.

  • Leaderless: client writes to \(W\) of \(N\) replicas and reads \(R\) (Dynamo, Cassandra).

Synchronous replication waits for followers (no data loss, higher latency). Asynchronous returns immediately (fast, may lose recent writes on failover). Semi-synchronous waits for at least one follower.

🧠 Expert

Replication lag anomalies: a user updates their profile then reloads and sees the old one (read from a lagging follower). Fixes: read-your-writes by routing a user’s reads to the leader for a few seconds after a write, or by tracking the write’s log position and waiting for a follower to reach it. Failover is dangerous: split brain (two leaders) corrupts data. Use consensus-based leader election (Patroni with etcd, Raft-based systems) and fencing tokens so a deposed leader’s writes are rejected. Conflict resolution for multi-leader: last-write-wins (lossy), application merge, or CRDTs (conflict-free replicated data types: counters, sets, and sequences that merge automatically, used in collaborative editors and local-first apps).

Sharding (Partitioning)

🌱 Beginner

When one filing cabinet is full, buy more cabinets and split folders by the first letter of the customer’s name: A–F in cabinet 1, G–M in cabinet 2. That is sharding. The trick is picking a split that keeps cabinets equally busy.

Hash-based sharding

🔧 Intermediate

  • Range sharding: by key range (dates, IDs). Great for range scans; risk of hot spots (all new writes hit the latest range).

  • Hash sharding: by hash of key. Even distribution; range scans span all shards.

  • Directory sharding: a lookup table maps key to shard. Flexible; the directory is a dependency.

  • Geo sharding: by region. Locality and data residency.

Choose a shard key with high cardinality that matches your main access pattern (e.g. tenant_id for SaaS, so one tenant’s queries hit one shard).

🧠 Expert

Sharding costs: cross-shard joins and transactions, global secondary indexes, uneven tenants (one tenant larger than a shard), and resharding. Pre-split into many logical shards (e.g. 4,096) mapped onto fewer physical nodes so rebalancing moves whole logical shards. Tools: Vitess (MySQL, used by YouTube, Slack), Citus (Postgres), or adopt distributed SQL, which shards and rebalances automatically using range partitions replicated by Raft groups.

Specialized Storage

🔧 Intermediate

Object storage (S3) is the backbone of modern data: images, video, backups, logs, and data lakes. Open table formats (Apache Iceberg, Delta Lake, Hudi) add ACID tables on top of object storage, forming the lakehouse. A newer trend is systems that use S3 as their primary storage layer (“diskless” Kafka variants, S3-backed databases, S3 Tables, S3 Vectors) to trade some latency for much lower cost.

Search engines use inverted indexes (term \(\to\) list of documents) with BM25 scoring. Vector databases index embeddings with approximate nearest-neighbor structures:

  • HNSW: multi-layer navigable graph; fast, high recall, memory heavy.

  • IVF: cluster vectors, search nearest clusters only.

  • PQ / scalar / binary quantization: compress vectors 4–32\(\times\).

  • DiskANN: SSD-resident graph index for billions of vectors.

📦 Use case: Multi-tenant SaaS

Postgres sharded by tenant_id with Citus. Small tenants share shards; the three largest tenants get dedicated shards. Every table includes tenant_id and row-level security enforces isolation.

📦 Use case: IoT telemetry at 1M writes/s

Devices write to Kafka; consumers write to ScyllaDB partitioned by (device_id, day) with a clustering key on timestamp. Old data is compacted into Parquet on S3 and queried with an OLAP engine.

📦 Use case: Global user accounts

CockroachDB or Spanner with rows homed in the user’s region (regional-by-row). Logins are local-latency; global uniqueness of email is still enforced.

Deep Dive: Transactions, Isolation, and MVCC

🌱 Beginner

Two people edit the same spreadsheet cell at once. Isolation decides what each of them sees while the other is mid-edit, and whose change survives. Stronger isolation means fewer surprises but more waiting.

🔧 Intermediate

Isolation levels are defined by which anomalies they allow:

Level Default in Dirty Non-repeat. Phantom Skew
Read uncommitted rarely used possible possible possible possible
Read committed Postgres, Oracle, SQL Server no possible possible possible
Repeatable read / snapshot MySQL InnoDB no no mostly no possible
Serializable CockroachDB, Spanner no no no no

  • Dirty read: you see another transaction’s uncommitted write.

  • Non-repeatable read: reading the same row twice gives different values.

  • Phantom: re-running a range query returns new rows.

  • Lost update: two read-modify-write cycles overwrite each other (two clerks both read stock = 5, both write 4).

  • Write skew: two transactions each check a condition, then write different rows, breaking a rule together. Classic example: a hospital requires at least one doctor on call; two doctors both see “2 on call” and both go off call.

🔧 Intermediate

MVCC (multi-version concurrency control) is how Postgres, MySQL InnoDB, and most modern databases implement isolation without readers blocking writers. An update never overwrites a row in place; it writes a new version tagged with the transaction ID that created it. A reader gets a snapshot: the set of transactions committed when it started, and it ignores versions created after. Old versions are cleaned up later (Postgres VACUUM, InnoDB purge). This is why the Notion and Figma cases in Part (cases) were driven by vacuum problems: massive tables produce dead versions faster than cleanup can reclaim them.

🧠 Expert

Fixing lost updates and write skew in practice:

  • Atomic updates: UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty > 0. The check and write happen in one statement; check the affected row count.

  • Explicit locks: SELECT … FOR UPDATE locks the rows you read. For write skew, lock the rows the condition depends on.

  • Optimistic concurrency: a version column; UPDATE … WHERE id=? AND version=7; zero rows updated means someone else won, so retry.

  • Serializable isolation: Postgres’s Serializable Snapshot Isolation detects dangerous read/write patterns and aborts one transaction. The app must retry on serialization failures (SQLSTATE 40001).

Write and read amplification. A B-tree update rewrites a whole page (often 8–16 KB) for a small row change, plus the write-ahead log: write amplification of 10\(\times\) or more for small random writes, but reads touch \(O(\log n)\) pages. An LSM tree writes sequentially and compacts later; total write amplification across compaction levels can be 10–30\(\times\), but it is sequential I/O. Reads may check several levels, helped by Bloom filters (a few bits per key give a 1% false-positive rate). Pick B-trees for read-heavy OLTP and range scans, LSM trees for write-heavy ingestion (Discord, IoT, metrics).

📦 Use case: Selling the last concert ticket twice

Two buyers load a seat and both click buy. Naive code reads status = 'available', then writes 'sold': both succeed under read committed. The fix is a conditional write: UPDATE seats SET status='sold', buyer=? WHERE id=? AND status='available'; exactly one gets 1 row. Ticketmaster-scale systems add short-lived holds with TTLs before payment (Part (cases)).

Deep Dive: Inside a Relational Database

Query Planning

🔧 Intermediate

SQL says what you want; the query planner decides how. It parses the query, considers alternative plans (which index to use, sequential vs index scan, join order, join algorithm: nested loop for small inputs with an index, hash join for large unsorted inputs, merge join for sorted inputs), estimates each plan’s cost from table statistics (row counts, value distributions, histograms), and picks the cheapest. EXPLAIN ANALYZE shows the chosen plan with real row counts and timings; the usual problems are a sequential scan where an index was expected, estimated rows far from actual rows (stale statistics: run ANALYZE), or a function on an indexed column (WHERE lower(email) = ? cannot use an index on email; create an expression index). A plan that changes after a deploy or data growth is a classic latency incident.

Write-Ahead Log and Recovery

🔧 Intermediate

Databases change pages in memory and write them to disk later. To survive crashes, every change is first appended to the write-ahead log (WAL) and the log is fsynced at commit; the data pages can be written lazily. On restart, recovery replays the WAL from the last checkpoint (a point where all earlier changes were flushed to data files), redoing committed changes and discarding uncommitted ones (the ARIES family of algorithms adds undo for steal policies). The same log feeds replication (followers replay it) and change data capture, and point-in-time recovery restores a base backup and replays archived WAL up to any moment. Settings like Postgres synchronous_commit=off trade a small window of possible data loss for faster commits.

A Key-Value Store on SQL

🔧 Intermediate

CREATE TABLE kv (k TEXT PRIMARY KEY, v BYTEA, version BIGINT, expires_at TIMESTAMPTZ) gives a durable, transactional key-value store on infrastructure you already run: get is a primary-key lookup, put is an upsert (INSERT … ON CONFLICT (k) DO UPDATE), compare-and-set uses WHERE version = ?, TTL is a filter plus a periodic cleanup job. It handles thousands to tens of thousands of operations per second per instance and is a good choice before adding Redis or DynamoDB. Uber’s Schemaless and Facebook’s use of MySQL under TAO (Part (cases)) are large-scale versions of this idea.

🔧 Intermediate

Ticket servers: Flickr ran two MySQL servers, one returning odd and one even IDs (auto_increment_increment=2), using REPLACE INTO on a one-row table to draw the next ID; either server could fail. Batching (lease 1,000 IDs at a time) removes the per-insert hop, at the cost of gaps.

Clock skew and ID ordering: time-based IDs are only as ordered as the clocks that generate them. If a machine’s clock jumps backward (NTP correction, VM migration), Snowflake could generate duplicates or out-of-order IDs. Implementations refuse to generate IDs (or wait) until the clock passes the last timestamp used, and alert on large skew. Across machines, IDs are only roughly ordered (within clock skew, typically milliseconds), so never rely on ID order for correctness across machines; use a single sequencer, logical clocks (Chapter (dtx)), or TrueTime-style bounds when you need strict order.

Keyset Pagination

🔧 Intermediate

OFFSET 100000 LIMIT 20 makes the database read and discard 100,000 rows, getting slower with every page, and items shift between pages when rows are inserted. Keyset (cursor) pagination remembers the last row’s sort key: WHERE (created_at, id) < (?, ?) ORDER BY created_at DESC, id DESC LIMIT 20, served by an index on (created_at, id). Every page costs the same, and results are stable. Include a unique tie-breaker (the ID) in the sort key. Return an opaque cursor (base64 of the key) so clients cannot depend on its contents. The trade-off: no “jump to page 57.”

Online Indexing and Schema Evolution

🔧 Intermediate

Adding an index to a large table with a plain CREATE INDEX locks writes for the whole build. Use online methods: Postgres CREATE INDEX CONCURRENTLY (slower, two table scans, does not block writes; if it fails it leaves an invalid index to drop), MySQL InnoDB online DDL, or tools such as gh-ost and pt-online-schema-change that build a shadow table, copy rows in chunks, apply ongoing changes from the binlog or triggers, and swap atomically. Throttle the copy based on replication lag.

Schema evolution without downtime follows expand and contract (Chapter (cicd)): add new columns as nullable or with cheap defaults, deploy code that writes both, backfill in batches, switch reads, stop writing the old column, then drop it. Never rename a column in one step; never add a NOT NULL column with a volatile default to a huge table on older engines. For event and API schemas, only make backward- compatible changes (add optional fields) and version breaking ones.

Soft Delete

🔧 Intermediate

Instead of DELETE, set deleted_at = now(). Benefits: undo, audit, referential integrity for historical records, safer bulk mistakes. Costs: every query must filter WHERE deleted_at IS NULL (enforce with views, row-level security, or the repository layer, or someone will forget); unique constraints must exclude deleted rows (a partial unique index: UNIQUE (email) WHERE deleted_at IS NULL); tables grow forever. Soft delete is not deletion for privacy purposes: personal data must still be purged on schedule or on request (Chapter (obs)). A common hybrid: soft delete for 30 days, then a background job hard-deletes or anonymizes, or move deleted rows to an archive table.

Hot and Cold Storage and Archival

🔧 Intermediate

Most data is read rarely after a few weeks. Keep recent, frequently accessed data in the primary database and caches (hot); move older data to cheaper storage (warm: a separate partition, cheaper instance, or columnar store; cold: Parquet files in object storage, archive storage classes). Techniques: time-based table partitioning (detach and archive old partitions instead of deleting rows), TTLs in key-value stores, object storage lifecycle rules (move to infrequent-access after 30 days, archive after 180). Keep the archive queryable (Athena, BigQuery, Trino over Parquet) and document restore times: archive tiers can take hours to retrieve.

Graph Databases

🔧 Intermediate

Graph databases (Neo4j, Amazon Neptune, TigerGraph) store nodes and edges with index-free adjacency: each node points to its neighbors, so traversals of several hops are fast regardless of total graph size, queried with Cypher or Gremlin. Good fits: fraud rings (accounts sharing devices and cards), knowledge graphs, network topology, permissions graphs, recommendation over multi-hop relationships. Poor fits: simple one-hop social queries at huge scale, where sharded adjacency lists in SQL or key-value stores (TAO, FlockDB) are simpler and faster, and analytics over the whole graph, which is better done in batch graph processing (Spark GraphX, Pregel-style systems).

Deep Dive: Sizing a Database

🔧 Intermediate

A worked example for an order system: 50M orders/day, each 1 KB with indexes, kept 2 years hot.

  • Writes: \(50\text{M}/10^5 = 500\)/s average, 2,000/s at peak. One well-tuned Postgres primary handles this.

  • Storage: \(50\text{M}\times 1\,\text{KB}\times 730 \approx 36\) TB. Too big to keep comfortably in one instance (backups, vacuum, restore time).

  • Working set: if 95% of reads hit the last 30 days, that is \(50\text{M}\times 30\times 1\,\text{KB} = 1.5\) TB; memory for that is expensive but feasible across a few shards.

  • Decision: shard by customer_id (most queries are “my orders”) into 8 physical shards with 256 logical shards; move orders older than 90 days to columnar storage on S3 for analytics.

The forcing function is not QPS here, it is data size and its operational cost (backup/restore time, vacuum, index rebuilds). That is common.

🔑 Takeaways

  • Default to Postgres; specialize when you measure a real need.

  • Replication scales reads and survives failures; sharding scales writes.

  • Pick the shard key around your dominant query.

  • Object storage plus open table formats is the modern data foundation.
